## 1. 方向与帧结构

| 项 | 规则 |
| --- | --- |
| 方向 | **只允许 车 → App**；车端收到 LOG 帧静默丢弃 |
| 帧格式 | `AA | SEQ | [记录 TYPE][记录 param] × 8 | CRC8` |
| 帧长 | **固定 19 字节** = `1 + 1 + 16 + 1`，与任何 TYPE 静态表项无关 |
| 每帧记录数 | 恒为 8 条；不足 8 条用 `0x00 0x00` 补齐 |
| CRC8 | CRC-8/ATM（`0x07`、初值 `0x00`），覆盖 `AA` 到第 8 条记录的 param 字节（共 18 字节） |
| 应答 | **不需要 ACK**，App 不得回 ACK |
| 分片 | 19 字节一个 notify 分片 |

```text
偏移  0     1     2..17（8 条 × 2 字节）        18
     AA   SEQ   [TYPE0 param0] … [TYPE7 param7]  CRC8
```

- 偏移 2 处的字节是**第 1 条记录的 TYPE**，它同时充当帧的“TYPE 位”。因为它最高 2 位恒为 `01`（LOG），
  解析器据此把帧长定为 19；这也是本协议唯一“帧长不查表”的例外。
- 解析时先读偏移 2：`KIND = 该字节 >> 6`；若 `KIND == 1` 就按 19 字节取帧，再逐条解码。
- 末条之后的补齐记录 `TYPE = 0x00`、`param = 0x00`，App 必须跳过 `TYPE == 0x00` 的记录。

## 2. 记录字节：TYPE + param

每条记录 **2 B = 16 bit（TYPE 1 B + param 1 B）**：

| 字节（1 B = 8 bit） | 内容 |
| --- | --- |
| 记录 TYPE | `(KIND_LOG << 6) | (等级分区 << 4) | 模块号`，KIND_LOG = 1，故基址为 `0x40` |
| 记录 param | 事件码或数值；`0x00` 表示“无附加数值” |

`param` 的取值语义（来自 `Protocol.h`）：

| 区间 | 含义 |
| --- | --- |
| `0x00` | 只有事件码、无附加数值（**也用作补齐**） |
| `0x01`~`0x1F` | 模块内事件码（见 §5） |
| `0x20`~`0x2F` | BLE 模块：**未知 CMD** 的 item 编号（`0x20 + item`） |
| `0x30`~`0x3F` | BLE 模块：**参数非法 CMD** 的 item 编号（`0x30 + item`） |
| `0x40`~`0x7F` | 数值/码段（当前固件不产生） |
| `0x80`~`0xFF` | 预留，当前固件不产生 |

> 车端入队规则：`param != 0 ? param : code`。也就是说**如果调用点同时给了事件码和参数，事件码会被参数覆盖**。
> 当前所有调用点都不传 `param`，所以第二字节就是事件码本身。新增调用点时不要两者同时给。

## 4. 等级分区

`等级分区` 占用记录 TYPE 的 bit5-4。固件把 5 个日志等级映射到 3 个分区：

| 分区 | 名称 | 固件等级 | 记录 TYPE 基址 |
| --- | --- | --- | --- |
| 0 | D（调试/信息） | `Debug`、`Info` **都并入 D** | `0x40` |
| 1 | E（错误/致命） | `Error`、`Fatal` **都并入 E** | `0x50` |
| 2 | W（警告） | `Warning` | `0x60` |
| 3 | 预留 | — | 不使用 |

- **D 与 E 各自合并了两个固件等级**，App 无法从帧中区分 `Debug/Info`、`Error/Fatal`，这是协议的有意取舍。
- 举例：模块 1（BLE）的 W 记录 TYPE = `0x40 | 0x20 | 1` = `0x61`。

## 6. 发送节拍与队列

| 项 | 值 |
| --- | --- |
| 队列容量 | 64 条（每条 2 字节，约 1.2 s 突发缓冲） |
| 每帧条数 | 8 |
| 最小帧间隔 | **20 ms** |
| 发送前提 | 已连接 **且** 已完成 `CMD_SESSION_INIT` |
| 队列满策略 | **丢最旧一条**并累加丢弃计数，绝不阻塞调用方 |
| 丢弃计数 | 通过 `DAT_MEM` 的 `logDropped`（偏移 14~15）上报，饱和 65534 |
| 待发计数 | 通过 `DAT_MEM` 的 `logPending`（偏移 12）上报，饱和 255 |
| 无 LEN 的后果 | 每次出队最多 8 条就封一帧，剩余留到下一轮，不跨帧拼包 |
| 优先级 | 每轮 `update()` 的顺序为：DAT 遥测 → DAT_MEM → 实时 LOG → 补发 |

- 未握手时，队列里的日志按“离线规则”处理（见 §7），不会在握手完成后突然涌出旧日志。
- 实时 LOG 与 DAT 共用同一条 BLE 通知通道，每帧 19 字节一个分片，不等待 App 应答。

## 7. 断连补发

| 项 | 规则 |
| --- | --- |
| 缓存对象 | **只缓存 W 和 E 两个分区**；D 分区（Debug/Info）断连即丢 |
| 容量 | 32 条，环形，满时丢最旧 |
| 时效 | 条目从“被捕获时刻”起算，超过 **30000 ms** 未补发即丢弃 |
| 出队时机 | 实时队列为空，且距上一帧 LOG ≥ 20 ms，且距上一帧 DAT ≥ 20 ms |
| 每帧条数 | 8 条（与实时帧同格式），SEQ 与实时帧共用同一计数器 |
| 重发 | 不重试、不重排；只按捕获顺序补最近 32 条 |
| 与握手关系 | 补发不要求重新握手，但要求已连接且已握手；否则继续留在环里等待或超期丢弃 |

- 补发帧与实时帧**格式完全相同**，App 无法区分，也不需要区分。
- 由于 30 s 时效，长时间断连后重连只会收到最近的 W/E，早期的错误不会补。

## 8. 完整帧示例

### 8.1 3 条有效 + 5 条补齐

第 1 条 `D/SYSTEM/READY`（TYPE `0x40`，param 2）、第 2 条 `W/BLE/SEQ_ZERO`（TYPE `0x61`，param 14）、
第 3 条 `E/SYSTEM/BOOT_STOP_TFT`（TYPE `0x50`，param 3），其余 5 条补齐：

```text
AA 06 40 02 61 0E 50 03 00 00 00 00 00 00 00 00 00 00 06
 |  |  |  |  |  |  |  |                          └ CRC8 = 06（覆盖前 18 字节）
 |  |  |  |  |  |  |  └ 第 3 条 param = 3
 |  |  |  |  |  |  └ 第 3 条 TYPE = 0x50（E/SYSTEM）
 |  |  |  |  |  └ 第 2 条 param = 14
 |  |  |  |  └ 第 2 条 TYPE = 0x61（W/BLE）
 |  |  |  └ 第 1 条 param = 2
 |  |  └ 第 1 条 TYPE = 0x40（D/SYSTEM），也决定帧长 = 19
 |  └ SEQ = 6
 └ HEAD
```

### 8.2 满 8 条（无补齐）

```text
AA 07 40 02 61 0E 50 03 68 04 51 01 69 01 55 01 61 31 07
```

逐条解释：

| 序号 | TYPE | param | 含义 |
| --- | --- | --- | --- |
| 1 | `0x40` | 2 | D / SYSTEM / 就绪 |
| 2 | `0x61` | 14 | W / BLE / `SEQ = 0` 非法 |
| 3 | `0x50` | 3 | E / SYSTEM / TFT 初始化失败 |
| 4 | `0x68` | 4 | W / RECORD / 正在录音回放 |
| 5 | `0x51` | 1 | E / BLE / 事件队列创建失败 |
| 6 | `0x69` | 1 | W / MOTOR / 失联自动停车 |
| 7 | `0x55` | 1 | E / AUDIO / I2S 初始化失败 |
| 8 | `0x61` | `0x31` = 49 | W / BLE / 参数非法 CMD，item = 1（`CMD_VOLUME`） |

### 8.3 1 条有效 + 7 条补齐

```text
AA 06 40 02 00 00 00 00 00 00 00 00 00 00 00 00 00 00 FA
```

- App 侧解码步骤：读偏移 2 确认 `KIND = 1` → 固定取 19 字节 → 校验 CRC → 从偏移 2 起每 2 字节一条 →
  跳过 `TYPE == 0x00` 的记录 → 按 `模块号 = TYPE & 0x0F`、`等级 = (TYPE >> 4) & 0x03`、`param` 查表显示。

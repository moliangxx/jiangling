# AI 语音 + 文字双流搭建方案

> 项目：JiangLing AI（ESP32-S3 N16R8，PlatformIO + Arduino 3.x）
> 定位：可评审、可落地的技术文档，不是调研报告。
> 口径：主线是**板子的局域网方案**；本文的 AI 链路是叠在主线上的**第三条通道**，不改动控制（V2.0）与视频（WS）的任何已定约定。

> **术语校准（2026-11-10）**：本文写在协议还叫「V2.0」的时期。现行为 **V21**（`AA|SEQ|TYPE|LEN|PAYLOAD|CRC8`，LEN 定界，版本号 `21`）。文中所有「V2.0 帧」请读作「V21 帧」；凡以「**无 LEN / 定长**」为前提的论证（如第 7 节「变长文本不能塞进 ctrl」）已过时——V21 由 LEN 定界，DAT 可承载 ≤255 B 的变长内容，是否改走 ctrl 需重新评估。链路分工、双流思路与音频规格不受影响。

## 1. 端到端链路总览

```
 ┌─────────────── 车端 ESP32-S3 ───────────────┐        ┌──────── 云端 AI 网关 ────────┐        ┌─── App ───┐
 │                                             │        │                              │        │           │
 │  MEMS 麦克风                                 │        │  ┌─────────┐                │        │           │
 │     │ I2S RX (GPIO7)                         │        │  │  VAD /  │                │        │           │
 │  AudioBus ──► Mic 采样 16 kHz / 16 bit / 单声道│       │  │ 端点检测 │                │        │           │
 │     │ 分块 20 ms = 640 B                    │        │  └────┬────┘                │        │           │
 │  AudioService（上下行 + 抖动缓冲）             │        │       ▼                     │        │           │
 │     │                                       │  WSS   │  ┌─────────┐   ┌────────┐   │        │           │
 │     └────────────► audio↑ ───────────────────┼───────►│  │  ASR    │──►│  LLM   │   │        │           │
 │                                             │  443   │  └─────────┘   └───┬────┘   │        │           │
 │  MAX98357A 功放 + 喇叭                        │        │                    ▼        │        │           │
 │     ▲ I2S TX (GPIO6)                        │        │              ┌─────────┐      │        │           │
 │     └───────────── audio↓ ◄──────────────────┼───────◄│              │  TTS    │      │        │           │
 │        抖动缓冲 30–80 ms                     │        │              └────┬────┘      │        │           │
 │                                             │        │                   │ 音频块     │        │           │
 │                                             │        │                   └─ 文本(同源) │        │           │
 │  ctrl 通道：V2.0 帧（CMD/ACK/DAT/LOG）        │◄──────►│  文本 side-channel            │◄──────►│ 字幕/控制  │
 └─────────────────────────────────────────────┘        └──────────────────────────────┘        └───────────┘
```

三条通道，互不共用 TCP 连接：

| 通道 | 内容 | 端口/协议 | 优先级 |
|---|---|---|---|
| `ctrl` | V2.0 帧（CMD/ACK/DAT/LOG） | TCP 8080（局域网）/ WSS（远程） | 2 |
| `video` | 单帧 JPEG | WS 81（局域网）/ WSS（远程） | 3（最低） |
| `audio` | PCM/Opus 音频块 + 文本 side-channel | WSS 8443 / WSS 443 `/audio` | 1（最高） |

> 为什么必须分开：音频怕队头阻塞、要求低延迟不重传；视频要大包、可丢帧；控制要可靠去重。三种语义塞进一条流一定会互相拖死。

## 2. 逐段规格表（格式 / 采样率 / 包大小 / 协议）

| # | 段 | 数据格式 | 采样率 / 位宽 | 包大小 | 传输 | 备注 |
|---|---|---|---|---|---|---|
| 1 | 麦克风 → I2S | PCM16 小端、单声道 | 16 kHz / 16 bit | DMA 缓冲，20 ms = **640 B** | I2S 标准（Philips） | 现有 `AudioBus`：BCLK=40、LRCLK=41、DATA=42【事实】 |
| 2 | I2S → 设备缓冲 | 同上 | 同上 | 640 B / 20 ms | 内存环形缓冲 | 建议 3–5 块（60–100 ms）抗抖动 |
| 3 | 设备 → 云端（上行） | PCM16 或 Opus | 16 kHz | 640 B（PCM）/ 24–32 kbps（Opus 报文） | WSS 二进制 | 蜂窝/远程优先 Opus，局域网优先 PCM |
| 4 | 云 ASR | 接收上行音频 | 16 kHz | 流式 | WSS | 输出 partial（中间结果）+ final（终稿）文本 |
| 5 | ASR → LLM | 纯文本 | — | 一条消息 | 内部调用 | 携带对话上下文 |
| 6 | LLM → TTS | 纯文本，流式 token | — | 按句切分 | 内部调用 | 按标点切句，出第一句就合成 |
| 7 | TTS → 设备（下行） | PCM16（或 Opus） | 16 kHz（或 24 kHz） | 640 B / 20 ms | WSS 二进制 | 采样率必须与设备喇叭一致，否则设备侧要重采样 |
| 8 | 设备 → 喇叭 | PCM16 小端、单声道 | 16 kHz / 16 bit | 640 B / 20 ms | I2S | 现有 `Speaker`：GPIO6，`play()` 非阻塞【事实】 |
| 9 | 文本 side-channel | UTF-8 文本 + 元数据 | — | 20–300 B / 句 | 同 audio 通道 | 见第 7 节 |

**码率计算（必须能自己算）**

```
裸 PCM 单方向码率 = 采样率 × 位宽 × 声道数
                 = 16000 × 16 × 1 = 256,000 bps = 256 kbps = 32 kB/s
20 ms 一块的字节数 = 16000 × 0.02 × 2 = 640 B
双向合计          = 512 kbps ≈ 0.55 Mbps（含包头与 WS 开销）
```

| 编码 | 单方向码率 | 双向 | 带宽节省 |
|---|---|---|---|
| PCM16 16 kHz | 256 kbps | 0.55 Mbps | 基准 |
| Opus c0（16 kHz 单声道） | 24–32 kbps | 0.05–0.07 Mbps | **约 87%** |

## 3. 双流设计：语音与文字的三种关系

用户要求：**AI 回复必须同时有语音 + 文字**。这里的关键不是"两条流"，而是**文字从哪来**。

### 3.1 三种做法

| # | 做法 | 机制 | 优点 | 问题 |
|---|---|---|---|---|
| **① 同源（推荐）** | 文字 = 喂给 TTS 的那段文本 | LLM 输出文本 → 同时送去 TTS 合成 + 原样回传设备/App | 一份文本、零额外延迟、**保证字幕与语音逐字一致** | 若 TTS 会自动改写（数字读法、缩写展开），字幕与听感有细微差异 |
| ② 独立生成 | LLM 生成"展示文本"，再改写一次生成"播报文本" | 两次 LLM 调用 | 可分别优化书面语/口语 | **延迟 +200–600 ms【推算】**；两段文本可能语义不一致；成本翻倍 |
| ③ 反向 ASR（把 TTS 音频再识别） | TTS 出声 → 再走一次 ASR → 文字 | 复用 ASR 能力 | 理论上"字幕必然与音频一致" | **多一跳、延迟 +200–400 ms【推算】**、误差叠加（ASR 错 → 字幕错）、双向带宽翻倍、TTS 一改就要重跑 |

**结论：采用 ① 同源。** ③ 是用户提出的"用 AI 回复的语音转文字"，看似省事，实际是把 TTS 已经确定的文本再猜一遍——信息量只减不增，纯属浪费。

### 3.2 同源的具体落地形态（字段表，不写代码）

TTS 返回每一句音频时，配套返回一条文本描述：

| 字段 | 类型 | 说明 |
|---|---|---|
| `kind` | u8 | 0x01=音频块，0x02=文本句，0x03=事件（开始/结束/打断） |
| `utteranceId` | u16 | 本次回复的编号，用于把同一轮的音频与文本关联 |
| `sentenceIndex` | u8 | 第几句，从 0 开始 |
| `text` | UTF-8 | 该句文本，建议 ≤ 512 B |
| `audioLen` | u16 | 该句对应音频字节数（可为 0 表示"本句无音频"） |

App 侧按 `utteranceId + sentenceIndex` 对齐：收到 0x02 就立刻上屏，收到 0x01 就播，两者不要求同帧到达。

## 4. 核心决策：语音转文字放在哪一侧

### 4.1 三条路

| 维度 | **A. 设备本地 ASR** | **B. 云端 ASR（推荐）** | **C. 反向 ASR（TTS 再识别）** |
|---|---|---|---|
| 具体形态 | S3 上跑离线模型（Whisper / ESP-SR） | 设备上传音频，云端返回文本 | 把 TTS 输出音频再送 ASR |
| CPU | 开放域模型：单核持续 **80–100%**，不可用【推算】；命令词模型：单核 20–40%【推算】 | 设备 ~0（只做分块与重传） | 云端承担 |
| RAM | Whisper tiny int8 约 **40 MB**，远超 8 MB PSRAM → **不可行**【推算】；ESP-SR 命令词模型为**几百 KB 量级**【公开资料】 | 设备侧 0 | 云端 |
| 延迟 | 本地 200–600 ms（且仅限命令词）【推算】 | 150–400 ms（流式首字）【推算】 | B 的延迟 + 200–400 ms【推算】 |
| 准确率 | 命令词 95%+（限定词表）；开放域 <50%【推算】 | 95–98%【推算】 | 低于 B（误差叠加） |
| 上行带宽 | **0** | 256 kbps（PCM）/ 24–32 kbps（Opus） | 同 B，且下行还要再传一份 |
| 开发量 | 高（模型移植、内存布局、唤醒词调优） | 中（WSS + 鉴权 + 重连） | 低但无收益 |
| 离线可用 | **是** | 否 | 否 |
| 结论 | 仅用于**唤醒词 + 固定指令**（"向前""停下"），不做开放域 | **主用** | **不采用** |

### 4.2 S3 本地跑 ASR 的现实可行性（结论要硬）

- **Whisper tiny 不可行**：39 M 参数，int8 量化后约 40 MB，而 N16R8 的 PSRAM 只有 8 MB；且 S3 无 SIMD/向量指令，推理速度远低于实时【推算】。**直接排除。**
- **ESP-SR（乐鑫官方）可行但有边界**：`WakeNet`（唤醒词）+ `MultiNet`（命令词）模型体积在几百 KB 级，可跑在 S3 上；但它只识别**预设词表**，不是通用听写。
- **因此推荐组合**：本地 `WakeNet` 做唤醒 + 云端 ASR 做内容识别。唤醒词常驻不耗云资源，内容识别准确率有保证。

### 4.3 一个例外：什么时候值得用 C

只有一种情况：**TTS 被第三方改写且拿不到原文**（例如接入的 TTS 服务只返回音频流、不返回文本）。这时才考虑反向 ASR，并且要在文档里明确"字幕以听感为准，可能与原文有差"。

## 5. ESP 发送端三种输入模式

用户说"ESP 发送可以文字/语音，或者两个一起"。这里的"发送"是**用户向 AI 输入的方式**。

| 模式 | 上行内容 | 流量 | 端到端延迟 | 适用场景 | 代价 |
|---|---|---|---|---|---|
| **只文字** | App 键盘输入 → 一条文本消息 | ≈ 0.1–1 kB/次 | **最低**（省掉采集 + ASR，约省 300–600 ms） | 安静环境、弱网、隐私场合、精确指令 | 失去"免手操作" |
| **只语音** | 麦克风 PCM/Opus → 云端 ASR | 0.55 Mbps（PCM）/ 0.06 Mbps（Opus） | 标准 | 双手占用（驾驶/手持设备）、日常对话 | 噪声环境准确率下降 |
| **两者一起** | 语音上行 + 同时带一段文本（App 已有字幕/候选词） | 语音流量 + <1 kB | 略高于只语音 | 语音为主、文字纠错（"我刚才说的是 X 不是 Y"） | 需要 App 与设备共同时序，实现复杂度最高 |

**推荐**：一期只做「只文字」与「只语音」两种，二选一由 App 开关；「两者一起」作为后续增强，不进一期范围。

## 6. 网络连接与配网

### 6.1 联网路径

| 步骤 | 做什么 | 失败处理 |
|---|---|---|
| 1 | 上电，从 NVS 读 WiFi 凭据（SSID / 密码） | 无凭据 → 进 SoftAP 配网模式 |
| 2 | STA 连接路由器，DHCP 取地址 | 30 s 超时 → 重试 3 次 → 转 SoftAP |
| 3 | SNTP 对时 | **TLS 校验证书必须有正确时间**，对时失败则改用证书 pin |
| 4 | 出站 TLS 连接 AI 网关 `443` | 退避重连 |
| 5 | 发送 AUTH（设备 ID + HMAC-SHA256 签名 + 时间戳 + nonce） | 失败 5 次 → 停止 10 分钟 |
| 6 | 服务端回 READY | — |
| 7 | 按需开 audio 通道（用户说第一句话时） | 单独重连，不影响 ctrl |
| 8 | 心跳开始（WS ping 15 s） | 45 s 无响应 → 主动重连 |

【事实】ESP32-S3 只有 2.4 GHz 射频，**路由器若只开 5 GHz，设备连不上**。

### 6.2 配网（两种，按优先级）

| 方式 | 流程 | 优点 | 缺点 |
|---|---|---|---|
| **BLE 传凭据（主）** | App 通过 BLE NUS 下发一条"WiFi 凭据"命令（SSID + 密码，建议单独 TYPE，不进 V2.0 的运动/音频分区） | 不需要切 WiFi、不需要知道设备 IP | 需要 App 有 BLE 权限 |
| **SoftAP 兜底** | 设备开 `JiangLing_xxx` 热点，App 连上后访问 `192.168.4.1` 配网页面 | 跨平台、可网页配网 | 手机要切网络；NAP 需显式开启才能出公网 |

【事实】本项目预编译库已编译 NAPT（`CONFIG_LWIP_IPV4_NAPT=1`，`dio_opi` 变体），但 Arduino 运行时默认不开启，需要 `WiFi.AP.enableNAPT(true)`，且必须在 `softAP()` 之后调用。

### 6.3 鉴权与重连

| 项 | 建议 |
|---|---|
| 设备身份 | NVS 存 `devId`（16 hex）+ 32 B 预共享密钥 |
| 鉴权方式 | TLS 建立后首条消息：`devId + ts + nonce + HMAC-SHA256(secret, devId|ts|nonce)` |
| 时间窗 | ±60 s，nonce 去重 |
| 心跳 | WS ping 15 s；应用层 30 s 无任何下行判离线 |
| 重连 | 1 / 2 / 4 / 8 / 15 / 30 s 指数退避，±20% 抖动 |
| 降级 | 重连期间音频切 Opus 低码率，视频降到 QVGA 5 fps |

## 7. 文字如何送到 App

### 7.1 三种可选通道

| 方案 | 做法 | 优点 | 问题 | 结论 |
|---|---|---|---|---|
| **① audio 通道 side-channel（推荐）** | 在同一条 audio WS 上交替发 0x01 音频块 / 0x02 文本句 | 与语音**天然按句对齐**；一条连接保序；无额外握手 | 需要区分消息类型（1 字节就够） | **采用** |
| ② 走 ctrl 通道（V2.0） | 新增一个 DAT 类型承载文本 | 复用已有通道 | 文本是变长的，V2.0 是**定长无 LEN** 协议，变长文本要拆片/限长，污染协议；且 ctrl 上与 ACK/DAT 混流，还要额外关联 ID | 不采用 |
| ③ 单独开一条文本 TCP/WS | 独立连接 | 隔离彻底 | 多一条 TLS 握手与心跳，收益为零 | 不采用 |

### 7.2 为什么文字不需要单独开一条 TCP

1. 一条 WS 已经**保序**，文本与音频在同一连接上不会乱序；
2. 文本量极小（<300 B/句，对话 1 句/几秒），对 TCP 的占用可忽略；
3. 多开连接 = 多一次 TLS 握手（S3 上约 40–60 KB heap + 200–600 ms【推算】），纯负担；
4. 文本可丢、音频不可丢，但两者共用一条流时，文本丢一帧不影响播放，反而更简单（不需要为文本做重传）。

**注意**：文本消息不能阻塞音频发送路径——文本用独立的小 buffer，发不出去就丢（字幕可补），不要让它加入音频的重传队列。

### 7.3 消息格式建议（字段表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `kind` | u8 | 0x01 音频块 / 0x02 文本句 / 0x03 事件 |
| `flags` | u8 | bit0=final（是否终稿），bit1=partial |
| `utteranceId` | u16 | 本轮回复 ID |
| `sentenceIndex` | u8 | 句序号 |
| `payloadLen` | u16 | 后续负载长度 |
| `payload` | bytes | 音频字节 或 UTF-8 文本 |

## 8. 专业知识：人话 ↔ 术语对照

### 8.1 VAD（Voice Activity Detection，语音活动检测）

**人话**：判断麦克风这一刻收到的到底是"人说话"还是"空调声/风扇声/静音"。
**作用**：静音不上传，省带宽；也是端点检测的前置。

### 8.2 端点检测（Endpointing）

**人话**：判断"这句话说完了没有"。VAD 只回答"有没有声音"，端点检测要回答"停了多久算说完"。
**为什么是最大瓶颈**：说完全靠"静音持续 500–800 ms"来判，这段时间用户已经在等。**本方案中建议把静音阈值压到 300–500 ms**，并允许用户打断。

### 8.3 流式 ASR（Streaming ASR）

**人话**：边说边出字，不是等你说完再识别。
**价值**：把"首字延迟"从整句时长降到 100–300 ms。

### 8.4 首字延迟（TTFT，Time To First Token）

**人话**：从"说完"到"听到 AI 第一个字"，中间等多久。

### 8.5 抖动缓冲（Jitter Buffer）

**人话**：网络送来的音频块忽快忽慢，先攒几十毫秒再匀速喂给喇叭，避免声音一顿一顿。
**本项目取值**：30–80 ms；太小会卡顿，太大会增加延迟。

### 8.6 barge-in（打断）

**人话**：AI 正在说话时用户开口，立刻停止播放并开始听。
**必要条件**：设备侧有本地 VAD + 扬声器可立即停；不能等云端往返。

### 8.7 AEC（Acoustic Echo Cancellation，回声消除）

**人话**：喇叭放出来的声音会被自己的麦克风收回去，AI 就会"听到自己说话"。AEC 把这段已知的播放信号从麦克风信号里减掉。
**本项目的特殊性**：MAX98357A 功放与麦克风在**同一块板上**，结构回声强，**AEC 几乎是必需的**，否则 TTS 一出声就会自我触发。乐鑫 ESP-SR 的 AFE 提供 AEC，但会额外占用 10–20% 单核 CPU【推算】。

### 8.8 Opus vs PCM

| | PCM | Opus |
|---|---|---|
| 本质 | 原始采样，不压缩 | 有损压缩编码 |
| 码率 | 256 kbps（16 k 单声道） | 24–32 kbps |
| 延迟 | 最低（≈0） | +5–15 ms |
| CPU | ≈0 | 编码 26%（c0）/ 34%（c2）/ 49%（c5）单核【用户提供数据】 |
| 适用 | 局域网、有线 | 蜂窝、远程、弱网 |

### 8.9 采样率与位宽

- **采样率 16 kHz**：每秒采 16000 个点，能还原 0–8 kHz 的声音，覆盖人声主要能量。
- **位宽 16 bit**：每个点用 2 字节表示幅度，动态范围约 96 dB。
- 8 kHz 会明显损失齿音；48 kHz 对语音是浪费（带宽 ×3）。

## 9. 限制（技术 / 硬件 / 网络）

### 9.1 技术限制

| 限制 | 数值 | 影响 | 缓解 |
|---|---|---|---|
| 单核音频编码占用 | Opus c0 **26%**、c2 **34%**、c5 **49%**【用户数据】 | c5 与 JPEG 编码叠加会挤爆 | 只用 c0；音频独占一核 |
| TLS 握手内存 | 约 40–60 KB heap/连接【推算】 | 三条通道 = 三份 | 用 ECDSA P-256 证书；PSRAM 兜底 |
| 变长文本与 V2.0 | V2.0 是**定长无 LEN** | 文本不能塞进 V2.0 | 文本走 audio 通道 |
| AEC 开销 | +10–20% 单核【推算】 | 与视频编码争抢 | 仅在"喇叭正在播放"时开 AEC |
| 端点检测延迟 | 300–800 ms | 主观"反应慢" | 压到 300–500 ms + barge-in |

### 9.2 硬件限制

| 限制 | 数值 | 影响 |
|---|---|---|
| PSRAM | 8 MB（OPI，GPIO33–37 被占用） | 放不下 Whisper tiny（约 40 MB） |
| 麦克风与功放同板 | 结构回声强 | 必须 AEC |
| 功放增益 | MAX98357A 增益由板载电阻固定【事实】 | 软件只能做数字衰减，不能提升物理增益 |
| I2S 引脚 | BCLK=40 / LRCLK=41 / MIC=42 / SPK=47【事实】 | 不可挪用 |
| WiFi 频段 | 2.4 GHz only | 路由器只开 5 GHz 时不可用 |
| 供电 | 功放峰值电流较大 | 与舵机、4G 模块共用电源时要单独估算 |

### 9.3 网络限制

| 限制 | 数值 | 影响 |
|---|---|---|
| 上行带宽（PCM） | 256 kbps/向 | 蜂窝下流量约 **115 MB/小时** |
| 上行带宽（Opus） | 24–32 kbps/向 | 蜂窝下约 **11–14 MB/小时** |
| 视频共存 | QVGA 1–2 Mbps | 与音频合计 1.1–2.1 Mbps |
| BLE 共存 | 2.4 GHz 共享射频 | 三者同时活跃时视频必须降档 |
| 公网 RTT | 同城 10–30 ms / 跨省 40–80 ms【推算】 | 音频抖动缓冲要按 P95 设计 |

## 10. 专业名词表

| 术语 | 人话解释 |
|---|---|
| **ASR** | 语音识别，把声音变成文字 |
| **TTS** | 语音合成，把文字变成声音 |
| **LLM** | 大语言模型，生成回复文本 |
| **VAD** | 判断"有没有人在说话" |
| **Endpointing（端点检测）** | 判断"这句话说完了没有" |
| **Streaming ASR（流式识别）** | 边说边出字，不用等整句 |
| **TTFT（首字延迟）** | 说完到听到第一个字的时间 |
| **Jitter Buffer（抖动缓冲）** | 先攒一小段音频再匀速播放，抗网络抖动 |
| **Barge-in（打断）** | AI 说话时用户开口立即停止播放 |
| **AEC（回声消除）** | 把喇叭放出来的、被麦克风收回来的声音减掉 |
| **Opus** | 一种低码率语音压缩编码 |
| **PCM** | 未压缩的原始音频采样 |
| **Sample Rate（采样率）** | 每秒采集多少个声音点，16 kHz 即每秒 16000 点 |
| **Bit Depth（位宽）** | 每个采样点用多少位表示，16 bit = 2 字节 |

| **Side-channel** | 在同一条连接上附带传输的辅助信息（本文指文本） |
| **WSS** | 加密的 WebSocket（WebSocket over TLS） |
| **SNTP** | 简单网络时间协议，用于对时（TLS 校验证书必需） |
| **HMAC** | 用密钥做的消息签名，用于鉴权 |
| **NVS** | ESP32 的非易失存储区，存 WiFi 凭据和设备密钥 |

## 11. 与已定方案的一致性声明

1. 本方案**不新增任何 V2.0 命令 TYPE**；AI 的控制意图由 App/网关转换成已有的 `CMD_FORWARD`/`CMD_STOP` 等帧，走 ctrl 通道。
2. **共用 SEQ、`SEQ=0` 免去重**原样生效——AI 在设备眼里就是"另一个 App"，不需要特殊处理。
3. **视频始终走 WiFi**，音频通道与视频通道分开，互不影响。
4. BLE 模式下，音频与视频都走**局域网 WiFi**，BLE 只承载 ctrl（NUS 吞吐不足以承载音频）。
5. 本文所有"建议"均为可选项；与"已定"冲突时以已定项为准。

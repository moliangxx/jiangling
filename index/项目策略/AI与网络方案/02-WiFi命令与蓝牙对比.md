# WiFi 传命令 vs 蓝牙（局域网效率与距离对比）

> 项目：JiangLing AI（ESP32-S3 N16R8）
> 定位：回答"局域网里用 WiFi 传命令，和蓝牙比到底差多少、值不值得做"。
> 结论先行见第 0 节，数据在第 1–3 节，判定标准在第 4 节。

> **术语校准（2026-11-10）**：本文写在协议还叫「V2.0」的时期，现行为 **V21**（`AA|SEQ|TYPE|LEN|PAYLOAD|CRC8`）。文中「V2.0 帧」读作「V21 帧」；第 3 节的「帧长」应按 `5 + LEN` 重算（单字节 LEN 使帧多 1 B）。吞吐量级与「WiFi 更适合大包、BLE 适合小命令」的结论不变。

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 单看"传命令"，WiFi 比 BLE 强很多吗？ | **强 1000 倍以上，但这是浪费**。命令需求 < 1 kB/s，BLE 已有 10–25 倍余量 |
| 那 WiFi 命令还值得做吗？ | **值得，但理由不是带宽**：本项目视频必须走 WiFi，命令搭在同一条 TCP 上边际成本≈0；且远程场景只能走 WiFi |
| 距离谁远？ | **WiFi 明显更远**（空旷 100–300 m vs BLE 30–100 m），但距离由**发射功率与天线**决定，不是协议 |
| 用户说的"差不多就不用做"成立吗？ | **不成立**——两者在"命令带宽"上确实都够用，但 WiFi 的收益在**链路复用**与**远程可延展**，不在命令本身 |

## 1. 效率对比：吞吐 / 延迟 / 功耗 / 连接

### 1.1 有效吞吐

| | BLE（NUS + MTU 247） | WiFi（2.4 GHz HT20，单客户端 TCP） |
|---|---|---|
| 理论单包负载 | MTU 247 → 通知负载 **244 B** | 无 MTU 限制，按 MSS 分片（约 1460 B/包） |
| 典型连接间隔 | 15–30 ms（可协商） | 不适用 |
| 理论吞吐 | 244 B / 15 ms ≈ **16.3 kB/s（130 kbps）** | PHY 72 Mbps（HT20 MCS7），TCP 实际 8–15 Mbps |
| **实测区间** | **10–25 kB/s**（受连接间隔、调度、共存影响）【实测区间】 | **6–15 Mbps**（单客户端、无干扰）【实测区间】 |
| 与 BLE 共存时 | — | **6–10 Mbps**（前文口径） |
| 提升空间 | ESP32-S3 支持 BLE 5（2M PHY / Coded PHY）【手册事实】，但 Arduino BLE 库通常未暴露 2M PHY，实际用不到 | 换 5 GHz 不可能（S3 只有 2.4 GHz） |

### 1.2 延迟（命令 → ACK 往返）

| | BLE | WiFi（同 AP） |
|---|---|---|
| 单程基础 | 连接间隔的一半（7.5–15 ms）+ 协议栈 | 空口 1–3 ms + 协议栈 |
| **P50** | **30–60 ms**【实测区间】 | **15–30 ms**【前文口径】 |
| **P95** | **150–250 ms**【实测区间】 | **80–120 ms**【前文口径】 |
| 抖动来源 | 连接间隔调度、手机侧省电策略、与 WiFi 共存 | 信道竞争、重传、AP 排队 |
| 最坏情况 | 手机进入深度省电时可达 **数百 ms** | 信道拥塞时 100–300 ms |

> 关键差异：BLE 的延迟**下限由连接间隔锁定**，无法低于 7.5 ms；WiFi 的延迟下限可以做到个位数毫秒，但**抖动更大**。

### 1.3 功耗（ESP32-S3，连接态）

| 状态 | BLE | WiFi |
|---|---|---|
| 连接态平均电流 | **15–40 mA**【实测区间】 | **80–120 mA**（关闭 modem sleep）【实测区间】 |
| 发射峰值 | 约 **60–90 mA**【实测区间】 | **240–350 mA**（20 dBm 附近）【实测区间】 |
| 省电机制 | 连接间隔拉长可显著省电 | `WIFI_PS_MIN_MODEM` 可省电，但引入 20–100 ms 抖动 |
| 对本项目的影响 | 适合"待机等命令" | 视频必须常开，功耗已被视频决定，命令的边际功耗≈0 |

**这是 WiFi 命令"几乎免费"的核心依据**：只要视频在跑，WiFi 射频本来就醒着，多跑几 kB/s 的命令不增加任何功耗。

### 1.4 连接建立与并发

| | BLE | WiFi |
|---|---|---|
| 首次连接时间 | 扫描 + 连接 + 服务发现 **1–3 s**【实测区间】 | 关联 + DHCP **2–5 s**（已存凭据时 1–3 s）【实测区间】 |
| 重连时间 | 0.1–1 s（已绑定） | 1–3 s |
| 并发客户端 | 理论 7 个，实际 1–3 个 | SoftAP 最多 8 个（`CONFIG_LWIP_DHCPS_MAX_STATION_NUM 8`【事实】），实际 3–5 个稳定 |
| 配对/鉴权 | 系统级配对，跨平台体验不一 | 无配对概念，靠应用层 token |

### 1.5 抗干扰

| | BLE | WiFi |
|---|---|---|
| 频段 | 2.4 GHz，**自适应跳频**（37 个信道跳） | 2.4 GHz，固定信道（1/6/11） |
| 抗窄带干扰 | **较好**（跳频天然规避） | 较差（信道被占就整体退化） |
| 抗 WiFi 拥塞 | 会与同频 WiFi 争抢，但跳频能绕开部分 | 直接面对拥塞 |
| 与自身 WiFi 共存 | ESP32 内部做时分调度，会互相降速 | — |

## 2. 极限距离对比

| 场景 | BLE | WiFi 2.4 GHz |
|---|---|---|
| **空旷视距** | **30–100 m**【实测区间】 | **100–300 m**【实测区间】 |
| **室内（1 堵墙）** | **10–20 m**【实测区间】 | **20–40 m**【实测区间】 |
| **室内（2–3 堵墙）** | **5–10 m**，明显不稳【实测区间】 | **10–20 m**，速率下降但可连【实测区间】 |
| 加中继/ mesh | 不支持（BLE mesh 是另一套，不做透传） | **可扩展**，多 AP / mesh 无缝 |
| 板载 PCB 天线 | 0 dBm 级发射，增益约 0–2 dBi | 约 20 dBm（可调），增益约 2–3 dBi |
| 理论增强 | BLE 5 Coded PHY（S=8）可到 200 m+，但需两端支持，Arduino 库未暴露 | 提高发射功率 / 换高增益天线 |

**必须讲清的一句**：距离取决于 **发射功率 + 天线增益 + 接收灵敏度 + 环境衰减**，协议只决定"在同等射频条件下能跑多快"。WiFi 距离远，是因为它允许更高的发射功率（20 dBm vs BLE 的 0–10 dBm 级），不是因为"WiFi 这个协议更强"。

## 3. 折算：每秒能发多少条 V2.0 命令帧

V2.0 帧长（`AA + SEQ + TYPE + PAYLOAD + CRC8`，无 LEN）：

| 帧 | 长度 |
|---|---|
| `CMD_STOP`（无 payload） | **4 B** |
| `CMD_FORWARD`（1 B payload） | **5 B** |
| `ACK_RESULT`（2 B payload） | **6 B** |
| 一次"命令 + ACK"往返 | **约 11 B** |

| | BLE（16 kB/s 理论 / 10–25 实测） | WiFi（10 Mbps） |
|---|---|---|
| 单向命令帧/秒（按 5 B） | **2000–5000 帧/s**【推算】 | **25 万帧/s**（理论，实际受应用层限制）【推算】 |
| 命令+ACK 往返/秒 | **900–1400 对/s**【推算】 | **11 万对/s**【推算】 |
| **本项目实际需求** | 运动命令 5–10 Hz + ACK ≈ **10–20 对/s** | 同左 |
| **余量** | **50–100 倍** | **数千倍** |

**结论**：命令带宽对两者都是"严重过剩"。用吞吐来论证"WiFi 比 BLE 好"是没有意义的。

## 4. 判定标准：什么场景值得做 WiFi 命令

### 4.1 判定表

| 产品形态 | 需要视频？ | 需要远程？ | 结论 |
|---|---|---|---|
| 纯命令小车（无视频、无远程、电池供电） | 否 | 否 | **只做 BLE**。WiFi 命令纯属增加功耗与复杂度 |
| **本项目（有视频、要远程）** | **是** | **是/后续** | **做 WiFi 命令**，但定位是"视频链路的副产物"，不是独立收益 |
| 有视频、不远程 | 是 | 否 | 建议做：命令与视频共用一条 TCP，省掉 BLE 的 MTU 分片与两套链路状态 |
| 无视频、要远程 | 否 | 是 | 必须做 WiFi（远程只能走 IP） |

### 4.2 判定标准（可量化）

> **如果"命令带宽需求 < 链路能力的 5%，且没有必须走 IP 的其他业务（视频/远程/OTA/AI）"，就不要单独为命令做 WiFi。**
>
> 本项目不满足该条：视频与 AI 音频都只能走 IP，因此 WiFi 命令的边际成本≈0，应该做。

### 4.3 WiFi 命令的真实收益（不是带宽）

1. **链路复用**：命令、视频、AI 音频共用一套 IP 栈与鉴权，不用维护 BLE 与 WiFi 两套连接状态。
2. **免 MTU 分片**：BLE 的 244 B 负载上限逼着应用层做分片/合帧；TCP 没有这个约束（虽然 V2.0 帧本身很小）。
3. **远程可延展**：同一套 TCP + V2.0 帧，改个地址就能走公网 relay（见文档三）。
4. **多客户端**：WiFi 可同时接手机 + 电脑 + AI 网关；BLE 实际只能一对一。
5. **延迟下限更低**：WiFi P50 15–30 ms，BLE P50 30–60 ms。

### 4.4 WiFi 命令的真实代价

| 代价 | 说明 |
|---|---|
| 功耗 | 射频常开，80–120 mA（但视频已经常开，命令不额外增加） |
| 连接建立慢 | 1–5 s，比 BLE 首次连接慢 |
| 配网复杂 | 需要 SSID/密码，需要 BLE 配网或 SoftAP 兜底 |
| 抗干扰弱 | 2.4 GHz 固定信道，拥挤环境抖动大 |
| 安全面 | IP 可达即被扫描，必须鉴权（BLE 有系统级配对） |

## 5. V2.0 协议在 WiFi 上怎么跑

### 5.1 承载方式

| 项 | 局域网 WiFi 做法 |
|---|---|
| 传输层 | **TCP 字节流**（端口 8080） |
| 解析 | **完全复用现有 `FrameCodec`**：扫 `0xAA` → 查 `payloadLengthOf(type)` 静态表 → 校验 CRC8 |
| 分帧 | 不需要额外分帧：V2.0 帧自带 `AA` 同步头 + 定长表，字节流里直接能切 |
| 半帧处理 | 沿用现有 1 s 超时逻辑（TCP 保序，不会出现 BLE 那种乱序） |
| 未知 TYPE | 沿用现有策略：丢 1 字节重扫，**不回 ACK** |
| 方向强制 | CMD 只 App→车；LOG/DAT/ACK 只车→App（与 BLE 完全一致） |

### 5.2 SEQ 与去重

| 项 | 结论 |
|---|---|
| SEQ 来源 | **App 侧单一全局计数器**，与链路无关 |
| 去重表 | **设备侧只有一份 64 条环**，BLE 与 WiFi 共用 |
| `SEQ=0` | **免去重**，可重复使用（用于幂等/状态类命令） |
| 两条链路同时在线 | **允许**（设备不做冲突防御），由 App 侧策略决定从哪条发 |
| 唯一纪律 | 同一时刻只允许**一个 App 实例**持有控制权（否则两份 App 各自从 0 计数，会撞） |

### 5.3 与 BLE 实现的差异（改造点）

| 差异 | BLE 现状 | WiFi 需要 |
|---|---|---|
| 数据入口 | `BLECharacteristicCallbacks::onWrite` → 事件队列 | `WiFiClient`/`NetworkServer` 的读回调或轮询 |
| 分片 | 单次写入 ≤ 244 B，可能一帧跨多个通知 | TCP 自动重组，但一帧可能跨多个 `read()` |
| 背压 | 通知无背压，发了就发 | 需要处理 `write()` 阻塞与 `availableForWrite()` |
| 断连语义 | 断开即清会话状态 | 需要保留会话状态（重连后不重新握手也可继续） |
| 连接状态 | `_connected` 标志 | 需要维护 socket 集合 |

> 结构上，这些差异正好落在前面方案里的 `ITransport` 抽象：BLE 与 WiFi 各实现一份，**`FrameCodec` 与业务层完全共用**。

## 6. 限制（技术 / 硬件 / 网络）

### 6.1 技术限制

| 限制 | 数值 | 影响 | 缓解 |
|---|---|---|---|
| BLE MTU | 247（协商值），负载 244 B | 大帧必须分片 | V2.0 帧最大 23 B，实际无压力 |
| BLE 连接间隔 | 15–30 ms | 延迟下限 7.5–15 ms | 需要更低延迟只能改连接参数（耗电） |
| WiFi 抖动 | P95 80–120 ms | 运动命令需 5 Hz 重发 | 设备 1 s 无命令自动停，容忍丢 1–2 帧 |
| 双链路状态 | 两套连接、两套超时 | 代码复杂度上升 | 用 `ITransport` 抽象统一 |
| SEQ 共用 | 一份去重表 | 两个 App 会撞 | 只允许一个 App 持有控制权 |

### 6.2 硬件限制

| 限制 | 数值 | 影响 |
|---|---|---|
| 射频共存 | WiFi + BLE + 摄像头共用 2.4 GHz 与天线 | 三者同时活跃时视频必须降档（QVGA 8–10 fps） |
| 单射频 APSTA | AP 与 STA 分时，聚合吞吐为单 STA 的 50–70%【推算】 | SoftAP 与 STA 同时用时吞吐减半 |
| 发射功率 | WiFi 约 20 dBm；BLE 0–10 dBm 级 | 距离差异的主因 |
| 电源 | WiFi 峰值 240–350 mA | 与舵机、功放共用时要单独估算瞬态 |
| 发热 | 持续 4 Mbps 视频 + WiFi 常开 | S3 与功放区域会明显升温，需留散热 |

### 6.3 网络限制

| 限制 | 数值 | 影响 |
|---|---|---|
| WiFi 频段 | 仅 2.4 GHz | 路由器只开 5 GHz 时设备连不上 |
| 信道 | 1/6/11 固定 | 邻居多时整体退化 |
| 单客户端吞吐 | 6–15 Mbps | 视频 5 Mbps 时剩余给命令与音频的余量仍充足 |
| BLE 吞吐 | 10–25 kB/s | 够命令，**不够音频**（音频最低 24 kbps 且要求低抖动） |
| 距离 | 室内穿墙衰减大 | 车体/金属结构会进一步削弱 |

## 7. 专业名词表

| 术语 | 人话解释 |
|---|---|
| **NUS（Nordic UART Service）** | 一种把 BLE 当串口用的标准服务，本项目用的是它的自定义 UUID 版本 |
| **MTU** | 一次 BLE 数据包最多能装多少字节，247 表示 244 B 有效负载 |
| **连接间隔（Connection Interval）** | BLE 主从双方约定多久通信一次，15 ms 表示每 15 ms 交换一次数据 |
| **通知（Notification）** | BLE 从设备主动向主机推送数据的方式 |
| **跳频（FHSS）** | BLE 在 37 个信道间快速跳转，避开干扰 |
| **HT20** | WiFi 20 MHz 信道带宽，2.4 GHz 的常见模式 |
| **MCS7** | WiFi 调制编码方案等级，数值越高越快但越怕干扰 |
| **RTT** | 往返时延，一次请求到收到响应的时间 |
| **P95** | 95% 的请求都快于这个值，用来描述"通常最坏情况" |
| **背压（Backpressure）** | 发送方比接收方快时，让发送方等待或丢弃的机制 |
| **字节流 vs 报文流** | TCP 是字节流（没有天然边界），BLE 通知是报文流（一次一条有边界） |
| **APSTA** | 设备同时当热点（AP）又当客户端（STA） |
| **射频共存（Coex）** | 同一芯片上 WiFi 与 BLE 共享天线与射频时的调度机制 |

## 1. 接入总览

**一句话**：设备作为**出站 WebSocket 客户端**连小智的公共云，用 JSON 文本帧交换状态、用二进制帧收发 Opus 音频；**唤醒、播放结束计时、小车控制三段完全是我们自己的**。

```
┌──────────────── 车端 ESP32-S3（我们自己的固件） ────────────────┐        ┌──── 小智公共云（第三方）────┐
│                                                                │        │                            │
│  【我们的】WakeNet 唤醒（本地）                                  │        │   ASR → LLM → TTS          │
│        │ 命中                                                    │        │                            │
│        ▼                                                        │  WSS   │                            │
│  Opus 编码 ── audio↑（二进制帧）───────────────────────────────┼───────►│  16 kHz 上行 / 可能 24 kHz 下行│
│                                                                │  443   │                            │
│  Opus 解码 ◄── audio↓（二进制帧）──────────────────────────────┼───────◄│  tts start / stop / 文本    │
│        │                                                       │        │                            │
│  【我们的】播放结束 → 本地 30 s 计时启动                          │        │                            │
│                                                                │        │                            │
│  【我们的】控制链路：V2.0 帧（BLE / WiFi TCP 8080）              │        │                            │
└────────────────────────────────────────────────────────────────┘        └────────────────────────────┘
```

| 段落 | 归属 | 说明 |
|---|---|---|
| 唤醒词检测 | **我们**（本地） | 命中后才建立 WSS、才开始推流 |
| 音频采集 / 编码 | 我们（格式受它约束） | Opus 16 kHz 单声道 60 ms |
| ASR / LLM / TTS | **它** | 不落本地 |
| 音频解码 / 播放 | 我们 | 下行可能 24 kHz，需重采样 |
| 30 s 计时 | **我们**（本地） | 播放完起算，与它无关 |
| 小车运动 / 云台控制 | **我们**（V2.0） | 与 AI 通道完全隔离 |
| 视频 | **我们**（WS 81） | 与 AI 通道完全隔离 |

**边界必须讲清**：小智云只负责"语音对话"，**不控制小车、不传视频、不做鉴权代理**。小车控制仍走自有 V2.0，AI 若要控车，由 App/网关把语义翻成 V2.0 CMD。

## 2. 字段与消息表

### 2.1 握手请求头（WebSocket 升级时携带）

| 名称 | 方向 | 类型 | 含义 | 取值 |
|---|---|---|---|---|
| `Authorization` | 设备→服务端 | Header 字符串 | 访问凭证 | `Bearer <token>`；**token 获取方式未核实** |
| `Protocol-Version` | 设备→服务端 | Header 字符串 | 协议版本 | 与 hello 的 `version` 一致（当前文档描述为 1/2/3） |
| `Device-Id` | 设备→服务端 | Header 字符串 | 设备物理标识 | **MAC 地址** |
| `Client-Id` | 设备→服务端 | Header 字符串 | 客户端软件标识 | 软件生成的 UUID，清 NVS / 重刷固件后重置 |

### 2.2 设备 → 服务端（JSON 文本帧）

| type | 字段 | 类型 | 含义 | 取值 |
|---|---|---|---|---|
| `hello` | `version` | int | 协议版本 | 1（默认） |
| | `features.mcp` | bool | 是否支持 MCP | 可选 |
| | `features.aec` | bool | 是否声明服务端 AEC | 可选（编译开关触发） |
| | `features.glyph_push` | bool | 是否支持动态字形推送 | 可选 |
| | `text_font` | object | 字形字体声明 | `bundle` / `charset` / `size` / `bpp`，可选 |
| | `transport` | string | 传输类型 | `"websocket"` |
| | `audio_params.format` | string | 编码格式 | `"opus"` |
| | `audio_params.sample_rate` | int | 采样率 | `16000` |
| | `audio_params.channels` | int | 声道 | `1` |
| | `audio_params.frame_duration` | int | 帧长（ms） | `60`（对应 `OPUS_FRAME_DURATION_MS`） |
| `listen` | `session_id` | string | 会话 ID | 服务端 hello 下发 |
| | `state` | string | 收听状态 | `"start"` / `"stop"` / `"detect"` |
| | `mode` | string | 收听模式 | `"auto"` / `"manual"` / `"realtime"` |
| | `text` | string | 唤醒词文本 | `state="detect"` 时可带 |
| `abort` | `session_id` | string | 会话 ID | — |
| | `reason` | string | 中断原因 | `"wake_word_detected"` 或实现自定义 |
| `mcp` | `session_id` | string | 会话 ID | — |
| | `payload` | object | JSON-RPC 2.0 | 工具发现/调用 |

### 2.3 服务端 → 设备（JSON 文本帧）

| type | 字段 | 类型 | 含义 | 取值 |
|---|---|---|---|---|
| `hello` | `transport` | string | 必须匹配 | `"websocket"` |
| | `session_id` | string | 会话 ID | 设备保存 |
| | `audio_params` | object | 服务端期望的音频参数 | `format` / `sample_rate`（示例为 **24000**）/ `channels` / `frame_duration` |
| `stt` | `text` | string | 用户语音的识别结果 | 上屏用 |
| `llm` | `emotion` | string | 情绪 | 如 `"happy"` |
| | `text` | string | 表情/展示文本 | 如 `"😀"` |
| `tts` | `state` | string | TTS 状态 | `"start"` / `"stop"` / `"sentence_start"` |
| | `text` | string | 当前句文本 | `sentence_start` 时带（字幕） |
| `mcp` | `payload` | object | JSON-RPC 2.0 | 服务端下发工具调用 |
| `system` | `command` | string | 系统命令 | `"reboot"` |
| `alert` | `status` | string | 告警标题 | 如 `"Warning"` |
| | `message` | string | 告警详情 | 如 `"Battery low"` |
| | `emotion` | string | 情绪 | 如 `"sad"` |
| `custom` | `payload` | object | 自定义消息 | 需编译开关开启 |

> **注意**：`llm` 消息在协议文档中承载的是**情绪与展示文本**，不是完整回复文本；完整字幕来自 `tts` 的 `sentence_start`。这一点与我们 01 文档"文字与 TTS 同源"的设计天然吻合。

### 2.4 二进制帧

| 版本 | 结构 | 说明 |
|---|---|---|
| **v1（默认）** | 裸 Opus 帧，无额外头 | WS 本身已区分文本/二进制 |
| v2 | `version:u16, type:u16, reserved:u32, timestamp:u32, payload_size:u32, payload[]` | `timestamp` 用于**服务端 AEC** |
| v3 | `type:u8, reserved:u8, payload_size:u16, payload[]` | 轻量头 |

> **我们的选择**：一期用 **v1**（裸 Opus），最简单；若要用服务端 AEC 再升 v2。

### 2.5 未核实字段

| 项 | 状态 |
|---|---|
| 应用层心跳消息（是否有 `ping`/`pong` 类型） | **未核实** |
| `session_id` 的长度/格式约束 | **未核实** |
| 服务端在 `listen.stop` 后是否必须等 `tts.stop` 才可再 `listen.start` | **未核实**（推测可以，但未验证） |
| 错误码枚举（是否只有 alert / 断连两种） | **未核实** |

## 3. 会话时序（含超时与失败处理）

| 步 | 动作 | 方向 | 超时 | 失败处理 |
|---|---|---|---|---|
| 1 | 设备连 WiFi（NVS 凭据） | — | 30 s | 重试 3 次 → SoftAP 配网 |
| 2 | SNTP 对时 | — | 10 s | 失败则用证书 pin |
| 3 | 本地 WakeNet 检测到唤醒词 | 设备内部 | — | 未命中不建连（**省电、省流量**） |
| 4 | 建立 WSS（带 4 个 Header） | 设备→云 | 10 s【推算，握手层】 | 退避重连，回 Idle |
| 5 | 发 `hello`（声明 Opus/16k/1ch/60ms） | 设备→云 | — | — |
| 6 | 等 `hello`（必须 `transport=websocket`） | 云→设备 | **10 s（已核实）** | 判连接失败，报网络错误，回 Idle |
| 7 | 保存 `session_id` | 设备内部 | — | — |
| 8 | 发 `listen state=start mode=auto` | 设备→云 | — | — |
| 9 | 持续上行 Opus 60 ms 帧 | 设备→云 | — | 发送失败 → 关闭通道 |
| 10 | 收 `stt`（识别文本） | 云→设备 | 无硬超时 | 可上屏 |
| 11 | 收 `tts state=start` | 云→设备 | 无硬超时 | 停上行（进入 speaking） |
| 12 | 收二进制 Opus 帧并播放 | 云→设备 | — | 丢帧不重传 |
| 13 | 收 `tts state=sentence_start`（带文本） | 云→设备 | — | 字幕上屏 |
| 14 | 收 `tts state=stop` | 云→设备 | 无硬超时 | **启动本地 30 s 计时** |
| 15 | 计时到 0 → 关闭通道回 Idle | 设备内部 | 30 s（本地） | — |
| 16 | 异常断开（任一侧） | — | — | 回 Idle，清 session，按策略重连 |

**协议自带的半双工约束**（已核实）：设备处于 `listening` 状态时，收到的下行音频帧会被丢弃——这正好避免"边听边说"的回声冲突。

## 4. 音频格式对照表

| 项 | 我们 01 文档的约定 | 小智的要求 | 差异与处理 |
|---|---|---|---|
| 编码 | **PCM16**（局域网） | **Opus**（hello 中 `format:"opus"`） | **必须转码**；上行不能发裸 PCM（服务端是否接受 PCM **未核实**，按不支持设计） |
| 采样率（上行） | 16 kHz | 16 kHz | **一致** |
| 采样率（下行） | 16 kHz | 服务端 hello 示例 **24 kHz** | 解码后若为 24 kHz → **降采样到 16 kHz** 再喂 I2S |
| 声道 | 1 | 1 | 一致 |
| 位宽 | 16 bit | Opus 无"位宽"，解码输出 16 bit | 一致 |
| 帧长 | **20 ms = 640 B（PCM）** | **60 ms**（`OPUS_FRAME_DURATION_MS`） | **冲突**：Opus 路径必须按 60 ms 组包 |
| 60 ms 的 PCM 当量 | — | 16000 × 0.06 × 2 = **1920 B** | 编码前缓冲 1920 B |
| 60 ms 的 Opus 体积 | — | 24–32 kbps 时约 **180–240 B**【推算】 | 远小于 PCM，带宽友好 |
| 帧边界 | 由我们自定 | 一个二进制帧 = 一个 Opus 包 | 不要在一帧里塞多个 Opus 包 |
| 时间戳 | 无 | v2 协议才带（服务端 AEC 用） | 一期 v1 不需要 |

**结论**：
1. 局域网自有 AI 通道可以继续用"PCM 20 ms / 640 B"；
2. **接小智必须另走一条 Opus 60 ms 的路径**，两者不能共用同一个缓冲参数；
3. 建议在 01 文档的规格表里增加一列"小智模式：Opus / 16 kHz / 60 ms / 180–240 B"。

## 5. Arduino 侧实现要点

### 5.1 WSS 客户端选型

| 候选 | 状态 | 说明 |
|---|---|---|
| `links2004/WebSockets` | 可用 | 支持文本/二进制、自定义 Header、`WiFiClientSecure`；与 03 文档的 relay 方案可共用 |
| `arduinoWebSockets` + `WiFiClientSecure` | 同上 | TLS 握手内存约 **40–60 KB heap/连接**【推算】 |

**必备能力**：设置 4 个自定义 Header、区分 text/binary、设置接收缓冲足够容纳 JSON（建议 ≥ 4 KB）。

### 5.2 Opus 编码 / 解码

| 项 | 事实/估算 | 结论 |
|---|---|---|
| 预编译库是否自带 libopus | **已核实：不带**（`framework-arduinoespressif32-esp32s3-libs` 中无 opus 符号） | 需自行引入固定点 libopus |
| 编码 CPU | 复杂度 c0 约 **26% 单核**、c2 34%、c5 49%（沿用前文数据） | **只用 c0** |
| 解码 CPU | 通常为编码的 1/3–1/2【推算】，约 **10–15% 单核** | 可接受 |
| 内存 | 编码器约 30–60 KB、解码器约 20–40 KB【推算】 | PSRAM 充足 |
| 与 JPEG 共存 | 编码 26% + 解码 15% + JPEG + TLS ≈ 单核 60–80%【推算】 | **可行但紧**：AI 说话期间视频降 QVGA 8–10 fps |
| 上行改 PCM 是否可行 | **未核实**；hello 已声明 opus | **不做假设**，按必须 Opus 设计 |

### 5.3 AEC 与半双工

| 方案 | 可行性 | 说明 |
|---|---|---|
| **半双工（推荐一期）** | **协议天然支持** | `listening` 时丢弃下行音频；`speaking` 时停止上行。回声问题从根上消失 |
| 服务端 AEC | 协议支持 | hello 声明 `features.aec=true` + 二进制 **v2** 带 timestamp；具体算法与效果 **未核实** |
| 设备侧 AEC | 需自行集成 | Arduino 的 `ESP_SR` 库只暴露唤醒/命令词接口，**未暴露 AFE 的 AEC**；要用需按 IDF 组件方式接入，工作量较大 |

**取舍**：一期用**半双工**，不做 AEC；二期若要做"边说边听"（barge-in）再考虑服务端 AEC。

### 5.4 唤醒词（本地）

**已核实（本地预编译库 `dio_opi/include/sdkconfig.h`）**：

| 配置 | 值 | 含义 |
|---|---|---|
| `CONFIG_MODEL_IN_FLASH` | **1** | 模型放 Flash，ESP_SR 库可编译 |
| `CONFIG_SR_WN_WN9_HIESP` | **1** | 只启用 **"Hi ESP"** 唤醒词模型 |
| `CONFIG_SR_MN_CN_NONE` | **1** | **中文命令词模型未启用** |
| `CONFIG_SR_MN_EN_MULTINET7_QUANT` | **1** | 仅英文命令词可用 |
| `CONFIG_AFE_INTERFACE_V1` | 1 | AFE 接口存在，但 Arduino 库未直接暴露 |

**结论**：
- Arduino 框架**可以用 `ESP_SR` 类**做本地唤醒（`SR_MODE_WAKEWORD`）；
- 但默认只有 **"Hi ESP"**，**没有"你好小智"**，也没有中文命令词；
- 要中文唤醒词需**替换 esp-sr 模型/预编译库**，这属于额外工作量（**未核实** Arduino 侧替换模型的具体路径）；
- 降级方案：一期直接用 "Hi ESP"，或自建"能量阈值 + 关键词确认"的粗糙方案（准确率低，不推荐）。

### 5.5 内存估算（与视频共存）

| 项 | 估算 | 备注 |
|---|---|---|
| WSS + TLS | 40–60 KB | 每连接一份 |
| Opus 编码器 | 30–60 KB | 固定点 |
| Opus 解码器 | 20–40 KB | — |
| 音频缓冲（上下行各 3 块 1920 B） | ≈ 12 KB | 按 60 ms 计 |
| JSON 解析 | 4–8 KB | 静态分配更稳 |
| **AI 通道合计** | **≈ 120–180 KB**【推算】 | 放内部 RAM 更稳，PSRAM 兜底 |
| 摄像头帧缓冲 | 2 × 数十 KB–数百 KB | 已在 PSRAM |
| **余量** | 8 MB PSRAM 下充足；内部 RAM 需关注 | 建议 AI 缓冲优先放内部 RAM，避免 PSRAM 带宽争用 |

## 6. 免费公共服务的真实边界

### 6.1 已核实的部分

| 项 | 内容 |
|---|---|
| 个人使用 | **注册账号后可免费使用 Qwen 实时模型**（官方 FAQ 口径） |
| 设备绑定 | 设备需在 `xiaozhi.me` 控制台**添加设备**（6 位验证码） |
| 固件开源 | 设备端固件开源（MIT，需以仓库 LICENSE 为准） |
| 服务端 | 官方服务端未开源；社区有多个开源实现（如 `xinnan-tech/xiaozhi-esp32-server`） |

### 6.2 未核实（不要当成承诺）

| 项 | 状态 | 影响 |
|---|---|---|
| 并发上限（同一账号/同一设备） | **未核实** | 多设备或多人同时用可能被拒 |
| 单次会话/每日时长限制 | **未核实** | 长对话可能被截断 |
| 设备数量上限 | **未核实** | 批量部署不可行 |
| 商用授权 | **未核实** | 对外销售前必须查清 |
| 数据是否经第三方（模型厂商） | **未核实** | 隐私合规风险 |
| 服务可用性/SLA | **未核实**（公共测试性质） | 可能随时变更或关闭 |
| 免费额度是否长期 | **未核实** | 不可作为产品依赖 |

### 6.3 判定线：什么情况下必须自建服务端

满足以下**任意一条**，公共云就不适用：

1. **并发 > 1–2**（多车/多人同时使用），或需要多设备常在线；
2. **商用或对外交付**——需要明确的授权与 SLA；
3. **要求数据不出域**（私有知识库、家庭隐私录音）；
4. **需要自定义唤醒词/音色/人设**且公共控制台不提供；
5. **需要稳定低延迟**（公共服在高峰期排队，**未核实**但不可假设）；
6. **需要与自有 V2.0/MCP 深度耦合**且公共服不开放对应能力。

**降级方案**：自建 `xiaozhi-esp32-server`（社区 MIT 实现），把 `OTA URL` 与 `WebSocket URL` 改成自己的地址即可——**设备侧协议完全不变**，这正是"只实现协议"的价值。

## 7. PoC 步骤与验收点

| # | 步骤 | 成功判据 | 失败排查 |
|---|---|---|---|
| 1 | 设备连上 WiFi，能访问外网 | `ping` 通 / 能解析域名 | 2.4 GHz？路由器是否只开 5 GHz |
| 2 | 首次启动触发 OTA，拿到 6 位验证码 | 串口/屏幕显示 6 位码 | OTA 地址是否被防火墙拦 |
| 3 | 在 `xiaozhi.me` 添加设备 | 控制台显示设备在线 | 验证码过期需重唤醒 |
| 4 | 建立 WSS 并完成 hello 往返 | 收到 `type=hello, transport=websocket` + `session_id` | 检查 4 个 Header；token 是否有效 |
| 5 | 说一句话 | 收到 `type=stt` 且文本合理 | 上行是否按 60 ms Opus |
| 6 | 收到回复 | 先 `tts start`，再连续二进制帧，再 `tts stop` | 下行播放是否有声（注意 24 kHz 重采样） |
| 7 | 播放结束 | 本地 30 s 计时启动，到点回 Idle | 计时是否被 `sentence_start` 误触发 |
| 8 | 断网重连 | 拔网 10 s 后恢复，能重新唤醒并对话 | 退避与状态清理 |
| 9 | 与视频共存 | AI 对话期间视频不卡死、不崩 | 降档策略是否生效 |

**最小闭环验收线**：第 4 + 5 + 6 + 7 步全部通过，即"连上→说一句→收到回复音频→播完起计时"。

## 8. 与 01 / 03 文档的合并建议

| 冲突/重叠 | 处理建议 |
|---|---|
| **01 的 PCM 20 ms / 640 B** vs 小智 **Opus 60 ms** | **不推翻 01**。在 01 的规格表加一列"小智模式"：Opus / 16 kHz / 60 ms / 180–240 B；两条路径共用同一个 `AudioService`，只换编码器与帧长 |
| **01 的文字 side-channel** vs 小智的 `tts.sentence_start` | **直接复用**：小智的 `sentence_start` 天然就是"文字与语音同源"，不需要再自造文本消息；把 `text` 映射到 01 的 `kind=0x02` 即可 |
| **01 的 AEC** | 小智场景一期改用**半双工**（协议本身支持），AEC 延后 |
| **03 的公网 relay** vs 小智云 | **并存，不替代**。小智云只管语音对话；小车的控制与视频仍走 03 的 relay。两者都是"设备出站 → 公网 → App"，可共用同一个 443 出口与证书体系 |
| **03 的设备鉴权** | 两套凭证分开：小智用它的 token，自有 relay 用我们的 HMAC。**不要混用** |
| **MCP 控车** | 可用：AI 通过 MCP `tools/call` 下发意图 → App/网关翻成 V2.0 CMD → 走 ctrl 通道。**不直接改 V2.0** |

## 9. 限制（技术 / 硬件 / 网络）

### 9.1 技术限制

| 限制 | 数值/状态 | 影响 | 缓解 |
|---|---|---|---|
| 上行必须 Opus | hello 声明 `format:"opus"` | 需要引入 libopus | 固定点、只用 c0 |
| 帧长 60 ms | 已核实 | 与 01 的 20 ms 冲突 | 双路径，不混用缓冲 |
| 下行可能 24 kHz | 服务端 hello 示例 | 需重采样 | 解码后降采样到 16 kHz |
| hello 超时 10 s | 已核实 | 弱网易失败 | 退避重连 |
| 免费边界未知 | 未核实 | 不可作为产品依赖 | 提前准备自建降级 |
| Arduino 无预编译 libopus | 已核实 | 需自行集成 | 用固定点版本，注意内存 |
| Arduino ESP_SR 只有 "Hi ESP" | 已核实 | 不能用"你好小智" | 替换模型或先用 "Hi ESP" |

### 9.2 硬件限制

| 限制 | 数值 | 影响 |
|---|---|---|
| Flash | 16 MB（`dio_opi`） | AI 模型 + 双 OTA 分区后剩余有限，注意唤醒词模型体积 |
| PSRAM | 8 MB OPI（GPIO33–37 占用） | 摄像头帧 + 音频缓冲共享 |
| 内部 RAM | 约 512 KB | TLS + Opus + 队列要精打细算 |
| 麦克风/喇叭同板 | 结构回声强 | 依赖半双工规避 |
| 射频 | 2.4 GHz 单射频 + BLE 共存 | AI 音频 + 视频 + BLE 三者要降档 |
| 功耗 | WiFi 常开 + Opus + JPEG | 峰值电流与发热需评估 |

### 9.3 网络限制

| 限制 | 数值 | 影响 |
|---|---|---|
| 上行带宽（Opus 24–32 kbps） | ≈ 11–14 MB/小时 | 蜂窝下可接受 |
| 上行带宽（若改 PCM） | 256 kbps ≈ 115 MB/小时 | 不建议 |
| 公网 RTT | 同城 10–30 ms / 跨省 40–80 ms【推算】 | 影响首字延迟 |
| 公共服可用性 | **未核实** | 可能排队/变更/关闭 |
| 防火墙/代理 | 需放行 443 WSS 与 OTA HTTPS | 校园网/企业网可能拦截 |
| 数据出境/第三方 | **未核实** | 隐私合规风险 |

## 10. 专业名词表

| 术语 | 人话解释 |
|---|---|
| **OTA** | 设备启动时向服务器查询"我是谁/要不要升级"，小智用它下发激活要求 |
| **WSS** | 加密的 WebSocket，长连接双向通信 |
| **hello 握手** | 连上后双方各发一条"我是谁、我支持什么格式"的自我介绍 |
| **session_id** | 一次对话的编号，消息都带着它 |
| **Opus** | 低码率语音压缩编码，小智上下行都用它 |
| **frame_duration** | 一个音频包覆盖多少毫秒，小智是 60 ms |
| **VAD** | 判断有没有人在说话 |
| **端点检测** | 判断这句话说完了没有 |
| **AEC** | 回声消除，避免喇叭的声音被麦克风收回去 |
| **半双工** | 要么听、要么说，不同时进行（本方案靠它躲开回声） |
| **WakeNet** | 乐鑫的本地唤醒词模型 |
| **MultiNet** | 乐鑫的本地命令词识别模型 |
| **MCP** | 一种让 AI 调用设备能力的标准协议（JSON-RPC 2.0） |
| **JSON-RPC** | 用 JSON 表示"调用哪个方法、参数是什么、返回什么"的规范 |
| **STT / ASR** | 语音转文字（两种叫法） |
| **TTS** | 文字转语音 |
| **LLM** | 大语言模型 |
| **重采样（Resample）** | 把 24 kHz 音频转成 16 kHz，让喇叭正常播放 |
| **token** | 访问凭证，放在 `Authorization` 头里 |
| **Client-Id** | 客户端唯一标识，重刷固件会变 |

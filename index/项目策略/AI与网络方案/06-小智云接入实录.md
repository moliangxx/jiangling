## 2. 设备激活：6 位码怎么来、怎么用

### 2.1 触发时机

设备**首次联网**后自动进入「激活设备」状态：先请求 OTA 地址检查版本，若响应带 `activation` 字段，就显示并朗读 6 位码；不带 `activation` 则视为无需激活，直接启动。

设备侧可触发/重听的方式：
- 官方固件：唤醒「你好小智」，会播报「请到控制台添加设备，验证码 xxxxxx」，**可以重复唤醒重听**；
- 不带离线唤醒的板子（如 C3 系列）：用按键唤醒；
- 也可以看串口日志或屏幕。

> 出处：[首次启动：配网、激活与绑定](https://xiaozhi.dev/docs/usage/activation)、[xiaozhi.me 添加设备文档](https://xiaozhi.me/xz-docs/docs/tutorial-basics/configure-wifi-and-add-devices/)

### 2.2 OTA 请求（设备 → 服务器）

| 项 | 值 | 依据 |
|---|---|---|
| 方法 | `POST`（请求体为空时才用 `GET`；官方固件始终非空，所以是 POST） | 【源码】`ota.cc` |
| 地址 | `https://api.tenclass.net/xiaozhi/ota/`（Kconfig 默认 `CONFIG_OTA_URL`；配网页「高级」里可改） | 【源码】`Kconfig.projbuild` |
| `Content-Type` | `application/json` | 【源码】`Ota::SetupHttp()` |
| `Activation-Version` | 有可读 eFuse 序列号时 `2`，否则 `1` | 【源码】同上 |
| `Device-Id` | 设备 MAC，小写冒号分隔，如 `aa:bb:cc:dd:ee:ff` | 【源码】`SystemInfo::GetMacAddress()` |
| `Client-Id` | 设备 UUID v4，存 NVS；擦 NVS / 整片重刷会变 | 【源码】`Board::GetUuid()` |
| `Serial-Number` | 仅当 eFuse USER_DATA 是可打印文本时带 | 【源码】`ota.cc` 构造函数 |
| `User-Agent` | `<BOARD_NAME>/<固件版本>` | 【源码】`SystemInfo::GetUserAgent()` |
| `Accept-Language` | 语言代码，如 `zh-CN` | 【源码】`Ota::SetupHttp()` |

请求体字段（`Board::GetSystemInfoJson()` 生成，实际就是这些）：

```json
{
  "version": 2,
  "language": "zh-CN",
  "flash_size": 16777216,
  "minimum_free_heap_size": "123456",
  "mac_address": "aa:bb:cc:dd:ee:ff",
  "uuid": "xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx",
  "chip_model_name": "esp32s3",
  "chip_info": { "model": 1, "cores": 2, "revision": 0, "features": 0 },
  "application": {
    "name": "xiaozhi",
    "version": "2.5.2",
    "compile_time": "2026-01-01T00:00:00Z",
    "idf_version": "v6.0.1",
    "elf_sha256": "..."
  },
  "partition_table": [
    { "label": "app", "type": 1, "subtype": 0, "address": 65536, "size": 4194304 }
  ],
  "ota": { "label": "ota_0" },
  "display": { "monochrome": false, "width": 320, "height": 240 },
  "board": { "...": "开发板自有字段" }
}
```

> 说明：`partition_table` 是完整分区表数组；`display` 在无屏设备上可能省略；`board` 由各开发板实现追加。**自研固件不必逐字段完全一致，但 `mac_address` / `uuid` / `application.version` / `chip_model_name` 必须稳定**，否则服务端会把同一台设备当成新设备。

### 2.3 OTA 响应（服务器 → 设备）

```json
{
  "firmware": { "version": "2.6.0", "url": "https://...", "force": 1 },
  "activation": {
    "message": "请登录控制台添加设备",
    "code": "123456",
    "challenge": "随机挑战串",
    "timeout_ms": 30000
  },
  "websocket": { "url": "wss://...", "token": "...", "version": 1 },
  "mqtt": { "...": "..." },
  "server_time": { "timestamp": 1760000000000, "timezone_offset": 480 }
}
```

| 字段 | 作用 | 备注 |
|---|---|---|
| `firmware` | 有新版本就先升级；`force:1` 强制 | 版本按点分十进制比较 |
| `activation.code` | **6 位数字字符串**，设备逐位朗读 | 类型是 string，不是 int |
| `activation.message` | 屏幕/语音提示文案 | — |
| `activation.challenge` | 激活应答的挑战串 | Activation-Version=2 时用 eFuse HMAC 密钥签名 |
| `activation.timeout_ms` | 服务端给的等待超时 | **具体默认值未公开【待确认】**；以每次响应为准 |
| `websocket` | 对话地址、token、二进制协议版本 | 整对象写进设备 NVS |
| `mqtt` | MQTT+UDP 方案配置 | 与 websocket 二选一 |
| `server_time` | 服务器时间，设备据此对时 | **TLS 证书校验依赖正确系统时间**，很关键 |

> 上例中的 `timeout_ms: 30000`、`code: "123456"` 等数值**只是示意**，实际以服务端每次下发为准。
> 出处：【源码】`main/ota.cc` 的 `CheckVersion()` 逐字段解析；【官方文档】首次启动页的响应字段表。

### 2.4 「已绑定」与「未绑定」到底怎么区分

设备在等待你操作期间，会反复向 `<OTA地址>/activate` 提交应答：

| 服务端返回 | 含义 | 设备行为 |
|---|---|---|
| `200` | **已绑定成功** | 停止轮询，加载 `websocket`/`mqtt` 配置，播成功音，进入待机 |
| `202` | **还没绑定**（控制台没输码 / 输错 / 还没提交） | 等 3 秒再试 |
| 其他状态 | 异常 | 等 10 秒再试 |
| 一轮 10 次仍未成功 | 本轮失败 | 回到「检查版本」重新来一轮，屏幕上会出现**新的激活码** |

所以：
- **未绑定** = 服务端一直回 202，设备停在激活码界面；
- **已绑定** = 服务端回 200，设备自动进入可对话状态；
- 你手上的码如果过期/换轮，以**屏幕最新显示的码**为准。

> 出处：[首次启动：配网、激活与绑定](https://xiaozhi.dev/docs/usage/activation)（原文明确写了 200/202/10 次/3 秒/10 秒）

### 2.5 设备已被别的账号绑定怎么办

| 场景 | 处理 |
|---|---|
| 自己以前绑过，现在换账号 | 在 `xiaozhi.me` 原账号「设备管理」里删除/解绑，再用新账号加 |
| 买到的二手板/模组已被陌生人绑定 | 官方渠道：发邮件到 `xiaozhi.ai@tenclass.com`，标题 `【解绑设备，设备ID XXX，MAC地址 XXX】` |
| 只是重刷固件 | 通常**不会自动解绑**：`Device-Id` 仍是 MAC，服务端认设备而不是固件；重刷后大概率仍绑在原账号（以控制台实际显示为准） |

> 出处：[掌控板小智使用教程·解绑](https://mpython-esp32s3-doc.readthedocs.io/zh-cn/latest/4_xiaozhi/3_xiaozhi.html)

**自研固件最少要做的 3 件事**：
1. OTA 响应里解析 `activation.code` + `timeout_ms`；
2. 屏幕或串口把 `code` 显示出来（语音朗读可选）；
3. 拿到码后持续 POST `<OTA地址>/activate`，**只认 200**，202 继续等。

## 3. WSS 连接与鉴权

### 3.1 地址从哪来（很重要）

**不要写死地址。** 官方固件在 `OpenAudioChannel()` 时从 NVS 读 `websocket.url` / `websocket.token` / `websocket.version`，这些值全部由 OTA 响应写入。

- 常见默认地址：`wss://api.tenclass.net/xiaozhi/v1/`；
- 端口：443（TLS）；
- 设备是**出站客户端**，不需要公网 IP，也不需要端口映射；只要网络放行出站 443 即可；
- 如果 OTA 响应既没有 `websocket` 也没有 `mqtt`，官方文档说默认走 **MQTT**（不是 WebSocket）——自研固件必须显式读 `websocket` 段。

> 出处：【源码】`main/protocols/websocket_protocol.cc`、`main/ota.cc`；【官方文档】首次启动页。

### 3.2 四个请求头

| Header | 值 | 作用 | 来源 |
|---|---|---|---|
| `Authorization` | `Bearer <token>`（若 token 本身不含空格会自动补 `Bearer `） | 访问凭证 | OTA `websocket.token`；**token 为空时官方固件根本不发这个头** |
| `Protocol-Version` | `1` / `2` / `3` | 声明**二进制帧版本**（不是 JSON 协议版本） | OTA `websocket.version`，默认 1 |
| `Device-Id` | MAC 地址 | 设备身份；绑定关系就认它 | 本机 MAC |
| `Client-Id` | UUID v4 | 客户端实例标识；换 NVS/重刷会变 | 本机 NVS |

补充：`Authorization` 的 token 不是用户在控制台手抄的，而是 **OTA 下发**。网上教程里出现的 `test-token` 只是示例，别照抄。

### 3.3 hello 握手（10 秒超时）

设备连上后立即发（源码实际行为）：

```json
{
  "type": "hello",
  "version": 1,
  "features": { "mcp": true },
  "transport": "websocket",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

- `features.mcp`：当前代码**无条件写 true**；`features.aec` 只在编译开启服务端 AEC 时出现；
- `text_font` / `glyph_push`：可选的动态字形扩展，不做就不发；
- `version` 与 `Protocol-Version` 头保持一致。

服务器必须回：

```json
{
  "type": "hello",
  "transport": "websocket",
  "session_id": "xxx",
  "audio_params": { "format": "opus", "sample_rate": 24000, "channels": 1, "frame_duration": 60 }
}
```

设备校验点：
1. `type == "hello"`；
2. `transport == "websocket"`，否则报错；
3. 保存 `session_id`；
4. 读取 `audio_params.sample_rate` / `frame_duration` 作为**下行播放参数**；
5. **10 秒内没收到就判连接失败**（源码 `pdMS_TO_TICKS(10000)`）。

> 出处：【源码】`WebsocketProtocol::GetHelloMessage()` / `ParseServerHello()` / `OpenAudioChannel()`；【社区文档】[WebSocket 通信协议](https://xiaozhi.dev/docs/development/websocket/)

### 3.4 二进制帧版本

| 版本 | 结构 | 适用 |
|---|---|---|
| **v1（默认）** | 裸 Opus 包，无头 | 最简单，WebSocket 本身已区分 text/binary |
| v2 | `u16 version, u16 type, u32 reserved, u32 timestamp, u32 payload_size, payload[]`（大端） | 需要服务端 AEC 时，`timestamp` 给回声消除用 |
| v3 | `u8 type, u8 reserved, u16 payload_size, payload[]`（大端） | 轻量头 |

一期建议 v1。

### 3.5 心跳

| 层 | 行为 |
|---|---|
| WebSocket 协议层 | 服务端发 **Ping**，设备回 **Pong**（源码 `OnPing` → `SendPong`） |
| 应用层 | 协议文档**没有**定义 `ping`/`pong` 类型的 JSON 消息【已核实：协议文档未描述】 |
| 断线检测 | 依赖 WebSocket 断开回调；源码记录 `last_incoming_time_`，但公开文档未说明其超时用途【待确认】 |

## 4. 消息类型：谁发、什么时候发

### 4.1 一览表

| type | 方向 | 时机 | 关键字段 |
|---|---|---|---|
| `hello` | 设备→云 | 连上立即 | `version` / `features` / `transport` / `audio_params` |
| `hello` | 云→设备 | 收到设备 hello 后 | `transport`(必须 websocket) / `session_id` / `audio_params` |
| `listen` | 设备→云 | 开始/停止录音、唤醒检测 | `state`: `start` / `stop` / `detect`；`mode`: `auto` / `manual` / `realtime`；`detect` 时可带 `text`（唤醒词显示文字） |
| 二进制音频 | 设备→云 | `listen start` 后持续推 | 一帧 = 一个 Opus 包（60 ms） |
| `stt` | 云→设备 | 服务端识别出用户语音 | `text`（上屏用） |
| `llm` | 云→设备 | 大模型产出时 | `emotion`（如 happy）、`text`（表情/展示文本，**不是完整回复**） |
| `tts` `start` | 云→设备 | 准备下发 TTS 音频 | 设备进入 `speaking`，**停止上行** |
| 二进制音频 | 云→设备 | `tts start` 之后 | 一帧 = 一个 Opus 包 |
| `tts` `sentence_start` | 云→设备 | 每句开始 | `text`：当前句字幕 |
| `tts` `stop` | 云→设备 | 本次 TTS 结束 | 设备播完缓存后回 `Idle`（或 auto 模式再 `listen start`） |
| `abort` | 设备→云 | 播放中被唤醒词打断 | `reason: "wake_word_detected"` |
| `mcp` | 双向 | 设备能力发现/工具调用 | `payload` = JSON-RPC 2.0 |
| `system` | 云→设备 | 远程控制 | `command: "reboot"` |
| `custom` | 云→设备 | 编译开关开启时 | `payload` |

### 4.2 一次完整对话的时序

```
设备                         云
 |  连 WSS(4头)                |
 |-- hello ------------------>|
 |<- hello(session_id,24k) ---|   ← 10s 内必须到
 |-- listen start,auto ------>|
 |-- Opus 16k/60ms 帧 ------->|   ← 持续上行
 |<- stt "今天天气" -----------|
 |<- llm emotion/text --------|   ← 只用于表情/UI
 |<- tts start ---------------|   ← 设备停上行，进 speaking
 |<- Opus 帧 ... -------------|
 |<- tts sentence_start "..."-|   ← 字幕
 |<- tts stop ----------------|   ← 播完回 Idle（或继续 auto）
 |-- listen start (auto) ---->|   ← 官方 auto 模式会续听
```

### 4.3 「30 秒空闲关闭」到底从哪个事件算

这是最容易以讹传讹的一条。先把四件事分开：

| 层 | 事实 | 状态 |
|---|---|---|
| 协议 | WebSocket 协议文档里**没有任何 30 秒/空闲超时字段或事件**；`listen` 也没有超时参数 | 【已核实】协议无此定义 |
| 官方云 / 官方固件 | `tts stop` 后设备播完缓冲回到 `Idle`；auto 模式会再发 `listen start` 继续听。**官方没有「30 秒关通道」这个行为定义**，源码里也没有 30 秒常量 | 【源码】；官方云是否有隐藏超时【待确认】 |
| 社区服务端 | `close_connection_no_voice_time` 默认 **120 秒**，可配置；这是**自建服务端**的断连策略，与官方云无关 | 【社区服务端配置】 |
| 量产产品 | 成品说明书里的「30 秒无对话休眠」是**产品策略**，不是云协议 | 【产品手册】 |

**本项目口径（写死，不要改）：**
- **30 秒空闲关闭是项目自己定的策略**：官方云没有这个行为，协议也没有这个定义；
- 计时起点按项目约定取 **`tts.state == "stop"`**（即最后一次 AI 回复语音播放结束）；
- 不要把起点放在 `tts sentence_start`，否则长回复会在播放中途被计时；
- 社区服务端的 120 秒是「自建服务端多久没语音输入就断连」，与项目的 30 秒**不是同一层的东西**，不能拿来当官方云依据。

## 5. 音频参数

### 5.1 硬指标

| 项 | 上行（设备→云） | 下行（云→设备） |
|---|---|---|
| 编码 | **Opus**（hello 里 `format:"opus"`） | Opus |
| 采样率 | **16000 Hz** | 服务器 hello 示例 **24000 Hz**（以实际下发为准） |
| 声道 | **1（单声道）** | 1 |
| 帧长 | **60 ms**（`OPUS_FRAME_DURATION_MS`） | 通常同 60 ms，以 `audio_params.frame_duration` 为准 |
| 每帧采样数 | 16000 × 0.06 = **960 samples** | 24000 × 0.06 = 1440 samples |
| 等长 PCM | 960 × 2 = **1920 B** | 1440 × 2 = 2880 B |
| 位宽 | 编码前 PCM 16 bit | 解码后 PCM 16 bit |

### 5.2 Opus 与 PCM 怎么选

| 方案 | 可行性 | 说明 |
|---|---|---|
| **Opus（推荐/官方路径）** | 官方固件就是这么做的 | 带宽 24–32 kbps 量级（经验值，**非官方指标**）；需要 libopus |
| PCM 上行 | 【待确认】 | 乐鑫 `esp_iot_solution` 的小智组件宣称支持 `OPUS / G.711 / PCM`，但**官方云的 hello 固定声明 opus**；官方云是否接受 PCM 未验证，别假设 |
| G.711 | 【待确认】 | 同上，组件支持 ≠ 官方云接受 |

工程取舍（本项目 Arduino 侧）：
- Arduino 的 ESP32 core **不自带 libopus**，要自己引固定点版本；
- 编码用 `OPUS_APPLICATION_VOIP`、`complexity=0`（CPU 优先）、60 ms 帧；
- 解码后若 `sample_rate=24000`，必须**重采样到 16000** 再喂 I2S；
- 无 AEC 时走**半双工**：`listening` 时丢弃下行音频、`speaking` 时停上行，避免自己听见自己。

> 出处：【源码】`GetHelloMessage()` / `ParseServerHello()`；【社区文档】WebSocket 协议第 5 节；【乐鑫文档】[小智 AI 聊天机器人组件](https://docs.espressif.com/projects/esp-iot-solution/zh_CN/latest/ai/xiaozhi.html)

## 6. 唤醒词：中文到底能不能用

**先给结论**：唤醒词**完全是设备端的事**，由固件里的 **WakeNet 预训练模型**决定。云端不参与识别，**控制台也没有换唤醒词的入口**。换词不是填一个字符串，而是「换模型 + 改编译配置 + 重新编译烧录」。完全自定义的词需要训练模型，或用 MultiNet 命令词替代。

### 6.1 官方固件内置（WakeNet9，ESP32-S3 / P4）

| 唤醒词 | S3 / P4 模型名 | C3 / C6（WakeNet9s） |
|---|---|---|
| Hi,乐鑫 | `wn9_hilexin` | `wn9s_hilexin` |
| Hi,ESP | `wn9_hiesp` | `wn9s_hiesp` |
| **你好小智（默认）** | `wn9_nihaoxiaozhi_tts` | `wn9s_nihaoxiaozhi` |
| Hi,Jason | `wn9_hijason_tts2` | `wn9s_hijason_tts2` |
| 小爱同学 | `wn9_xiaoaitongxue` | — |
| 嗨小欧 | `wn9_hai1xiao3ou1_tts3` | — |
| 你好小瑞 | `wn9_ni3hao3xiao3rui4_tts3` | — |

### 6.2 怎么改唤醒词（不是填字符串）

| 方式 | 具体做法 | 代价 / 限制 |
|---|---|---|
| **换内置预训练词** | ESP-IDF 下 `idf.py menuconfig` → ESP Speech Recognition → Wake Word 选模型；对应宏 `CONFIG_SR_WN_WN9_*` / `CONFIG_SR_WN_WN9S_*`；改完必须重新编译并烧录 | 只能从乐鑫已提供的模型里选；S3 之外的芯片可选更少 |
| **完全自定义词（训练）** | 自己训练 WakeNet 模型；乐鑫提供自定义唤醒词定制服务（商用申请，门槛较高） | 周期长、需要语料与训练环境；不是改配置能完成的 |
| **MultiNet 命令词替代** | S3 / P4 / S31 **且带 PSRAM**；中文写**拼音**，空格分隔，如 `ni hao xiao zhi`；阈值 1–99（越小越灵敏，默认 20） | 不是真正的唤醒词模型；**误触发率和功耗更高**，需要现场调阈值 |
| **换 assets.bin** | 用 Assets 生成器替换 `assets` 分区里的模型/字体/表情等资源 | 资源必须与编译配置匹配，单换文件不一定生效 |
| **控制台改** | 无此入口 | **云端不参与，改不了** |

### 6.3 限制来自哪里（结论）

| 问题 | 结论 |
|---|---|
| 云端能改唤醒词吗 | **不能**。唤醒在设备本地完成，云只收到 `listen state=detect` 的文本；控制台没有这个设置项 |
| 换词是填字符串吗 | **不是**。= 换 WakeNet 模型 + 改 `CONFIG_SR_WN_*` 编译配置 + 重编烧录 |
| 官方固件中文能用吗 | **能**，默认就是「你好小智」；同芯片还内置 Hi 乐鑫、Hi ESP、Hi Jason、小爱同学、嗨小欧、你好小瑞 |
| 完全自定义词怎么做 | 训练 WakeNet 模型（乐鑫定制服务），或退一步用 MultiNet 命令词（代价是误触发与功耗） |
| **本项目当前固件能用中文吗** | **不能**。Arduino ESP-SR 预编译库只编进了 Hi ESP 英文模型（`CONFIG_SR_WN_WN9_HIESP`），没有中文模型 |
| 本项目要用中文怎么办 | 换 ESP-IDF 固件（走 6.2 的 menuconfig 换模型），或替换模型分区/assets 文件；具体替换路径与可行性【待确认】 |

> 出处：[自定义 Assets 指南](https://xiaozhi.dev/docs/development/assets-customization/)、[xiaozhi.me 唤醒词更改教程](https://xiaozhi.me/xz-docs/docs/tutorial-extras/wake-up-word-change-configuration/)、[esp-sr 组件页](https://components.espressif.com/components/espressif/esp-sr/versions/2.5.1/readme?language=en)

### 7.4 超出后是限流还是付费？

- **官方没有公开任何规则**，所以三种情况都要在客户端兜住：HTTP `429`、WSS 被服务端主动断开、服务端静默降级（不回 `tts`）。
- 自研固件的处理建议：
  1. 收到 429/异常断开 → 指数退避重连（10s 起，翻倍，上限 10 次）；
  2. 连续失败 → 屏幕/语音提示「服务暂不可用」，**不要无限重试刷屏**；
  3. 保留「一键切自建服务端」的配置项（OTA 地址 + WS 地址可改），这是唯一可控的兜底。

### 7.5 什么时候必须离开公共云

**判定线**：只要出现「多车/多人并发」「对外销售」「数据不出域」「要求稳定 SLA」「需要明确账单」任意一条，就不要依赖公共云，改自建服务端（设备协议不变，只改 OTA/WS 地址）。

## 8. 常见失败与排查

| 现象 | 最可能原因 | 怎么查 / 怎么解 |
|---|---|---|
| **6 位码不出现** | ① OTA 地址不可达或返回非 200；② 设备已保存 Wi-Fi 但连不上（60 秒后才回配网）；③ 固件与板型不匹配；④ 喇叭/功放没接，听不到播报 | 看串口日志有没有 `Failed to check version, status code`；确认能访问 `api.tenclass.net`；换 2.4 GHz Wi-Fi；重刷匹配变体；屏幕/串口也能看码 |
| 一直停在激活码界面 | 服务端一直回 **202**（你还没在控制台提交 / 码已换轮） | 用**屏幕最新**的码；确认加到了正确的智能体；再看设备是否在「检查版本」重来 |
| 控制台提示设备已被绑定 | 设备先前绑在别的账号 | 原账号删除设备；或邮件解绑（标题格式见 2.5） |
| **WSS 连不上** | ① 自己写死了 URL，和 OTA 下发的不一致；② 出站 443 被防火墙/代理拦；③ token/Protocol-Version 不对；④ 学校/企业网需二次认证 | 用 OTA 返回的 `websocket.url`；抓包看 TLS 是否到 443；确认 `Device-Id` 是 MAC；先烧官方固件验证账号与网络 |
| **证书错误 / TLS 失败** | 系统时间不对（证书有效期校验失败） | OTA 响应里的 `server_time` 会设时钟——先跑通 OTA，再做 WSS；无 RTC 的板子上电必须先对时 |
| 连上但 10 秒后断开 | 没收到服务器 hello，或 `transport` 不是 `websocket` | 检查是否把二进制帧当文本发；确认发完 hello 后没阻塞主循环（TLS 读要在独立任务里） |
| 有字幕没声音 | 下行 24 kHz 没重采样 / Opus 解码失败 / I2S 配置错 | 按服务器 hello 的 `sample_rate` 解码后重采样到 16 kHz；先播本地测试音验证 I2S |
| 自己把自己打断 | 无 AEC，喇叭回声被麦克风收进去 | 一期半双工：`speaking` 停上行、`listening` 丢下行；喇叭与麦克风物理拉开 |
| 频繁重连 | 弱网 + 10 秒 hello 超时 | 退避重连；不要在 `tts` 播放期间做 OTA 检查 |

> 出处：排查项来自【源码】错误分支 + 【官方文档】首次启动页「常见问题排查」表 + 【官方文档】FAQ。

## 9. 从零到能对话：操作清单

> 两条路线二选一：
> **路线 A（推荐先做）**：烧官方固件，验证「账号 + 网络 + 云」这条链路是通的；
> **路线 B**：在自己固件里实现协议（本文第 2~5 节就是规格）。
> 先把 A 跑通，再动 B，能少踩一半坑。

### 路线 A：官方固件验证（最快跑通）

| # | 做什么 | 在哪里做 | 期望看到什么 |
|---|---|---|---|
| 1 | 注册/登录账号 | 浏览器打开 `https://xiaozhi.me/console/`，手机号收短信码登录 | 进入控制台首页 |
| 2 | 建智能体 | 控制台左侧「+新建智能体」，选角色/音色/模型，保存 | 智能体列表出现新卡片 |
| 3 | 下载对应固件 | GitHub Releases 选 `v2.5.2_<你的板型>.zip`，板型在「支持的开发板」查 | 拿到 bin/合并固件 |
| 4 | 烧录 | 用 Flash 工具或 esptool，芯片选 ESP32-S3，地址 `0x0` | 串口出现启动日志、无反复重启 |
| 5 | 配网 | 手机连设备热点 `Xiaozhi-XXXX`（开放无密码），浏览器开 `192.168.4.1`，选 **2.4 GHz** Wi-Fi 输密码 | 页面提示「登录成功」，设备 3 秒后重启 |
| 6 | 等 OTA | 设备自动联网并向 OTA 请求 | 串口出现 `Current version` / `Session ID` 之类日志；屏幕/语音出现 6 位码 |
| 7 | 绑定 | 控制台 → 智能体卡片「添加设备」→ 输入 6 位码 | 设备播成功音，控制台「设备管理」出现该设备（在线） |
| 8 | 对话 | 对设备说「你好小智」，再说一句话 | 先出 `stt` 文本，再听到回复语音；串口可见 `tts start/stop` |
| 9 | 验证空闲行为 | 回复结束后什么都不说，掐表 | 记录设备/连接多久进入 Idle 或断开（用来验证第 4.3 节【待确认】项） |

### 路线 B：自研固件接入（本项目）

| # | 做什么 | 在哪里做 | 期望看到什么 |
|---|---|---|---|
| 1 | 先完成路线 A 的 1~2 步 | 控制台 | 有账号、有智能体 |
| 2 | 实现 OTA 客户端 | 固件：HTTPS POST + 第 2.2 节头/体 | 串口打印服务器返回 JSON，含 `activation.code` |
| 3 | 屏幕/语音/串口输出 6 位码 | 固件 UI + 串口日志 | 与路线 A 第 6 步同样的码 |
| 4 | 控制台输入码 | 控制台 | 设备侧 `/activate` 收到 200 |
| 5 | 解析 `websocket` 段并落 NVS | 固件 | 拿到 `url` / `token` / `version` |
| 6 | 建 WSS + 4 头 + 发 hello | 固件：TLS + WebSocket 客户端 | 10 秒内收到服务器 hello + `session_id` |
| 7 | 发 `listen start,auto` + 推 Opus 60 ms | 固件：I2S → Opus 编码 → 二进制帧 | 服务器回 `stt` 文本 |
| 8 | 收 `tts start` → 解码播放 → `tts stop` | 固件：Opus 解码 + 重采样 + I2S | 喇叭出声，字幕随 `sentence_start` 更新 |
| 9 | 播完启动本地 30 秒计时 | 固件 | 30 秒无新对话 → 主动 `listen stop` / 关通道，下次唤醒重连 |
| 10 | 回归验证 | 断网/重连/重复唤醒 | 不重复绑定、不重复推帧、不卡死屏幕 |

## 10. 易错点（照做时最容易翻车的地方）

1. **把 `wss://api.tenclass.net/xiaozhi/v1/` 写死在代码里**：官方云下发的 URL/token 才是准的，写死会在换服/换账号时失效。
2. **把 `Protocol-Version` 当成 JSON 协议版本**：它是二进制帧版本（1/2/3）。
3. **`Authorization` 硬塞 `test-token`**：token 为空时官方固件根本不发这个头；乱塞反而可能被拒。
4. **`Device-Id` 不是 MAC**：服务端按它认设备，填错会重复绑定/生成新设备。
5. **没有先对时**：TLS 证书校验会失败；OTA 的 `server_time` 就是给你对时用的。
6. **hello 之后阻塞主循环**：10 秒等不到 hello 就断；TLS/WS 读必须独立任务。
7. **上行发 PCM 碰运气**：官方路径是 Opus；PCM 是否被接受【待确认】。
8. **把 `tts sentence_start` 当计时起点**：30 秒是项目自定策略，应按 `tts.state="stop"` 起算。
9. **忽略下行 24 kHz**：不重采样会变调/爆音。
10. **以为重刷固件会解绑**：绑定认 MAC，换账号必须先解绑。

## 0. 名词与前提

| 名词 | 含义 |
| --- | --- |
| 语音通道 | 专门承载双向实时音频的独立 socket，**不属于 ctrl** |
| 语音会话 | 一次「开启 → 持续双向流 → 结束」的完整过程 |
| 上行 | 手机 → 车（App 麦克风采集的声音） |
| 下行 | 车 → 手机（车端麦克风采集的声音） |
| 抖动缓冲 | 接收端按到达时间平滑播放的 PCM 环形缓冲 |
| PLC | Packet Loss Concealment，丢包时用上一帧延续/淡化补洞 |
| DTX | Discontinuous Transmission，静音期不发包 |
| AEC | Acoustic Echo Cancellation，回声消除 |

**既定前提（来自现有固件，不是本文新定）**

| 项 | 现状 | 依据 |
| --- | --- | --- |
| 主控 | ESP32-S3，N16R8（16 MB Flash / 8 MB PSRAM），双核 240 MHz | `platformio.ini` |
| 音频硬件 | INMP441 + MAX98357A 一体模块，**单 I2S 控制器全双工**，采样率固定 16 kHz | `AudioBus.h` |
| 麦克风读取 | `Mic::read()` 非阻塞，单次最多 512 采样点（16 kHz 下 32 ms） | `Mic.h` |
| 喇叭写入 | `Speaker::play()` 非阻塞，DMA 满即返回 0；软件音量 0~100 | `Speaker.h` |
| ctrl 通道 | WiFi 近程 TCP 8080（唯一通道；蓝牙已于 2026-11-11 整体移除） | `Wifi.h` |
| 帧格式 | `AA | SEQ | TYPE | LEN | PAYLOAD | CRC8`，帧总长 `5 + LEN`，LEN ≤ 255 | `Protocol.h` |
| 协议版本 | `21` | `PROTOCOL_VERSION` |
| AI 通道 | 独立 WSS，走小智云；请求-应答式（说完等云端） | `AiLink.h` / `AiConfig.h` |

## 1. 定位与边界

### 1.1 解决什么问题

语音通话要解决的是**「人和人说话」被机器人两端拉长后的场景**：

- 手机用户在远处看着车，想直接对车周围的人说话；
- 车周围的人想直接回答手机用户；
- 两端都要**持续开着麦克风和喇叭**，像打电话一样随时开口，不需要「按一下说一句」。

它要的是**连续的、双向的、低延迟的音频管道**，而**不是**一条「请求-应答」的业务链路。

### 1.2 与 AI 通道的区别

| 维度 | 语音通话（本文） | AI 通道（小智云） |
| --- | --- | --- |
| 交互模型 | **双向持续流**，两端同时收发 | 请求-应答：说一句、等云端想、回一句 |
| 延迟要求 | 单向 < 150 ms 才算「像打电话」 | 秒级可接受（ASR + LLM + TTS） |
| 端点 | 手机 ↔ 车 | 车 ↔ 云端 |
| 语音处理 | **不做识别、不做合成**，只搬运 | 云端 ASR / LLM / TTS |
| 链路 | 局域网（WiFi） | 公网（WSS 443），需外网 |
| 谁发起 | App（用户按开关） | 设备（唤醒词） |
| 会话节奏 | 用户手动开关，持续到关 | 30 s 无问答自动关闭 |
| 与对方关系 | **互斥**：语音模式开启即关闭 AI（这是 AI **总开关**条件②的自然结果，见 §1.8.5） | 语音模式期间不可用 |

一句话：**AI 是「问一句答一句」，语音是「一直通着」**。二者共用同一套麦克风和喇叭，所以在设备侧必须互斥，不能同时占用音频出口。

### 1.3 与普通数据推送（DAT / LOG）的区别

| 维度 | 语音 | DAT / LOG |
| --- | --- | --- |
| 性质 | 实时流，**允许丢、不允许等** | 状态同步，**不允许丢、允许等** |
| 节奏 | 每 20 ms 一包（50 包/s） | 每 500 ms 一轮（2 帧/s） |
| 大小 | 每包 40~640 B | 每帧 5~29 B |
| 重发 | **不重发**，丢了用 PLC 补 | 补发环 / 下一轮重报 |
| 优先级 | 最高（仅次于急停类安全命令的延迟要求） | 最低 |

### 1.4 明确不做的事

| 不做 | 原因 |
| --- | --- |
| 公网远程通话 | 项目当前不做远程（见 `总览.md` §3.2 / §6） |
| BLE 承载语音 | 带宽差 1~2 个数量级，见 §2.2 |
| 视频与语音同通道 | 视频码率更高，同 socket 会把音频挤成 PPT |
| 云端中转语音 | 语音是「手机 ↔ 车」直连，不经任何服务器 |
| 语音识别 / 语音合成 | 那是 AI 通道的职责 |
| 多方通话 / 录音存档 | 超出范围 |

### 1.5 对讲（语音通信）的会话边界

**唯一开关源是 App。板子不自作主张开始，也绝不因「空闲」自行结束。**

| 项 | 规定 | 由谁触发 |
| --- | --- | --- |
| 开始 | App 打开开关 → App 立即向 `192.168.4.1:8888` 发首包（bit6=1）；板子**收到首包即会话开始** | App |
| App 侧起点 | App 打开开关即开始发送，不等握手、不等 ACK；发送失败则回滚 UI | App |
| 保持 | 从起点到结束，板子**持续占用麦克风与喇叭**（按半双工方向切换，§5.3.1），不释放给 AI / 录音 | 板子 |
| 空闲 | **不设任何内部空闲超时**。用户连续 10 分钟不说话也不结束、不降级、不退出 | — |
| 结束 | 只有三类事件：① App 关闭开关并发 bit5 结束帧；② 连接断开（2 s 无任何包 / 热点断 / WiFi 掉线）；③ 设备复位或音频致命故障 | App / 链路 / 设备 |
| 板子能主动结束的范围 | 仅限链路断开与致命故障；**板子不得以「空闲」「超时」为由结束会话** | 板子 |

**板子侧的时间参数（全部与「空闲」无关）**

| 参数 | 值 | 性质 | 计时方 |
| --- | --- | --- | --- |
| 等 App 首包 | 无超时 | 板子不主动开始；空等不结束会话 | — |
| 上行静默判死 | 2 s（App 每 500 ms 至少发一包静音心跳，§3.4） | 断链判定 | 板子 |
| 关闭收尾 | ≤ 500 ms | 收尾上限 | 板子 |
| 结束帧 | 1 包（bit5） | 协议约定 | App |

> 结论：**「多久没说话」不是结束条件；只有「开关关了」或「连不上了」才结束。**

### 1.6 AI 通信的会话边界（状态机）

> 前提：AI 走小智云 WSS，与语音通道物理独立。当前固件 `AI_ENABLE_WAKEWORD = 0`（唤醒词未启用），本节规则在唤醒词启用后生效。
>
> **本节只管「会话内部怎么走」，「能不能进会话」由 §1.8 的两级开关决定**：总开关为关时，本状态机整个停在 `AI_DISABLED`，`AI_IDLE` 都进不去。
>
> 会话成长：**一次唤醒 = 一个最长 30 s 的输入窗口；每播完一条回复，窗口重新计时 30 s。**

```
待唤醒（AI_IDLE）
  │ 唤醒词命中（板子本地判定）
  ▼
等待输入（AI_LISTEN）  ←── 播放完成，30 s 重新计时
  │ 30 s 内出现语音输入
  ▼
上行 / 等待回复（AI_THINK）
  │ 收到 tts.start
  ▼
播放回复（AI_SPEAK）
  │ 播放完成（tts.stop）
  └──▶ 回到「等待输入」，重新计时 30 s

等待输入满 30 s 无输入 ──▶ 关闭通道（AI_CLOSE）──▶ 待唤醒（AI_IDLE）
```

| 状态 | 板子做什么 | 计时器 | 计时方 | 出口 |
| --- | --- | --- | --- | --- |
| `AI_IDLE` 待唤醒 | 唤醒词检测开启；麦克风与喇叭不占用 | 无 | — | 唤醒词命中 → `AI_LISTEN` |
| `AI_LISTEN` 等待输入 | 开上行链路，等待用户说话；不播放 | **30 s，从进入本状态起算** | 板子 | 有输入 → `AI_THINK`；满 30 s → `AI_CLOSE` |
| `AI_THINK` 上行 / 等待回复 | 持续上行音频，等云端回复 | 不设计时器 | — | 收到 `tts.start` → `AI_SPEAK`；连接断 → `AI_CLOSE` |
| `AI_SPEAK` 播放回复 | 播放 TTS；此阶段暂停上行（半双工） | 不设计时器 | — | 播放完成（`tts.stop`）→ `AI_LISTEN` 并重置 30 s；被语音抢占 / 断链 → `AI_CLOSE` |
| `AI_CLOSE` 关闭通道 | 停上行、停 TTS、关 WSS、释放麦克风与喇叭 | ≤ 500 ms | 板子 | 回到 `AI_IDLE` |

**触发点与责任方**

| 触发点 | 由谁触发 | 动作 |
| --- | --- | --- |
| 唤醒词命中 | 板子（本地唤醒词引擎） | `AI_IDLE` → `AI_LISTEN`，30 s 开始计时 |
| 30 s 内无任何输入 | 板子（本地计时器） | `AI_LISTEN` → `AI_CLOSE` |
| 回复播放完成 | 板子（检测 `tts.stop` / 播放缓冲排空） | `AI_SPEAK` → `AI_LISTEN`，30 s 重新计时 |
| 语音开关开启（首包到达） | App 触发、板子执行 | 任意 AI 状态 → `AI_CLOSE`（见 §1.7） |
| 网络断开 | 链路 | 任意 AI 状态 → `AI_CLOSE` |

> **是否需重新唤醒：需要。** 语音结束或断开后，AI 只回到 `AI_IDLE`，**必须重新说唤醒词**才会再次进入 30 s 输入窗口；不恢复上一轮会话，也不自动开新窗口。

### 1.7 两条通道的互斥与优先级

**互斥是硬互斥：任一时刻，麦克风与喇叭只归一条通道。**

| 时点 | 板子必须做的事 | 时限 | 由谁触发 |
| --- | --- | --- | --- |
| App 打开语音开关（首包到达） | ① 终止 AI：停上行、停 TTS 并**丢弃剩余 TTS 缓冲**、关 WSS 会话、**关闭唤醒词检测**；② 进入 `ACTIVE` | **≤ 100 ms**，首包到达即执行 | App 触发 + 板子执行 |
| 语音 `ACTIVE` 期间 | 唤醒词检测**失效**：麦克风已被通话占用，且显式禁止唤醒，收到唤醒词一律忽略 | 全程 | 板子 |
| 语音 `ACTIVE` 期间收到 AI 上行 / 音频 / 字幕 | 丢弃；不建 AI 会话，不占用喇叭 | 全程 | 板子 |
| 语音关闭 / 断开 / 收尾完成 | 恢复唤醒词检测；AI 回 `AI_IDLE`（**需重新唤醒**） | 收尾 ≤ 500 ms 后 | 板子 |
| AI 正在播放回复时语音开启 | **立即中止 TTS**，不播完、不留尾音；AI 音频不得与手机语音叠加 | ≤ 100 ms | 板子 |

**优先级（与 §6.1 一致，按会话粒度重申）**

1. **手机语音（上行 / 下行音频）**：最高，随时可抢占喇叭与麦克风。
2. **AI 回复（TTS / 字幕）**：次之；**AI 回复不得阻断手机语音**，语音包一到即让路。
3. **DAT / LOG**：最低，不抢音频。

| 冲突场景 | 结果 |
| --- | --- |
| AI 正在说话，手机语音开启 | AI 立即静音并终止会话，手机语音独占 |
| 语音进行中，用户说唤醒词 | 忽略，不响应 |
| 语音进行中，云端仍在推 TTS | 丢弃，不入播放队列 |
| 语音断开瞬间仍有 AI 残留音频 | 先清空 AI 音频缓冲，再恢复唤醒词与 AI 通道 |

> 一句话：**语音开关一开，AI 立刻让位并静默；语音一关或一断，AI 回到待唤醒，必须重新唤醒才能再用。**

### 1.8 AI 两级开关门控（定稿）

> **唯一真源是 `总览.md` §4.6**；本节是语音视角的复述，用于说明「互斥为什么不用单独写一套机制」。两处若冲突，以 §4.6 为准。
>
> 用户口径：**「一层开关（总闸）手机开语音就关、没网就关；二层开关唤醒词才开；两个开关同时开才可以运行」**。

#### 1.8.1 两级开关

| 层 | 名称 | 位置 | 打开条件 | 关闭条件 |
| --- | --- | --- | --- | --- |
| 第一层 | **总开关**（系统级） | 主板 | 三条**同时成立**：① 板子自测**有外网**（§1.8.2）；② **手机语音通道未开启**；③ AI 模块初始化正常（麦克风、功放、WSS 客户端、唤醒词引擎均就绪） | 三条中**任一条**不成立 |
| 第二层 | **二层开关**（会话级） | 主板 | **唤醒词命中**（本地引擎判定） | ① 进入 `AI_LISTEN` 后 **30 s 无任何输入**；② 播放完成（`tts.stop` / 缓冲排空）后**再计时 30 s** 仍无新输入 |

**运行 = 总开关 且 二层开关**。任一层为关，AI 一律不采集、不上行、不播放。

| 总开关 | 二层开关 | AI 状态 | 表现 |
| --- | --- | --- | --- |
| 关 | 任意 | `AI_DISABLED` | 二层开关**打不开**：唤醒词检测本身被关闭，说唤醒词没有反应 |
| 开 | 关 | `AI_IDLE` | 麦克风只做本地唤醒词检测，不上传、不联网 |
| 开 | 开 | `AI_RUN` | 才允许上行推流与 TTS 播放（进入 §1.6 的 `AI_LISTEN` / `AI_THINK` / `AI_SPEAK`） |

- App 观测：`0x87.flags.bit4` = 总开关、`bit5` = 二层开关（见 `数据.md`）。
- **两层开关都没有独立的 App 开关命令**：总开关由设备自动判定，二层只由唤醒词触发；App 只能读状态，不能直接置位。

#### 1.8.2 「有外网」的探测（板端自测，不能用 `WL_CONNECTED` 代替）

手机开热点但自身不开数据时，DHCP 照样分配 IP、`WL_CONNECTED` 也为真，可网关并不与外网互通；而 AI 依赖公网 443，只能由板子发真实探测。

| 项 | 值 |
| --- | --- |
| 主探测 | TCP 三次握手到 `api.tenclass.net:443`（小智云 OTA 域名），连上即关，不发应用层数据 |
| 备用探测 | DNS 解析 `api.tenclass.net`（超时 2 s），只用于区分「DNS 不通」与「TCP 被拦」，**不单独作为判据** |
| 单次超时 | **3 s** |
| 有外网时复查 | **30 s** |
| 离线时探测 | **10 s** |
| 判离线 | **连续 3 次失败**（最迟约 39 s 内确认） |
| 判恢复 | **连续 2 次成功**（间隔 10 s） |
| 触发时机 | `STA` 拿到 IP 后立即探一次；换 SSID、重连成功、IP 变化时清零计数并立刻重探 |
| 与 ctrl 的关系 | **完全独立**：探测失败只关 AI 总开关，`TCP 8080` 的 CMD / ACK / LOG / DAT 照常 |

**恢复后是否重走 OTA**：同一外网会话内短暂抖动（IP、SSID 未变）**不重走**，复用上次 WSS 地址；IP 变化或换 SSID（手机热点 ↔ 路由器）**重走 OTA** 再建连。

#### 1.8.3 门控状态图

```
        ┌─────────────────────────────────────────────────────────┐
        │ 总开关 OFF  →  AI_DISABLED                              │
        │ 无外网 / 手机语音开启 / AI 模块初始化异常               │
        │ 动作：停采集 · 丢 AI 音频 · 唤醒词检测关闭              │
        └───────────▲──────────────────────────┬──────────────────┘
                    │ 任一条失效                │ 三条同时成立
                    ▼                          ▼
        ┌─────────────────────────────────────────────────────────┐
        │ 总开关 ON、二层 OFF  →  AI_IDLE（待唤醒）               │
        │ 麦克风仅做本地唤醒词检测，不上行、不播放                │
        └───────────▲──────────────────────────┬──────────────────┘
                    │ 二层置关                 │ 唤醒词命中（二层 ON）
                    │ 30 s 无输入 /            │
                    │ 播放后再 30 s 无输入     ▼
        ┌─────────────────────────────────────────────────────────┐
        │ 双层全开  →  AI_RUN                                     │
        │ AI_LISTEN → AI_THINK → AI_SPEAK → AI_LISTEN（重新计时） │
        └─────────────────────────────────────────────────────────┘
```

#### 1.8.4 任一层关闭时的收敛

| 触发 | 时限 | 必须做的事 |
| --- | --- | --- |
| 外网判离线 | **≤ 200 ms** | 停上行采集 → 丢弃已收未播的 AI 音频 → 关 WSS → 关闭唤醒词检测 → 总开关置关 → 记 `0x70/0x36` |
| 手机语音开启（首包到达） | **≤ 100 ms** | 见 §1.8.5 |
| AI 模块初始化失败 | 启动时 | 总开关保持关，唤醒词不启动，记 E 级日志 |
| 30 s 无输入 / 播放后再 30 s 无输入 | 判定 ≤ 20 ms，收尾 ≤ 500 ms | 二层置关 → 回 `AI_IDLE`，唤醒词检测**保持开启** |

「立即收敛」= **停采集、丢 AI 音频、唤醒词失效**三件事同时发生，不允许「先把这句话说完再关」。

#### 1.8.5 与对讲（手机语音）的互斥 —— 总开关的自然结果

**互斥不单独写一套机制**：语音首包一到达，总开关条件②即不成立，总开关自动关，AI 按 §1.8.4 收敛。语音关闭后条件②恢复，但二层开关仍为关，因此**必须重新说唤醒词**。

时序约束沿用 §1.7，三条顺序不能颠倒：

1. 先回 `ACK`（若由命令触发通道切换）；
2. **≤ 100 ms** 终止 AI：停上行、停 TTS 并丢弃剩余缓冲、关 WSS、关闭唤醒词检测；
3. 再进对讲 `ACTIVE`。

优先级不变：**手机语音 > AI**。AI 正在播放时语音开启，同样立即中止 TTS，不留尾音、不叠加。

#### 1.8.6 无外网与恢复

| 跳变 | 行为 | 日志 |
| --- | --- | --- |
| 有外网 → 无外网 | 关 AI（总开关关）；唤醒词**不生效**；App 显示「需外网」；控制与视频照旧 | `0x70/0x36`（每次跳变只记一条） |
| 无外网 → 有外网 | 总开关置开；AI 回 `AI_IDLE` **待唤醒**，**不自动进入会话**，不补播断网期间的消息 | `0x70/0x37` |
| 手机语音开 → 关 | 条件②恢复，但二层仍关，**必须重新唤醒** | 不新增日志（语音侧另有记录） |

### 1.9 麦克风占用标志（App 通话优先，定稿 2026-11-11）

麦克风只有一路，**谁在采集必须只有一个 owner**。用一个设备侧占用标志 `micBusy` 表达，App 不需要下发任何新命令。

| 项 | 规定 |
| --- | --- |
| 置位 | 板子收到语音首包、进入 `ACTIVE`（`beginSession()`）的那一刻置位；**由 App 的通话行为触发，不由 App 直接写标志** |
| 清位 | 会话结束（收到 `FLAG_END` / 2 s 无包 / 链路断开）→ `CLOSING` → `IDLE`（`finishSession()`）时清位；`CLOSING` 的 ≤500 ms 收尾期间**仍算占用** |
| 检查点 1 | AI 上行 `pumpUplink()` 每次读麦前检查：`micBusy == true` 立即返回，不读 `Mic` |
| 检查点 2 | 本地唤醒词检测：语音开始即 `WakeWord::pause()`；语音期间 `resume()` 必须被拒绝，避免与对讲抢 I2S RX |
| 检查点 3 | AI 会话启动（`wake()` / 唤醒词命中）前检查：`micBusy == true` 时忽略唤醒，不建会话 |
| 与总开关的关系 | `micBusy` 就是总开关条件②的数据来源（手机语音通道是否开启）；条件②不成立 → 总开关关 → AI 按 §1.8.4 收敛。**这是自然结果，不另设一套互斥逻辑** |
| 故障态 | 语音因音频未就绪被拒绝时**不置位**（没有真正占用麦克风），AI 门控不受影响 |

- 固件落点：`Mic::setBusy()` / `Mic::isBusy()`（`main/audio/Mic.*`），`Voice::beginSession()` 置位、`finishSession()` 清位，`AiLink::pumpUplink()` 与 `WakeWord::resume()` 检查。
- App 观测：语音会话期间 `0x87.flags.bit4`（AI 总开关）必为 `0`；语音结束后恢复与否取决于外网与 AI 模块状态，二层开关仍需重新唤醒。

## 2. 能否复用当前协议（核心结论）

分三个层次回答：**帧格式能不能复用**、**通道能不能复用**、**TYPE 编号能不能复用**。

### 2.1 带宽账：先算清楚音频到底要多少

| 方案 | 计算 | 结果 | 备注 |
| --- | --- | --- | --- |
| PCM16 单声道 16 kHz | 16000 × 16 bit | **256 kbps / 32 kB/s** | 【估算】最朴素的直通方案 |
| PCM16 + 轻量帧头（20 ms 一包，643 B） | 640 B 音频 + 3 B 头 | **≈ 257 kbps** | 【估算】开销约 0.5%（见 §10） |
| Opus 16 kHz 单声道 16 kbps | 定码率 | **16 kbps / 2 kB/s** | 【估算】语音质量已可懂 |
| Opus 16 kHz 单声道 24 kbps | 定码率 | **24 kbps / 3 kB/s** | 【估算】接近手机通话质量 |
| BLE NUS（MTU 23，20 B/包，连接间隔 20 ms） | 20 B × 50 包/s | **≈ 8 kbps（含开销前）** | 【估算】 |
| BLE NUS（连接间隔 30~40 ms，Android 常见） | 20 B × 25~33 包/s | **≈ 4~5 kbps** | 【估算】 |
| BLE 理论最好（连接间隔 7.5 ms） | 20 B × 133 包/s | **≈ 21 kbps** | 【估算】公开理论值，实际拿不到 |

### 2.2 BLE 为什么过不了（选型依据，蓝牙已整体移除）

- PCM 需要 **256 kbps**，BLE 最理想也只有 **≈21 kbps**，差 **12 倍**；
- 即使改用 Opus **24 kbps**，也**高于** BLE 的理论上限，且语音需要的是**稳定**而非峰值速率；
- 当前固件**不协商 MTU**，每包固定 20 B（`MAX_NOTIFICATION_BYTES = 20`），没有提升空间；
- 单射频 2.4 GHz 下 BLE 与 WiFi 还要分时，蓝牙通话和「WiFi 视频同时开」一样不现实。

**结论：BLE 不承载语音，一条也不行。** 语音只在 WiFi 局域网可用；蓝牙已于 2026-11-11 整体移除，本节只作选型依据保留。

### 2.3 WiFi 为什么扛得住

| 链路 | 可用吞吐 | 256 kbps 占比 | 结论 |
| --- | --- | --- | --- |
| WiFi 近程 TCP（STA / AP） | 【待实测】按 ESP32-S3 2.4 GHz 常见水平估算 1~10 Mbps | < 5% | 直通 PCM 完全可行 |
| WiFi 近程 TCP（AP 直连，手机贴车） | 【待实测】通常更好 | < 5% | 首选场景 |

AP 直连时，手机连板子默认热点：SSID = `jianglingAPP`，密码 = `31957172yz`，车地址 `192.168.4.1:8080`（与《总览》§2.2 同一组凭据，可用 `0xC6` 改写，**仅本次运行有效、不持久化**）。

**结论：局域网 WiFi 跑 PCM 直通没有带宽压力**，压力全在延迟、抖动和回声（见 §4、§5）。

### 2.4 帧格式：不复用，改用语音轻量帧

**结论：不套用 ctrl 的 `AA|SEQ|TYPE|LEN|PAYLOAD|CRC8`，语音用独立的 3 字节头（定义见 §10）。**

| 项 | ctrl 帧的做法 | 语音要的做法 | 为什么不能共用 |
| --- | --- | --- | --- |
| 长度能力 | LEN ≤ 255 | 单块负载固定 640 B | 一帧装不下，20 ms 要切 3 帧，头部开销 ×3、解析次数 ×3 |
| 序号 | 帧头 SEQ 1 B | 毫秒时间戳低 16 位 2 B | 1 B 序号在 50 包/s 下 **5.1 s 就回绕**，无法判断迟到/丢包 |
| 差错控制 | 每帧 CRC8 | **不做 CRC** | 局域网丢包率低；语音丢一帧用 PLC 补即可，重传只会增加时延 |
| 语义 | 去重 / ACK / 能力闸门 / 优先级队列 | **全部不做** | 50 包/s 会冲掉 64 条命令去重环；ACK 会把实时流拖慢 |
| 解析 | 按 TYPE 查表 + 变长 | 固定 3 B 头 + 固定 640 B 负载 | 语音没有扩展类型需求，不需要类型表 |

### 2.5 通道能不能复用（不能）

**不能复用 ctrl 的 TCP 8080，而且不用 TCP，改用独立 UDP 8888：**

1. **队头阻塞**：同一条 TCP 流里，一个 640 B 语音包排在 ACK 前面，ACK 就被推迟 20~40 ms；一次 TCP 重传会把后面所有语音包一起压住，抖动直接变成几百毫秒。**控制面与实时流必须分开。**
2. **节拍冲突**：ctrl 是「有事才发」，语音是「每 20 ms 必发」。混在一起会被 ctrl 的单帧节流直接卡住。
3. **解析误判**：ctrl 解析器遇到未登记 TYPE 会**整帧丢弃**并逐字节重扫 `0xAA`，语音包混进 8080 只会刷日志。
4. **UDP 免重传**：TCP 丢包会阻塞后续包等重传；语音宁可丢一帧、用 PLC 补，也不等重传。
5. **同端口双向**：App 与板子都只用 8888 一个 socket 收发，不需要握手、不需要第二条连接。

### 2.6 结论（四句话）

1. **帧格式不复用**：语音用 3 字节头轻量帧（§10），不套 ctrl 五段帧、不算 CRC。
2. **通道必须独立**：语音走 **UDP 8888**，与 ctrl 的 TCP 8080 完全分开。
3. **无状态**：不做去重、不做 ACK、不进能力闸门、不参与优先级队列；时间戳只用于排序与抖动缓冲。
4. **BLE 不可承载语音**：语音只在 WiFi 局域网可用。

## 3. 通道设计

### 3.1 通道表

| 通道 | 承载 | 传输 | 端口 | 状态 |
| --- | --- | --- | --- | --- |
| ctrl | CMD / ACK / LOG / DAT | TCP 8080（运行期唯一；BLE 只做配网） | 8080（单出口） | 已实现 |
| **voice** | 双向音频帧（上行 + 下行） | **UDP** | **8888（板子 192.168.4.1，双向同端口）** | **固件已实现（本轮）；App 待接** |
| video | JPEG 流 | WS | 81（规划） | 未实现 |
| AI | WSS | 公网 443 | — | 阶段一 |

### 3.2 为什么是「独立 UDP + 同端口双向」

| 设计选择 | 取值 | 理由 |
| --- | --- | --- |
| 独立通道 | UDP 8888 | 与 TCP 8080 完全分开；UDP 无连接、无重传、无队头阻塞 |
| 同端口双向 | 一条 UDP socket | 收发都走 8888；对端地址由**收到的源 IP/port 学习**，不硬编码 |
| UDP 而非 TCP | UDP | TCP 丢包会阻塞后续包等重传，时延抖动被放大；语音宁可丢帧用 PLC |
| 不做握手 | 无 | 首包即会话开始；结束靠 bit5 结束帧或断链 |
| 不做 CRC / 不去重 / 无 ACK | 无 | 见 §2.4 |
| 接收侧抖动缓冲 | 攒 3 包（60 ms）起播，上限 8 包（160 ms） | 排乱序、抹平抖动；超水位丢最旧 |
| 不做发送缓冲 | 无 | 板子每 20 ms 发一次；网络/DMA 满即丢，不排队、不补发 |

**为什么不是 TCP**：TCP 的重传与拥塞控制会把「丢一个包」变成「全体等 200 ms+」，语音对这种放大零容忍；UDP 丢一帧只丢 20 ms，用 PLC 平顺过去即可（见 §5.4）。

### 3.3 与 BLE 的冲突：语音期间建议独占 WiFi

现有规则是「**BLE 已连接时，LAN 通道让路**」（`总览.md` §2.3）。语音恰好要求 LAN 通畅，因此：

| 阶段 | 行为 | 状态 |
| --- | --- | --- |
| 进入语音模式 | 设计约定：停 BLE 广播、断开已有 BLE 连接 | **本轮固件未改动 BLE，仍保持广播**（不改 BLE 代码是硬约束），共存影响待实测 |
| 语音模式期间 | LAN ctrl + voice(8888) 并行 | 已实现 |
| 退出语音模式 | 若曾停止广播则恢复 | 本轮无此动作 |

> 单射频共存会同时损伤 BLE 与 WiFi。本轮先不碰 BLE，**语音期间请勿同时使用 BLE 大数据量操作**；是否停广播留待实测后定（§11）。

### 3.4 一次语音会话的生命周期

```
IDLE
 │  App 打开语音开关 → App 立即向 192.168.4.1:8888 发首包（bit6=1）
 ▼
ACTIVE   双向 20 ms 流；板子用收到的源 IP/port 记住对端
 │  收到 bit5 结束帧 / 2 s 无任何包 / WiFi 断 / 设备复位
 ▼
CLOSING  停采集、停播放、清抖动缓冲、回一帧 END；≤ 500 ms
 ▼
IDLE
```

| 步骤 | 责任方 | 超时 / 兜底 |
| --- | --- | --- |
| 开始 | App | **首包到达即会话开始**；不要求握手，也不回 ACK |
| 对端学习 | 板子 | 以本会话第一个包的源 IP:port 为准；会话结束即遗忘，下次重新学习 |
| 保活 | App | 无论是否采集，**每 500 ms 至少一包**（静音期置 bit4）；**2 s 无任何包**判断链 |
| 结束 | App | 置 bit5 的结束帧；板子收到立即进 `CLOSING` |
| 异常结束 | 板子 | 2 s 无包、WiFi 掉线、音频致命故障；收尾 ≤ 500 ms |
| 空闲 | — | **不设任何空闲超时**，见 §1.5 |

### 3.5 与 ctrl 的关系

| 项 | 约定 |
| --- | --- |
| 语音包会出现在 8080 上吗 | **不会**。传输与端口都不同（UDP 8888 vs TCP 8080） |
| 语音会占 CMD 的 SEQ / 去重环 / ACK 吗 | **不会**，三者都不参与 |
| 语音期间 ctrl 还发 DAT 吗 | 照常，500 ms 一轮（带宽占比 < 1%） |
| 语音期间能发运动命令吗 | 能，走 8080；1 s 失联自停规则不变 |
| 语音期间 `CMD_RECORD` 录音 | 回 `ACK_ST_CANNOT(6)`（麦克风被通话占用） |
| 时间戳的作用 | 只用于排序、丢包判断、抖动缓冲；**不是法定序号**，不参与任何去重/握手 |

## 4. 延迟预算

### 4.1 「像打电话」的判定标准

| 单向延迟 | 体验 | 依据 |
| --- | --- | --- |
| < 150 ms | 接近面对面，几乎察觉不到 | 【公开标准】ITU-T G.114 推荐上限 |
| 150~400 ms | 可通话，但能感到「隔了一层」 | 【公开标准】同一建议书 |
| > 400 ms | 开始抢话、频繁打断 | 【公开标准】 |

**本项目目标：单向 100~160 ms，往返 200~320 ms。** 低于 150 ms 视为优秀，超过 250 ms（单向）判为不达标。

### 4.2 分段预算（以 PCM 直通、20 ms 帧为例）

| 段 | 目标耗时 | 说明 | 来源 |
| --- | --- | --- | --- |
| ① 采集缓冲（I2S DMA + 攒满 20 ms） | **20~40 ms** | 20 ms 块本身 + DMA 半满触发，取 1~2 块 | 【估算】 |
| ② 编码 | **0 ms**（PCM 直通）/ **1~5 ms**（Opus 20 ms 帧） | 定点 Opus 复杂度 0~5，S3 240 MHz | 【估算】【待实测】 |
| ③ 网络传输 | **2~15 ms** | 同房间 WiFi RTT 通常个位数 | 【待实测】 |
| ④ 抖动缓冲 | **40~80 ms** | 目标水位 60 ms（3 个 20 ms 帧） | 【估算】 |
| ⑤ 解码 | **0 ms**（PCM）/ **1~3 ms**（Opus） | | 【估算】 |
| ⑥ 播放缓冲（I2S DMA） | **20~40 ms** | `Speaker::play()` 非阻塞，DMA 深度决定 | 【估算】 |
| **设备侧单程合计** | **≈ 65~180 ms** | 不含手机系统音频路径 | 【估算】 |
| ⑦ 手机系统音频通路 | **10~30 ms** | 采集/播放各自的系统缓冲，iOS/Android 差异大 | 【待实测】【待确认】 |
| **端到端单程** | **≈ 75~210 ms** | 典型落在 **110~160 ms** | 【估算】 |

> 说明：表中「端到端单程」指「A 说话 → B 听到」。往返（A 说 → B 听 → B 回答 → A 听）约等于两个单程 + 人的反应时间，管道部分约 220~320 ms。

### 4.3 预算怎么保

| 措施 | 作用 |
| --- | --- |
| 20 ms 一块，不用 60 ms（AI 通道的取值） | 每块多 40 ms 是纯延迟，通话不能用 |
| 抖动缓冲初始 60 ms，自适应 40~120 ms | 40 ms 下限保证不饿死，120 ms 上限保证不「越积越慢」 |
| 接收端抖动缓冲超 160 ms 丢最旧 | 宁可断一拍，也不让延迟无限增长 |
| UDP 无发送缓冲、无 Nagle | 包到即发，不攒包 |
| 音频任务独立优先级 + 固定核 | 避免被 TFT 刷屏、WiFi 重连卡住 |

## 5. 采样与同步

### 5.1 采样参数（硬性）

| 参数 | 值 | 依据 |
| --- | --- | --- |
| 采样率 | **16 kHz** | `AudioBus::SAMPLE_RATE_HZ`，全双工下 TX/RX 必须同率 |
| 位深 | 16 bit | `Mic::read()` 输出 PCM16 |
| 声道 | 单声道 | 模块只接一路麦、一路功放 |
| 帧长 | **20 ms**（320 采样 / 640 B） | 延迟与开销的折中；可扩展 40 ms（1280 B，§10.4） |
| 字节序 | **小端（低字节在前）** | 语音轻量帧就地取 PCM16LE，与 I2S / Android `AudioRecord` 原生一致；**不套协议的大端约定** |

> 注意：语音通道的 PCM 是**小端**（§10），与 ctrl 协议「多字节大端」是两套规则；两端必须一致，否则会被听成噪声。

### 5.2 两端时钟不一致

两端各自用本地晶振产生 16 kHz，频率不可能完全相等。

| 项 | 估算 |
| --- | --- |
| 典型晶振偏差 | ±20 ppm（板载无源晶振常见值）【估算】 |
| 16 kHz 下每秒漂移 | 16000 × 20 ppm = **0.32 采样/s** |
| 每分钟漂移 | ≈ **19 采样 / 1.2 ms** |
| 10 分钟通话累计 | ≈ **12 ms**（约 0.6 个 20 ms 帧） |

**处理策略（抖动缓冲水位自适应）：**

| 水位 | 判定 | 动作 |
| --- | --- | --- |
| 正常 | 40~80 ms | 原样播放 |
| 偏高 | > 100 ms | 每 100 ms 检查一次；连续偏高则**丢一帧**（跳 20 ms），逐步回到 60 ms |
| 偏低 | < 40 ms | 用 PLC 延续上一帧（最多连续 2 次），再低则补静音 |
| 空 | 0 | 不补静音硬撑，直接进入「等待」；超过 2 s 无包判链路失效 |

- 不允许「靠调采样率对齐」：ESP32 I2S 改率会牵动 TX/RX 双工配置，代价大于收益（【推导】）。
- 漂移只在长通话显著；**10 分钟内的累计误差用一次丢帧即可抹平**。

### 5.3 回声抑制（结论已定：不换硬件，三层叠加）

> **本节全部为设计推断，尚无实测数据。** AEC 在 ESP32-S3 上的实际抑制量、CPU 占用与延迟增量，必须等结构件到位、有真实录音后实测；本文不预设效果数字。

**结论先定死：回声抑制不需要换硬件，也不靠单一手段，而是三层叠加，缺一层都补不回来。**

| 层 | 做什么 | 代价 | 什么时候做 |
| --- | --- | --- | --- |
| **① 声学隔离** | 麦克风与喇叭远离、朝向错开；中间加隔断/腔体；麦克风加减震（软胶、泡棉）抑制结构传导 | 结构件与装配工时，**没有电子成本** | **结构定型前必须做**。目标先把直达声削掉十几到二十分贝【估算】；定型后再改模具代价高得多 |
| **② 软件 AEC** | ESP32-S3 **没有专用 AEC 硬件**，只能跑算法。ESP-SR 的 AFE 内含 AEC：把「正在播放的音频」当参考信号，从麦克风采集信号里减掉回声 | CPU 占用、内存、算法对齐延迟（计入 §4.2 延迟预算） | **二期**。前提是参考信号拿得到、有真实录音可验证，见 §5.3.3 |
| **③ 时钟一致** | 播放与采集必须**同采样率、同一套 BCLK/LRCLK** | 现有架构已满足，无额外成本 | **从现在起作为架构红线**。一旦为别的功能拆成两路独立 I2S，两边晶振各自漂移，参考信号与采集信号逐渐错位，AEC 直接失效——这是架构问题，调参救不了 |

**为什么现有硬件已经够用**：AEC 的两个硬前提本项目都现成满足——

1. **参考信号拿得到**：`Mic` 与 `Speaker` 共用一套 I2S（`AudioBus`），播放数据在固件内部本来就有一份，可直接作为 AEC 参考信号，不需要额外回采电路；
2. **播放与采集同源时钟**：全双工共用 BCLK/LRCLK、同为 16 kHz（`AudioBus::SAMPLE_RATE_HZ`），不会各自漂移。

缺的是**声学隔离**与**算法**，不是换麦克风或换功放。

**回声路径对照**

| 环节 | 回声从哪来 | 谁能消 |
| --- | --- | --- |
| 车端喇叭放音 → 车端麦克风拾取 | 车端回声 | **设备侧**（一期靠半双工静音，二期靠 AEC）；手机端无法代劳 |
| 手机播放车端音频 → 手机麦克风拾取 | 手机自己的回声 | 手机系统 AEC（VoIP 音频会话自带），App 需显式配置通话音频模式 |
| 车端麦克风拾取车周围的人声 | 不是回声，是有效信号 | 保留 |

#### 5.3.1 一期策略：半双工，不做 AEC

**一期明确不做 AEC。用半双工把回声问题从「算法问题」降级成「调度问题」。**

| 谁在说 | 车端麦克风 | 车端喇叭 | 手机麦克风 | 手机喇叭 |
| --- | --- | --- | --- | --- |
| 手机用户（上行：手机 → 车） | **停采集**（只发静音心跳） | **播放手机语音** | 采集上传 | 静音 |
| 车周围的人（下行：车 → 手机） | 采集上传 | **静音** | **停采集**（只发静音心跳） | 播放车端语音 |

**一句话**：任何时刻只允许一路声学活动——**播的时候不采，采的时候不播**，听的一方把自己的麦克风静音。

> 方向口径：本文「上行」= **手机 → 车**。因此「手机推送时车端要静音」的对象是**车端麦克风**（此时车端喇叭正是播放手机语音的那一端）；「车端采集上行时」才静音车端喇叭。两者合起来就是上表，**播放与采集永不重叠**。

- **谁在说由谁判断**：车端用 `Mic::rms()` / `peak()` 做能量门限；App 侧用系统 VAD 或按住说话。方向切换加 **200~300 ms 迟滞**，避免来回抖。
- **与 AI 通道同构**：这正是现有 AI 通道「TTS 播报期间暂停上行音频」的同一套规避逻辑，实现上复用同一处互斥开关，**改造成本最低**。
- **半双工下回声不存在**：同一时刻没有「一边放一边收」，所以一期**不需要 AEC 参数、不需要额外算力、不需要实测抑制量**。
- **代价**：不能抢话，一方说完另一方才出声，切换瞬间有 200~300 ms 空档，体验接近**对讲机**而不是电话。

#### 5.3.2 为什么一期的半双工是「正式形态」而不是凑合

- 半双工的互斥开关、静音调度、方向切换，**二期仍然要保留**——AEC 失效或环境太吵时它就是兜底，不是白写的代码；
- 反过来，「看起来双向、实际啸叫」的方案比明确标注「一期是对讲机」更糟：用户会按电话的预期同时说话，得到的是回声和啸叫，属于**功能虚假可用**；调试时也无法区分「AEC 没调好」与「声学隔离没做」；
- 因此一期**不允许**把 AEC 写进默认路径，只能作为编译开关（默认关）存在。

#### 5.3.3 二期进入条件（AEC 转正的硬门槛）

以下四条**全部满足**才允许把半双工改成全双工，缺一条都不进：

| # | 条件 | 验收口径 |
| --- | --- | --- |
| 1 | **硬件到位** | 声学隔离件已定型并装到真机（麦克风/喇叭位置、隔断、减震固化）；I2S 参考信号路径确认可用 |
| 2 | **有真实录音可验证** | 能同时采到「参考信号 + 麦克风信号 + 播放信号」三段，形成可复现的回声语料（安静房间 / 有环境噪声 / 不同音量至少各一组） |
| 3 | **能测出实际抑制量** | 给出量化结果：回声回波损耗增强（ERLE）目标 **≥ 15~20 dB**【估算，待实测】，且**双讲**（双方同时说话）不出现明显吞字、断句 |
| 4 | **资源与延迟有余量** | AEC + WiFi + 音频并发连续 30 min 不丢帧；算法对齐延迟计入 §4.2 后，单向总延迟仍 **< 250 ms** |

> 四条不满足就**维持半双工**。半双工是正式交付形态，不是「临时凑合」；二期也不以「装上 AEC」为完成标志，而以**测出抑制量**为完成标志。

### 5.4 丢包与乱序

| 情况 | 处理 |
| --- | --- |
| 包乱序 | 按 16 bit 时间戳插入抖动缓冲；迟到超过水位上限的包**直接丢** |
| 丢包（UDP 无重传） | 不等待，用 PLC 补；迟到的旧包（时间戳早于已播放帧）丢弃 |
| 连续丢包 > 2 帧 | 输出静音，避免 PLC 拖出嗡嗡声 |
| 对端静音 | 一期不做 DTX：处于采集方向时连续发；播放/静音方向只发静音心跳包（见 §5.3.1）；二期 Opus 开启 DTX |

## 6. 优先级与抢占

### 6.1 优先级顺序

```
手机语音（上行/下行音频）
   > AI 消息（TTS 语音 + 字幕）
      > 普通数据（DAT 遥测）
         > 日志（LOG）
            > 视频（JPEG）
```

> 安全类命令（`CMD_STOP`）不参与排队：它走 ctrl，收到即执行、立即 ACK，任何时候都不降级。

### 6.2 落地方式

| 层面 | 做法 |
| --- | --- |
| **音频出口仲裁**（最关键） | 喇叭只有一个。`Voice` 有数据时 `Speaker` 只服务 `Voice`；AI 的 TTS 队列在语音模式期间**整体停用**（不是低优先级排队，是直接关闭 AI 会话） |
| **AI 互斥** | 语音首包到达即调用 `AiLink::closeSession()` 关闭 AI 会话；退出语音后 AI 才允许重新唤醒 |
| **网络出口** | 语音独占 UDP 8888，与 ctrl 的 TCP 8080 是两条完全独立的传输；ctrl 的 DAT/LOG 仍按 500 ms 节拍，不因语音加速 |
| **任务调度** | 语音收发/播放任务优先级高于 TFT 刷新与日志串口输出；I2S 读写保持非阻塞 |
| **缓冲策略** | 语音队列**不允许增长**：接收抖动缓冲超 8 包丢最旧；发送不排队、满即丢 |
| **视频** | 语音模式期间视频入口禁用（与 BLE 模式下无视频入口同理） |

**「手机发语音优先级最高」在 App 侧的含义**（App 需同步实现）：

1. 语音包播放优先于任何本地提示音；
2. 语音模式期间不播放 AI TTS、不弹 AI 字幕打断；
3. 语音上行采集优先于其他录音功能（录音在语音期间不可用）。

## 7. 状态机

> 本状态机只管语音通道；会话的开始与结束只由 App 命令、链路状态、设备故障决定，**不设空闲超时**（见 §1.5）。AI 的通道状态机见 §1.6，两者互斥见 §1.7。

### 7.1 状态定义

| 状态 | 含义 | 麦克风 | 喇叭 | UDP 8888 |
| --- | --- | --- | --- | --- |
| `IDLE` | 无语音会话（默认） | 归 AI / 录音 | 归 AI / 提示音 | 已绑定、空闲 |
| `ACTIVE` | 会话中（半双工：播时不采、采时不播） | 按方向启停 | 播放对端 PCM 或静音 | 双向收发 |
| `CLOSING` | 收尾中（≤ 500 ms） | 停 | 停 + 清抖动缓冲 | 只丢弃迟到包 |
| `FAULT` | 音频未就绪 / 致命故障 | 停 | 停 | 已绑定、拒收 |

> 没有 `OPENING`：UDP 不做连接握手，**首包到达即 `ACTIVE`**。

### 7.2 迁移表

| 起点 | 事件 | 终点 | 动作 / 兜底 |
| --- | --- | --- | --- |
| `IDLE` | 收到首个合法语音包（643 B，或 ≥ 3 B 头） | `ACTIVE` | 记对端 IP:port；清抖动缓冲；调 `AiLink::closeSession()`；回一帧 START |
| `IDLE` | 收到长度不符 / 非法包 | `IDLE` | 丢弃，不建会话 |
| `IDLE` | 首包到达但音频未就绪（Mic / Speaker） | `FAULT` | 丢弃并记一次 E 级日志，**不重启设备** |
| `ACTIVE` | 收到 bit5 结束帧 | `CLOSING` | 停采停播、清缓冲、回一帧 END |
| `ACTIVE` | 2 s 无任何包（含静音心跳；**断链判定，不是空闲超时**） | `CLOSING` | 判链路失效，记 E 级日志；空闲多久都不结束 |
| `ACTIVE` | WiFi 掉线 | `CLOSING` | 立即停采停播 |
| `ACTIVE` | 再次收到首包（bit6，App 重连/重开） | `ACTIVE` | 幂等：重置抖动缓冲与对端，**不重建会话** |
| `ACTIVE` | Mic / Speaker 读写出错 | `CLOSING` | 记 E 级日志，收尾后进 `IDLE` |
| `CLOSING` | 收尾完成（≤ 500 ms） | `IDLE` | 遗忘对端；恢复唤醒词检测；AI 回 `AI_IDLE`（**需重新唤醒**，§1.6） |

### 7.3 异常收尾清单

| 异常 | 必须做的收尾 | 不允许的做法 |
| --- | --- | --- |
| WiFi 断开 | 停采、停播、清抖动缓冲、遗忘对端、写日志 | 无限重连刷屏 |
| App 崩溃 / 杀进程 / 直接关热点 | 由 2 s 无包看门狗兜底 | 依赖 App 主动发结束帧 |
| 设备重启 | 上电即 `IDLE`（语音不持久化） | 记忆「上次在通话」，自动重开 |
| App 重复发首包 | 幂等，重置缓冲与对端 | 拆了重建会话 |
| 收尾超过 500 ms | 强制进 `IDLE` | 卡在 `CLOSING` |

| 7 | 网络抖动 | 家用路由器 + 2.4 GHz 干扰 | 延迟抖动放大 | 抖动缓冲 + 小 TCP 缓冲；实测为准 |

| 10 | 与录音 / AI 的资源冲突 | 共用同一 I2S 总线 | 并发即互相踩 | 全局互斥（§6.2） |
| 11 | 声学隔离错过结构窗口 | 结构件尚未做 | 后期补救成本高，回声抑制压力全部转嫁给软件 | 结构定型前完成隔离件（§5.3 第①层）。这是一期就该做、但不是软件改动的事 |

### 9.1 第一阶段能做到什么程度（明确边界）

**能做到**

- WiFi 局域网内、手机与车同网，按下开关即可对讲（**固件侧已实现，App 侧待接**）；
- 双向音频，单向延迟目标 < 250 ms；
- **无回声、无啸叫**（半双工调度，§5.3.1）；
- 语音期间 ctrl 与运动命令照常；
- 异常掉线自动收尾，不卡死设备、不影响屏幕。

**做不到**

- 蓝牙模式下通话（带宽不够）；
- 真正的「边听边说」/ 抢话（一期不做 AEC，只能半双工）；
- 公网远程通话；
- 高质量窄带压缩（无 Opus，占 256 kbps）。

## 10. 语音轻量帧定义（权威，固件已实现）

> 本节为定稿。语音**不走 V21 命令协议**：不定义 TYPE、不算 CRC、不回 ACK、不进能力闸门、不参与优先级队列。
> 语音没有扩展类型需求；将来若要加控制报文，另开端口，不往本帧里塞语义。

### 10.1 传输与地址

| 项 | 值 |
| --- | --- |
| 传输 | **UDP** |
| 端口 | **8888**（双向同端口） |
| 板子地址 | `192.168.4.1`（SoftAP 默认网关） |
| 对端 | App；板子从收到的**源 IP:port 学习**，不硬编码 |
| 包率 | 20 ms 一帧，**50 包/s**，每方向 |
| 总包长 | **643 B**（3 B 头 + 640 B 负载） |

### 10.2 帧格式

```
offset 0     1        2        3 ......................... 642
       [flags][ts_lo][ts_hi][        PCM 640 B           ]
```

**头 3 B（小端）**

| 偏移 | 字段 | 长度 | 说明 |
| --- | --- | --- | --- |
| 0 | `flags` | 1 B | 位定义见下表 |
| 1 | `ts_lo` | 1 B | 毫秒时间戳低 8 位 |
| 2 | `ts_hi` | 1 B | 毫秒时间戳高 8 位 |

**`flags` 位定义（1 B = 8 bit，逐位独立）**

| bit | 名称 | 取值与含义 |
| --- | --- | --- |
| 7 | `DIR` | `0` = App → 板；`1` = 板 → App |
| 6 | `START` | `1` = 会话首包 |
| 5 | `END` | `1` = 会话末包，收到即收尾 |
| 4 | `SILENCE` | `1` = 静音 / DTX 包，负载内容可忽略 |
| 3~0 | 保留 | 必须填 `0`，接收端忽略 |

**时间戳**：发送端本地毫秒时钟的**低 16 位**，约 65.5 s 回绕。只用于**排序、丢包判断、抖动缓冲**，**不是法定序号**，不参与任何去重或握手。

**负载**：`PCM16` / 16 kHz / 单声道 / **小端**，320 采样 = 640 B，正好 20 ms。静音帧负载填 0 或置 `SILENCE`。

### 10.3 语义约束

| 项 | 规定 |
| --- | --- |
| 去重 | **不做**。时间戳重复/回退的包直接丢 |
| ACK | **不做**。任何语音包都没有回执 |
| CRC | **不做** |
| 能力闸门 | **不做**。不查 `CAP_VOICE`，不验版本 |
| 优先级队列 | **不做**。语音不排队，缓冲满即丢最旧 |
| 会话开始 | `START`（bit6） |
| 会话结束 | `END`（bit5） |
| 保活 | App 每 500 ms 至少一包；静音期用 `SILENCE` |
| 板子心跳 | 板子处于「只听/只播」方向时，每 500 ms 回一个 `SILENCE` 包 |

### 10.4 扩展：40 ms 帧（后续优化，未实现）

## 11. 待确认

1. **BLE 共存**：本轮未停广播（不改 BLE 是硬约束），语音期间 BLE + WiFi 同射频的实际影响待真机实测后再定是否停广播。
2. **回声抑制落地条件**（原「AEC 方案」与「通话音量上限」合并）：ESP-SR `afe` 能否裁剪到只用 AEC、是否需要额外 Flash 分区、内存占用多少；实测 ERLE 与双讲表现；通话期是否需要固定音量上限；声学隔离件能否在结构定型前落实。
3. **手机系统音频路径延迟**：iOS / Android 各自实测值。
4. **Opus 库获取途径**：是否有可用的镜像/预编译包；拿不到就长期停在 PCM。
5. **App 侧对齐**：App 需改为 UDP 8888 + 3 B 头（小端）+ 640 B PCM16LE，并实现 500 ms 静音心跳与 bit5 结束帧；当前 App 的 8 B 头 / 8888 端口 / SSID 配置与固件不一致（见 §10）。
6. **长时间通话的功耗与温升**：需实测连续 30 min 的电流与外壳温度。
7. **AI 唤醒词尚未启用**：当前 `AI_ENABLE_WAKEWORD = 0`，§1.6 / §1.7 的唤醒与互斥规则需在唤醒词启用后联调验证（重点验证「语音关闭后必须重新唤醒」与「语音期间唤醒词无效」）。

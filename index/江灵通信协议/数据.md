# 江灵通信协议 · 数据（DAT）

> 本文件只写 DAT（车 → App）的字段与**推送调度**。TYPE、长度与字段取自固件 `Protocol.h`。
> 这 64 个类型是**平铺**的：低 6 位就是类型序号，表里的「分区」只是文档阅读用的中文分类，不是位域；App 与固件都按整字节 TYPE 查表。高 2 位 KIND 只表示方向（本表全部为 DAT）。
> 帧格式：`AA | SEQ | TYPE | LEN | PAYLOAD | CRC8`，帧总长 `5 + LEN`；LEN 等于本条 PAYLOAD 的字节数。多字节字段一律大端。SEQ 用车端独立计数器 `Data::_nextSeq`，与 LOG 不共用。
> **本版**：`0x87 DAT_INIT_STATE`（`LEN=9`）的 `[3]` 由 `role` 改为 `peerStage`，`flags` 位语义重排（副板在线 / 视频源 / 外网 / AI 两级开关）；**新增 `0x88 DAT_VIDEO_ENDPOINT`**（`LEN=7`，副板视频地址）。其余条目的 TYPE、PAYLOAD 与推送节拍不变。

| `0x88` | `DAT_VIDEO_ENDPOINT` | 状态 | `001000` | 副板视频端点（地址 + 端口 + 可用性） | `LEN=7` — `[0] state`（u8：0=不可用、1=可用）、`[1~4] ipv4`（4 B，副板地址；不可用时填 `0.0.0.0`）、`[5~6] port`（u16 大端，视频端口；不可用时填 `0`） | 收到副板 `0xF4`（IP/端口）且与上次不同、副板离线、副板恢复、`0xC0` 握手后端点已知 | **事件触发，不周期** |
| `0x90` | `DAT_MEM` | 统计 | `010000` | 内存与日志统计 | `16B — [0~1] ramFree`（u16，KB）、`[2~3] psramFree`（u16，KB，`0xFFFF` 无）、`[4~5] ramMinFree`、`[6~7] psramMinFree`、`[8~9] uptimeHigh`、`[10~11] uptimeLow`、`[12] logPending`（u8，条，255 饱和）、`[13] logQueueDepth`（u8，恒 `0xFF` 无效）、`[14~15] logDropped`（u16，条，65534 饱和）。`uptime = (uptimeHigh<<16) + uptimeLow`；字节 13 在 App 必须显示「无效」 | 与 `0x83`~`0x85` **同一轮**（握手或 `CMD_REQ_INFO` 补拉） | **不周期** |
| `0xA0` | `DAT_REQ` | 请求 | `100000` | 板端请求 App 执行动作 | `2B — [0] code`：1 停车、2 录音、3 左横移、4 右横移、5 俯仰、6 偏航、7 前进、8 后退、9 左转、10 右转；`[1] param` 随 code，越界车端静默裁剪到上限。App 不回应答，按 code 映射成 CMD 后用新 SEQ 发送；当前仅 code=2 有调用点 | 事件发生时才发 | **事件触发（边沿），不周期** |

**`0x87.flags` 位定义（1 B，逐位独立）**

| bit | 名称 | 含义 | 由谁置位 |
| --- | --- | --- | --- |
| 0 | `configured` | 本次运行已收到 App 下发的凭据并应用（**RAM 态，断电即忘，与 NVS 无关**） | 主板 |
| 1 | `peerOnline` | **副板在线**（等于 `peerStage ≥ 1`） | 主板（心跳判定） |
| 2 | `videoReady` | **视频源可用**（等于 `peerStage == 2`） | 主板（收到 `0xF4` 端点） |
| 3 | `internetOk` | **外网可用**（§4.6.2 探测结论，不是 `WL_CONNECTED`） | 主板（探测任务） |
| 4 | `aiMasterOn` | **AI 总开关**（外网可用 且 手机语音未开启 且 AI 模块正常） | 主板 |
| 5 | `aiSessionOn` | **AI 二层开关**（唤醒会话激活中） | 主板 |
| 6~7 | 保留 | 必须为 `0`，App 忽略 | — |

- `bit1` / `bit2` 是 `peerStage` 的**展开**，方便 App 只看 flags 就渲染；两者必须一致，不一致以 `peerStage` 为准。
- 旧版的 `bit1 = 使用默认 AP 凭据`、`bit2 = STA 失败已回落 AP` **作废**（这两个位已让给 `peerOnline` / `videoReady`）；**兜底 AP 状态不看 flags**，一律由 `wifiMode=1/2` + `stage=4` 表达，App 不要从 flags 推断是否回落了 AP（见 `总览.md` §2.2）。
- `bit4` / `bit5` 的判定口径唯一来源是 `总览.md` §4.6，本帧只做**状态回显**，不参与门控计算。
- `0x87` 与 `0x88` 的分工：`0x87` 给**两块板各自的阶段与就绪**（主板 `stage` + 副板 `peerStage` + 主板 `ipv4`），`0x88` 只给**副板视频端点**（IP + 端口 + 可用性）。App 连 ctrl 用 `0x87.ipv4`、连视频用 `0x88`，不要用 `0x87` 推副板地址。
- **网络三态跳变必须主动上报**：`0x86.state` 变化（尤其「已连无外网 ↔ 有外网」）时主板补一帧 `0x87`，App 据此切换网络提示与 AI 总开关显示，**不需要轮询 `0xC7`**（`0xC7` 只回 ACK，不带数据）；跳变判定沿用 `总览.md` §4.6.2 的阈值（连续 3 次失败才算离线、连续 2 次成功才算恢复），避免热点抖动导致提示闪烁。
- `0x88` 是 `0x87` 的**补充而非替代**：`0x88` 只在端点变化时发，`0x87` 仍在初始化/查询时发；两者可能不同步，App 以**各自最新一帧**为准。
- 方向只能 车 → App；DAT 不产生也不需要 ACK，App 不得对 DAT 回任何帧。
- DAT 不做断连补发；一次性数据漏收只能用 `CMD_REQ_INFO` 补拉。
- 优先级 DAT > LOG；DAT 只走 **回程 TCP 8080** 字节流，按 `5 + LEN` 重组，**这是唯一的回程通道**。**DAT 不走命令 UDP 8081**：UDP 8081 只承载 App → 主板的 CMD，下行数据仍走 TCP 8080（见 `总览.md` §2.3）。
- DAT 队列满（32 条）时丢弃新到的一条，并在「未满 → 满」那一刻发 `0x62 / param=0x01`；该码与 LOG 队列满**共用同一码**，App 无法区分来源。

## 3. 调度规则与理由

### 3.1 一次性：握手后一轮，之后不再发

**为什么不在周期里重复发**：

1. **省带宽**：`0x83`~`0x85` + `0x90` 一轮合计 4 帧（61 B），按 0.5 s 重复就是每秒 122 B 的纯静态信息；这些额度应留给遥测与日志，和 CMD 的 ACK 抢同一条 TCP 出口。
2. **这类数据「变了」意味着该重新握手**：型号、固件版本、协议版本、能力位在运行期不会变；真的变了（重烧固件、换硬件），正确动作是**重新建立会话**（`CMD_SESSION_INIT`）或**补拉**（`CMD_REQ_INFO`），而不是让 App 盯着周期包去猜。
3. **内存数据是排障用的快照**：`DAT_MEM` 反映的是握手那一刻的 RAM 水位、uptime 与日志丢弃计数；持续重复只会让 App 误以为这些值在实时变化，按需补拉更准确。

**触发点（唯一）**：`ACK_SESSION_INIT` 发出之后（WiFi 连上 / App 重连 / 车端重启后的首次握手），以及 `CMD_REQ_INFO` 的 ACK 之后。两处走同一段组帧代码，统一走 TCP 8080 出口，不各写一份。

### 3.2 慢变周期 5 s：电压

- 电压是**分钟级慢变量**：2S 电池在正常负载下 5 s 内的变化通常小于 0.1 V，更快的节拍只是把同一个值重复几十遍；
- 4~5 s 已足够让 App 判断「电量在掉」还是「在充电」，也不影响低电量提示的及时性；
- 取 **5000 ms**（落在用户给的 4~5 s 区间内），与快变档错开，避免两个档位在同一轮挤队列。

### 3.3 快变周期 0.5 s：转速、超声

- 轮速与测距**变化速率比电压快一个量级**：轮速直接参与运动是否打滑、是否堵转、是否到位判断，延迟会直接反映成**操控手感**（推杆后车已动、App 的轮速条还没动）；
- 0.5 s 是「人眼能接受的最小刷新」与「TCP 出口带宽」的折中：再快就要和 LOG、命令 ACK 抢同一出口；
- `DAT_WHEEL` 已接**左后轮单侧测速**（1 s 固定窗口），`DAT_US` 仍未接入；`0xFFFF` 只用于「该轮无效」，右轮当前恒为该值，不用来伪造 0。

### 3.4 边沿推送：跳变才补一包

**定义**：数值相对**上一包**的变化量达到阈值，且距上一次边沿 ≥100 ms，就立即补发一包；**不重置周期计时**，周期到点照发。

| 指标 | 阈值 | 内部单位 | 说明 |
| --- | --- | --- | --- |
| 电压 `DAT_BAT` | **0.10 V** | 10（0.01 V） | 满量程 8.4 V 的约 1.2%，能反映负载跳变/插拔充电 |
| 轮速 `DAT_WHEEL` | **0.25 r/s** | 25（0.01 r/s） | 最大轮速 5.00 r/s 的 5%，与摇杆死区同一口径 |
| 超声 `DAT_US` | **5 cm** | 5（cm） | 未接入；接入后按此值 |
| 边沿最小间隔 | **100 ms** | — | 压住阈值附近抖动造成的连发（`loop()` 约 10 ms 一轮） |

**和周期怎么配合**：

- **周期是保底心跳**：保证即使一直没有跳变，App 也知道「值还是这个值、链路还活着」；
- **边沿是及时性补充**：突然的电压跌落、轮速突变不用等下一个周期；
- 两者**不冲突**：同一次调度里若周期与边沿同时成立，只发一包；最坏情况是相邻两包内容相同，代价仅 7~21 B；
- 边沿包被链路挤掉也**无害**：下一次周期会带最新值，不需要重发。

**阈值常量落点**：`RuntimeCmd.h` 的 `DAT_BAT_EDGE_RAW`、`DAT_WHEEL_EDGE_RAW`、`DAT_EDGE_MIN_INTERVAL_MS`，注释写明单位。

### 3.5 当前不产生帧的条目

| 条目 | 原因 | 协议行为 |
| --- | --- | --- |
| `DAT_WHEEL 0x82` | 已接左后轮单侧测速 | 正常发送；右轮恒为 `0xFFFF`，App 视为「右轮无数据」 |
| `DAT_US 0x81` | 无超声波 | 不发送；能力位 bit3 = 0 |
| `DAT_REQ 0xA0` | 仅事件触发 | 当前只有录音结束的 code=2 |

## 4. 优先级与保底

DAT 在《总览》的优先级链里位于 **AI 消息与手机语音之下**：

`手机语音（最高） > AI 消息 > 普通数据（DAT） > 日志（LOG） > 视频`

因此节拍设计必须保证「即使被挤掉几轮，也不会让对端误判状态」：

| 情况 | 保底手段 |
| --- | --- |
| 慢变被挤掉几轮 | 下个 5 s 周期照发；电压本身变化慢，短时缺失不影响判断 |
| 快变被挤掉几轮 | 下个 0.5 s 周期照发；边沿包丢失也会被周期覆盖 |
| 一次性被挤掉/漏收 | `CMD_REQ_INFO` 补拉一整轮，不依赖重连 |
| App 判断「数据过期」 | 连续 **3 个周期**（电压 15 s、轮速 1.5 s）未收到即标「未知」，不沿用旧值做安全判断 |
| 队列满 | 丢弃新到的一条并发 `0x62/0x01`；DAT 不补发，靠下一次周期恢复 |

> 结论：周期负责**心跳与兜底**，边沿负责**及时性**，一次性负责**基线**；三者分工明确，任何一路被挤掉都能在下一次机会自愈。

## 5. 局域网 IP 广播发现（复用 `0x87` 原帧，定稿 2026-11-11）

**解决的问题**：板子是 STA，IP 由手机热点 DHCP 分配，App 不知道往哪连；而 `0x87` 表达 IP 又必须先进 TCP，形成「先有鸡还是先有蛋」。因此板子拿到 IP 后主动向局域网**广播 `0x87` 原帧**，App 监听同一端口，收到即建 TCP 8080。

| 项 | 规定 |
| --- | --- |
| 传输 | UDP **广播**，目的端口 **8082**（8080/8081 已占、8888 语音、81 视频） |
| 承载 | **复用 V21 原帧，不新增 TYPE**：`AA|SEQ|TYPE|LEN|PAYLOAD|CRC8`，TYPE=`0x87`（`DAT_INIT_STATE`），LEN=9，payload 与 TCP 上完全一致，CRC 照旧 |
| 目标地址 | **发两份**：受限广播 `255.255.255.255` **和**子网广播（如 `192.168.x.255`，由本机 IP + 掩码算出）。手机热点上单发受限广播有时到不了 App，两份最稳；**AP 档的第二份固定为 `192.168.4.255`** |
| 方向 | 板子 → App（单向）；App 不回任何应答 |
| 何时发 | **STA 已连并拿到本机 IP 后**：上电首次连上、换网后连上、IP 变化时；**AP / 兜底 AP 期间照常发**（热点起来即连发 3 帧，地址固定 `192.168.4.1`，App 在 AP 档也能自动发现，不必手填 IP） |
| 节奏 | 触发后**连发 3 帧**（间隔约 200 ms），之后**每 5000 ms 一帧**；间隔是实现常量，可调 |
| App 校验 | `AA` / LEN=9 / CRC8 / TYPE=0x87；并**要求 payload 里的 IPv4 等于数据包来源地址**，不一致直接丢弃。因此 payload 必须填本机真实 STA IPv4，不能填 `0.0.0.0` 或常量 |
| App 行为 | 校验通过即用该 IPv4 建 TCP 8080；重复帧只刷新地址，不重复建链 |
| 边界 | **广播只用于发现，业务仍走 8081（CMD）/ 8080（ACK/LOG/DAT）**，广播不承载命令、不回 ACK、不进去重表 |
| 丢包 | 无重传、无 ACK；靠 5 s 周期自愈 |

**帧结构（14 B = 5 + LEN 9）**

| 偏移 | 长度 | 字段 | 取值 |
| --- | --- | --- | --- |
| 0 | 1 B | `HEAD` | `0xAA` |
| 1 | 1 B | `SEQ` | 板端广播独立计数器，0~255 循环（与 `Data::_nextSeq` 不共用） |
| 2 | 1 B | `TYPE` | `0x87`（`DAT_INIT_STATE`） |
| 3 | 1 B | `LEN` | `9` |
| 4 | 1 B | `stage` | `3` = STA 已连网络并拿到 IP；`4` = 热点已起（AP / 兜底 AP，降级档） |
| 5 | 1 B | `wifiMode` | `0` = STA（已连路由器）；`1` = AP（热点档，含兜底 AP） |
| 6 | 1 B | `wifiState` | `1` = 已连无外网、`2` = 有外网（探测结论，不是 `WL_CONNECTED`）；**AP 档恒 `0`** |
| 7 | 1 B | `peerStage` | 副板阶段（`0` 离线 / `1` 心跳 / `2` 端点就绪；当前未接副板时恒 `0`） |
| 8 | 1 B | `flags` | bit0 `configured`、bit3 `internetOk` 有效；bit1/bit2 随 `peerStage` 展开；其余为 0 |
| 9~12 | 4 B | `ipv4` | **本机真实出口 IPv4**（必须等于 UDP 源地址）：STA 为 DHCP 地址，AP 为 `192.168.4.1`，4 B 大端 |
| 13 | 1 B | `crc8` | CRC-8/ATM（`0x07`），覆盖偏移 0~12 |

**示例**（板子 `192.168.43.27`，有外网）

```
AA 07 87 09 03 00 02 00 09 C0 A8 2B 1B <crc8>
```

- `stage=3`、`wifiMode=0`、`wifiState=2`、`peerStage=0`、`flags=0x09`（bit0 configured + bit3 internetOk）、`C0 A8 2B 1B` = 192.168.43.27。
- AP 档示例（兜底 AP，未配网）：`AA ?? 87 09 04 01 00 00 01 C0 A8 04 01 <crc8>` —— `stage=4`、`wifiMode=1`、`wifiState=0`、`flags=0x01`、`C0 A8 04 01` = 192.168.4.1，同时发往 `255.255.255.255` 与 `192.168.4.255`。
- 校验失败 / LEN≠9 / TYPE≠0x87 / IPv4 与源地址不符：App **静默丢弃**，不产生日志、不影响任何状态机。

> App 侧注意：Android 需持有 `WifiManager.MulticastLock` 才能稳定收到广播；只绑 8082。板子不做「被动应答扫描」，也不监听 8082，避免与 V21 混淆。

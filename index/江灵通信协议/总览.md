## 0. 名词与书写约定

| 名词 | 含义 |
| --- | --- |
| ctrl 通道 | 承载 CMD / ACK / LOG / DAT 帧的控制通道；**唯一通道是 WiFi** |
| 近程 | 手机与车在同一局域网（手机热点 / 路由器；兜底配网时为板子热点），不经公网 |
| 远程 | 手机与车不在同一局域网；**本方案不做**（公网穿透、鉴权、NAT、证书维护成本高） |
| AI 通道 | 独立的语音上行 / 语音+文字下行通道，**不属于 ctrl** |
| 播报完成 | 设备本地判定「本轮 TTS 音频已播完」（I2S 缓冲排空 / 播放回调），不是云端事件 |
| 板块 | 一条完整的通信能力域（WiFi / AI / 语音），一个板块内可以有多种子形态 |
| 子形态 | 同一板块下的具体工作方式（如 WiFi 的「近程·联网」「近程·热点」） |

- TYPE、帧头、原始字节用**十六进制**（`0xC3`）；参数、状态码、SEQ 用**十进制**。
- 字段位宽统一写 `8 bit（1 B）`；`1 B = 8 bit`；多字节一律**大端**。
- TYPE 是**整字节语义编号**；低 6 位是平铺的 64 个类型序号，高 2 位 KIND 只表示方向（命令/回复/日志/数据），不按位段拆分解析。

## 1. 板块划分：三个板块（WiFi / AI / 语音）

```
                ┌─────────────── 手机 App（只支持 Android）───────────────┐
                │  默认：开热点（可带外网）/ 可选：与双板同连路由器        │
                └──────┬────────────────────────────────────┬────────────┘
                       │                                    │
           V21 会话（唯一一条）                          视频（非 V21）
           命令 UDP 8081 · 回程 TCP 8080                 副板视频端口
                       │                                    │
        ┌──────────────▼──────────────┐      ┌──────────────▼──────────────┐
        │  主板                        │      │  副板                        │
        │  WiFi STA（上电即连，AP 仅兜底）│      │  WiFi STA · 摄像头           │
        │  命令解析与执行 · DAT/LOG     │      │  视频直推手机（不经板间）      │
        │  配网也经 WiFi（8081）        │      │  串口从设备（无 V21、无 SEQ） │
        │  AI 语音（麦克风与功放在本板）│      │                              │
        └──────────────┬──────────────┘      └──────────────▲──────────────┘
                       │  UART 921600（主 → 从：凭据 / 命令）  │
                       └──────────────────────────────────────┘
          UART 上行：命令结果 / 副板 IP 与端口 / 心跳 / 对时
          UART 不传：ACK 原帧 / DAT/LOG / AI 音频 / 视频
```

> **会话只有一条**：App 只与**主板**建立 V21 会话（SEQ 全局唯一、去重表唯一）；副板不监听命令端口、不参与 V21，只作为串口从机执行转发命令并自顾推视频。详见 §3.6.2。

| 板块 | 能做什么 | 可用条件 | 默认状态 | 固件状态 |
| --- | --- | --- | --- | --- |
| 一、WiFi（运行通道） | CMD / ACK / LOG / DAT（主板）+ 视频（副板）+ AI 承载（主板） | **上电默认 STA** 连手机热点 `jianglingAPP`；AP 仅兜底配网 | **默认开启** | ctrl 已实现；视频未落地 |
| 二、AI | 语音上行、语音 + 文字下行 | **主板**有外网 **且** AI 两级开关同时为开（§4.6） | 常驻待唤醒 | OTA + WSS + PCM 音频上下行 + 字幕 + 会话已实现（`ai/AiLink.cpp`）；Opus 编解码与唤醒词未接（PCM 直通、`wake()` 由 App 触发）；两级开关门控未实现 |
| 三、语音 | 手机与车的双向对讲 | WiFi 近程链路成立 | 空闲，等 App 发起会话 | **固件已实现**（UDP 8888 轻量帧，见 `语音.md`）；App 侧待接 |

**优先级链（全链路唯一口径，定稿 2026-11-11）**

`移动/云台命令 > 手机语音 > 数据/日志/遥测 > 视频 > AI 问答`

| 级别 | 内容 | 硬性规则 |
| --- | --- | --- |
| 1 | 移动 / 云台命令（UDP 8081，仅 WiFi） | 最高。小包优先处理，视频推流不得阻塞命令；丢帧不补，靠 300 ms 自停兜底 |
| 2 | 手机语音（板块三） | 语音通话期间视频降 5 fps 或暂停；AI 立即让出麦克风 |
| 3 | 数据 / 日志 / 遥测（TCP 8080） | 批量合批、可丢；不与运动帧抢发；不丢 CMD 的 ACK |
| 4 | 视频 | 允许丢帧、降质、不重传；弱网先降帧率再降分辨率/质量，最后暂停 |
| 5 | AI 问答 | 语音占用或外网不可用时整体关闭，不空转 |

- 同级按 FIFO，不抢占；跨级只在**整帧 / 整块边界**切换，不拆帧、不拆音频块。
- 之所以把命令放最高：操控直接决定车会不会撞，命令帧只有 17 B，让它插队成本极低。
- 之所以把语音放在 AI 之上：人对讲时不能等机器把话说完。
- 注意：命令与语音、视频共用同一条 WiFi 链路（§2.3、§5.1），优先级靠「UDP 不排队 + 小包优先 + 视频限码率」共同保证，不是靠独立物理通道。

## 2. 板块一：WiFi

WiFi 是**数据面与 AI 的物理承载**，但它本身只是传输；协议帧与 AI 消息都不属于 WiFi 板块。

### 2.1 默认拓扑与可选形态（定稿 2026-11-11：默认 STA，AP 兜底）

| 形态 | 网络条件 | 主板（命令 UDP 8081 / 回程 TCP 8080） | 副板视频 | AI 通道 |
| --- | --- | --- | --- | --- |
| **默认 · 手机热点** | 手机开热点 `jianglingAPP` / `31957172yz`；主板、副板、App 都连这个热点 | 可用（地址由热点 DHCP 分配，`0x87` 上报 IPv4） | 可用（副板直推手机） | **热点能出外网时可用**；无外网时总开关关（§4.6） |
| **可选 · 同一路由器** | 双板与手机都连同一路由器（换网后的形态） | 可用（`0x87` 上报 IPv4） | 可用 | 外网探测成功时可用 |
| **兜底 · 板子 AP（只配网）** | 默认网络连续 3 次退避重连失败（≈2 min），或 App 显式 `0xC4(1/2)` + `0xC8`；板子短时开 `jianglingAPP` / `192.168.4.1` | 可用（`192.168.4.1:8081` / `:8080`） | 不可用（副板未入网） | 不可用 |
| **远程（公网）** | — | **不做** | 不做 | 不做 |

- **上电第一形态是 STA，不是 AP**：`setup()` 用编译期常量 `jianglingAPP` / `31957172yz` 直接连手机热点，不需要 App 先连板子；`0x87` 上报热点 DHCP 分配的 IPv4。
- **AP 只是兜底配网口**：默认网络连不上（连续 3 次退避，约 2 min）或 App 主动要求换网时才起，SSID 仍是 `jianglingAPP`、地址仍是 `192.168.4.1`，配完（`0xC8` 生效）立即关 AP 回 STA；不做长期热点。
- **不是一失败就跳 AP**：单次失败只按 30 s 退避重连，超过阈值才起 AP；AP 期间后台仍每 30 s 尝试 STA，一连上就关 AP。
- **AP 期只做配网**：AP 模式下可收发命令、回执与日志（配网与排障），但**不推视频、不做外网探测**；AI 整体关闭。
- **有没有外网由板子自己探测**（§4.6.2），不以「手机热点已连」「已有 IP」代替；热点无网时 AI 整体关闭，控制与视频照常。
- **网络中心是手机热点**：手机开热点即整车网络；副板不开 AP、不参与配网决策。
- **换网回 AP 仍用现有命令字**：`CMD_WIFI_MODE(0xC4)` 的 `AP` / `APSTA` 是「回 AP」入口（配合 `0xC8` 提交生效），不是降级专用；App 连回 `jianglingAPP` 后即可重新配网（见 §2.4、`命令.md`）。

**命令只到主板，视频直连副板**：所有 CMD 由 **App → WiFi UDP 8081 → 主板** 下发，主板解析执行；视频类命令（开关流、分辨率、帧率、拍照）由 **主板 → 串口 → 副板** 转发，副板不监听命令端口（§3.6.4）。视频流本身由副板直接发往手机。

**只支持 Android**：iOS 无法用代码连 WiFi、个人热点对 2.4 GHz 与持续开启的限制也更严，本项目明确不支持 iOS，App 侧不写 iOS 引导流程。

**远程（公网）不做**：公网穿透、设备鉴权、NAT 打洞与 TLS 证书维护成本高，当前不投入；设备不暴露公网入口，也不连公网 relay。`../项目策略/AI与网络方案/03-公网远程操控.md` 仅作历史调研保留，不代表当前方案。

### 2.2 通道启停：上电 STA（默认），AP 仅兜底配网（定稿 2026-11-11 第五版）

| 模式 | 网络条件 | 局域网 ctrl | AI 通道 |
| --- | --- | --- | --- |
| `STA`（**上电默认 + 常态**） | 手机热点 `jianglingAPP`（编译期常量）或换网后的路由器 / 热点；凭据来自常量或 `0xC5` | 可用（IPv4 由 DHCP 分配，`0x87` 上报） | 外网探测成功时可用 |
| `AP`（**兜底配网口**） | 默认网络连不上（3 次退避）或 App 显式要求；板子自建 `jianglingAPP` / `31957172yz`，固定 `192.168.4.1` | 可用（`192.168.4.1:8081` / `:8080`） | 不可用 |
| `APSTA`（可选） | 边开 AP 边重连 STA（排障用） | 可用 | 外网探测成功时可用 |

- **上电默认 STA**：`setup()` 用 `m.h` 的 `WIFI_DEFAULT_STA_SSID` / `WIFI_DEFAULT_STA_PASSWORD`（`jianglingAPP` / `31957172yz`）直接 `WiFi.begin()`；20 s 未拿到 IP 进 `S7`，**不立即起 AP**。
- **只有 WiFi 一条通道**：AP 与 STA 是同一套 WiFi 栈的两种模式，命令、ACK、日志、遥测、AI 全在这一条链路上；**没有第二套通道、没有通道交接、没有通道仲裁**。
- **AP 兜底的两个触发**：① `S7` 退避重连**连续 3 次失败**（≈2 min）；② App 主动 `0xC4(1/2)` + `0xC8`。起来后 `192.168.4.1` 立即可用，受理 `0xC4`~`0xC8`。
- **配完立即回 STA**：`0xC8` 的 `mode=0` 直接关 AP 切 STA；未配网时保持 AP 等待，同时后台每 30 s 用最新凭据重连，成功即关 AP。
- **换网回 AP**：App 在板子当前所在网络里下发 `0xC4(1)` + `0xC8(1)`，板子离开 STA、重新起 AP（`jianglingAPP` / `192.168.4.1`）；不需要新增命令字。
- **`0xCB CMD_BLE_CONTROL` 已废弃**：原语义是「断链 + 停广播 / 恢复广播」，蓝牙移除后没有作用对象。编号保留不复用，收到一律回 `ACK 4 (UNKNOWN)`，不执行、不产生日志。
- **退避重连，不一失败就跳 AP**：每次尝试等 20 s 拿 IP，未拿到记 `0x60` / `0x25` 并退避 30 s 再试；**连续 3 次（20 s×3 + 30 s×3 ≈ 2 min）仍失败才起兜底 AP**；AP 期间继续重连，一连上就关 AP。
- **断链即停**：WiFi 断开（STA 掉线 / TCP 回程断开）任一发生，板子**立即主动停车**；这条与 300 ms 命令看门狗是**两层**保护，都要保留，不合并（§5.1）。
- **无持久化**：`0xC5` / `0xC6` 下发的凭据只存 RAM、断电即忘，不写 NVS；编译期默认凭据是**只读常量**，不读不写 NVS，不算网络记忆——重启后仍回到 `jianglingAPP`。
- **状态与模式正交**：对外状态是三态「未连网络 / 已连无外网 / 有外网」；`AP` 模式下三态恒为「未连网络」，但 `isLanReady()` 仍为真。
- **地址**：兜底 AP 固定 `192.168.4.1`，UDP 8081 与 TCP 8080 监听照常；STA 由 DHCP 分配，经 `0x87` 上报。
- **默认凭据（编译期常量）**：STA 用 `WIFI_DEFAULT_STA_SSID` / `WIFI_DEFAULT_STA_PASSWORD` = `jianglingAPP` / `31957172yz`；兜底 AP 用 `WIFI_AP_SSID` / `WIFI_AP_PASSWORD`（同名同密，WPA2），都在 `m.h` 里、都只读。
- **三态判定**：局域网 ctrl 门禁 = **已连网络**（AP 或 STA 都算，不需要外网）；AI 通道门禁 = **板子自己探测到外网**，判定参数见 §4.6.2，**不得用「WiFi 已连接」代替**。
- **单一 2.4 GHz 射频**：蓝牙不再启用，射频只服务 WiFi；ESP32-S3 只支持 2.4 GHz，手机热点不能开 5 GHz。

### 2.3 通道分工（定稿 2026-11-11：唯一控制通道是 WiFi）

| 通道 | 内容 | 端口/协议 | 优先级 |
| --- | --- | --- | --- |
| **discovery（发现）** | 主板地址广播（**复用 `0x87` 原帧**，UDP 8082） | 受限广播 `255.255.255.255` + 子网广播（`ip \| ~mask`；AP 档为 `192.168.4.255`）；连发 3 帧后每 5 s 一帧；**AP 档同样广播** | —（先于所有连接，见 `数据.md` §5） |
| **cmd（运行）** | **CMD 下行**（移动 `0xEB`、云台 `0xEC`、其余命令） | **UDP 8081**（一包一帧，V21 结构） | **1（最高）** |
| voice | 双向语音 | UDP **8888**（轻量帧，见 `语音.md`） | 2 |
| ctrl | ACK / LOG / DAT 回程与遥测 | TCP **8080**（STA 走路由器 IP，AP 走 `192.168.4.1`）；**任意 9 s 至少一帧**（`0x86` 5 s 心跳，连上即发） | 3 |
| video | 单帧 JPEG 流 | WS **81**（规划） | 4（最低，先降帧率） |
| AI 消息 | 语音上行 / 语音 + 文字下行 | 走小智云（OTA + WSS），**不走上面任何端口** | — |
| **init（初始化）** | 配网 `0xC4`~`0xC7`、提交 `0xC8`、查询 `0xC9`、恢复 `0xCA` | **与 cmd 同一条 WiFi 链路**（UDP 8081 下发，ACK 走 TCP 8080） | — |

**为什么命令走 UDP 而不是 TCP**

- TCP 有队头阻塞：一个丢包要等重传，后续命令全部卡住，操控表现为「一顿一顿」；UDP 丢一帧就丢一帧，下一帧（约 200 ms 后）自然补上，操控手感连续。
- 命令本身有**板端自停看门狗**兜底（300 ms 无新命令即停，§5.1、`命令.md`），丢帧不会造成持续运动。
- 回程 ACK / DAT / LOG 仍走 TCP 8080：这些是可靠、可容忍延迟的小流量，不与操控抢同一条队头。

**帧与解析（两条通道彻底分开）**

- 命令帧**直接复用 V21 结构** `AA | SEQ | TYPE | LEN | PAYLOAD | CRC8`，**不另造轻量帧**，避免两套解析器。
- UDP 数据报**一包一帧**：一个数据报里只放一个完整 V21 帧，`5 + LEN` 不等于报文长度即整包丢弃，不跨包拼接。
- **只有一条解析路径**：初始化命令与运行期命令都从 WiFi 同一入口进 `Cmd`，没有第二份解析器、没有旁路回执；ACK / LOG / DAT 统一由 `Wifi` 经 TCP 8080 发出。
- 收发都由帧类出口提供完整字节：`Cmd` / `Dat` / `Log` 的 `get()` 直接给出可发送帧，`Wifi` 只搬运字节，不组帧、不算 CRC。
- 视频**始终走 WiFi**：视频由副板直推手机，与命令共用物理链路但不进 V21，App 通过 `0x88` 拿端点。

### 2.4 配网职责边界（定稿 2026-11-11 第五版：STA 优先，AP 兜底）

**谁扫网、谁下发、谁执行、失败怎么回落，只有这一套口径。**

| 环节 | 责任方 | 规定 |
| --- | --- | --- |
| 扫描周边 WiFi | **没有人扫描** | App **不扫描周边 WiFi**，板子也不扫描上报；手机只负责把用户手填的 SSID / 密码原样下发 |
| 首次连接 | 板子自己 | 上电用编译期常量作 **STA** 连手机热点 `jianglingAPP`；连不上按 30 s 退避重连，连续 3 次失败才起兜底 AP |
| 换网入口 | App → 主板 WiFi | App 与板子在同一网络时直接经 **UDP 8081** 下发；不在同一网络时先连板子兜底 AP（`192.168.4.1`）再下发 |
| 凭据下发 | App → 主板 WiFi | `0xC4`（模式）/ `0xC5`（STA）/ `0xC6`（AP）；**只存 RAM，本次运行有效，不写任何持久化存储** |
| 应用凭据 | App → 主板 WiFi | `CMD_INIT_COMMIT(0xC8)`：改用 RAM 里的新凭据重连 WiFi（`mode=0` 切 STA，`mode=1` 回 AP） |
| 凭据转发 | 主板 → 副板 | STA 连接成功后串口 `0xF0` 同步当前有效凭据；副板同样只存 RAM；**副板没有独立配网入口** |
| 连接失败 | 主板 | **退避重连**（30 s），**连续 3 次（≈2 min）仍失败才起兜底 AP**（`jianglingAPP` / `192.168.4.1`）；AP 期后台继续重连，成功即关 AP；配网期间回 `ACK 5` |
| 外网判定 | 主板 | 板端探测（§4.6.2）；失败只关 AI，不影响 ctrl 与视频 |
| 副板角色 | 副板 | 配网后为纯 STA + 视频源 + 转发命令执行者；**不参与配网决策、不开 AP、不记忆凭据** |

**配网期间的板端状态（以板子为准）**

| 时点 | 板端行为 |
| --- | --- |
| 上电 / 复位 | 用常量凭据起 **STA** 连 `jianglingAPP`，同时起 UART；20 s 未拿到 IP 进入退避重连 |
| 退避重连 | 每 30 s 一次；**连续 3 次失败 → 起兜底 AP** `jianglingAPP` @ `192.168.4.1`，后台仍每 30 s 尝试 STA |
| 收到 `0xC4` / `0xC5` / `0xC6` | 只改 RAM，回 `ACK 3`，**不立即换网** |
| 收到 `0xC8` | 回 `ACK 0`（已受理），离开当前网络，按 `mode` 切 STA（或起兜底 AP） |
| 新网络就绪 | 主动发 `ACK(0xC8, 3)`=**初始化完成**（无后续收尾命令）；STA 下 `0x87` 上报 IPv4，AP 下固定 `192.168.4.1` |
| 初始化失败 / 超时 | 发 `ACK(0xC8, 5)`，30 s 退避重连；连续 3 次进兜底 AP；App 可改参数重提 |
| 任意时刻 | `0xC9` 幂等只读；`0xCB` 已废弃，回 `ACK 4` |

### 2.5 默认 STA 直连与「无记忆」策略（定稿 2026-11-11 第五版）

**上电即连手机热点，AP 只在连不上时兜底。** 板子用 `m.h` 的只读常量 `jianglingAPP` / `31957172yz` 作 STA 直连；`0xC5` 下发的换网凭据只活在这次运行里，不落盘。

| 项 | 规定 |
| --- | --- |
| WiFi 初始状态 | **STA**：`setup()` 用常量 SSID / 密码直接 `WiFi.begin()` 连手机热点；不预先起 AP |
| 默认凭据 | `m.h` 的 `WIFI_DEFAULT_STA_SSID` / `WIFI_DEFAULT_STA_PASSWORD`（`jianglingAPP` / `31957172yz`），**只读常量**；兜底 AP 沿用 `WIFI_AP_SSID` / `WIFI_AP_PASSWORD`（同名同密） |
| 换网方式 | App 与板子同网 → UDP 8081 下发 `0xC4` / `0xC5` / `0xC6` → `0xC8`；不同网 → 连兜底 AP 后同样下发 |
| AP 兜底 | 触发：退避重连连续 3 次失败（≈2 min）或 `0xC4(1/2)` + `0xC8`；SSID `jianglingAPP`、固定 `192.168.4.1`；配完立即回 STA |
| 回 AP | `0xC4(1)` + `0xC8(1)`：离开 STA、重建兜底 AP；App 重新连 `jianglingAPP` 即可再次配网 |
| 是否持久化 | **否**。不读不写 NVS、不写 flash；`0xC5` 只写 RAM，断电即忘；重启仍从常量网络（`jianglingAPP`）开始 |
| 凭据优先级 | `0xC5` 本次下发的 RAM 值 > 编译期常量；两者都不落盘 |
| 频段 | **2.4 GHz 专用**；ESP32 不支持 5 GHz，手机热点不能开 5 GHz |
| 副板 | 不接受配网、不记忆；网络参数由主板串口 `0xF0` 同步 |

**实现方式（常量 ≠ 持久化）**：`m.h` 里写 `static constexpr char WIFI_DEFAULT_STA_SSID[] = "jianglingAPP"` / `WIFI_DEFAULT_STA_PASSWORD[] = "31957172yz"`；`Wifi::begin()` 先 `WiFi.persistent(false)`（不写 NVS），再用常量 `WiFi.begin(ssid, pass)`。运行期收到 `0xC5` 时只覆盖 RAM 里的 `staSsid` / `staPass`，重启后 RAM 清空、回落到常量。全程不调用 `nvs_open` / `Preferences`，所以「不做网络记忆」与「写死默认凭据」不冲突：前者指不持久化用户下发的值，后者只是编译进固件的只读默认值。

**配网流程（唯一流程）**

1. 手机开热点 `jianglingAPP` / `31957172yz`，App 与双板都连上；主板用常量凭据连入，`0x87` 上报 IPv4；
2. 换网：App 经 **UDP 8081** 下发 `0xC4(0)`（选 STA）/ `0xC5`（新 SSID + 密码），每条都从 TCP 8080 回 ACK；
3. App 发 `0xC8(0)`（回 `ACK 0`），板子离开当前网络、换用新凭据连 STA；
4. 就绪后板子主动发 `ACK(0xC8, 3)` = 初始化完成；App 用 `0x87` 拿新 IPv4；
5. 连不上：回 `ACK(0xC8, 5)`，30 s 退避重连；**连续 3 次仍失败 → 起兜底 AP** `jianglingAPP` @ `192.168.4.1`，App 连 AP 重新配网；后台继续重连，成功即关 AP；
6. 想立刻回 AP：`0xC4(1)` + `0xC8(1)`；或断电重启，回到常量默认网络。

**代价**：板子必须与手机在同一热点（或路由器）；热点没开 / 改了名时板子连不上，要等 3 次退避后走 AP 兜底配网；AP 期副板与 AI 不可用。

**IP 发现**：STA 由 `0x87 DAT_INIT_STATE` 的 `ipv4` 字段上报 DHCP 地址；兜底 AP 固定 `192.168.4.1`。**不引入 mDNS，也不要求用户手填 IP。**

### 3.5 模式切换（已作废，改用 `0xC4`~`0xC7`）

### 3.6 江灵初始化（双 STA + 串口从机）

> **拓扑定稿**：**App 只与主板建立一条 V21 会话**；副板是主板的**串口从设备**，同时自己作为**视频服务端**直连手机。
>
> - **主板**：WiFi STA **唯一入口（命令 UDP 8081 / 回程 TCP 8080，配网命令同一条链路）**、命令解析与执行、DAT/LOG 推送、AI 语音（麦克风与功放都在本板）、串口主设备。
> - **副板**：WiFi STA、摄像头、视频直推手机；**不监听命令端口、不参与 V21、不分配 SEQ**；只执行主板经串口下发的命令，结果经串口回主板。
> - **一条会话**：SEQ 全局只有一个（App 的 CMD 计数器），去重表只有一份，都在主板；初始化命令与运行期命令共用这张表。
> - **视频**：仍由副板直连手机，**不走串口**；端口不进 V21 会话。
>
> **作废**：此前「副板开 AP + 转发」「主板代理副板配网」「两块板各一条 V21 会话 / 两个 SEQ 空间」「UART 不传命令」「副板保留最小 V21 端口」「BLE 兜底命令 / BLE 与 WiFi 共用解析入口」「BLE 配网 / 广播窗口 / 通道仲裁」这些表述**全部作废**，不得与本节并存。

#### 3.6.1 拓扑与职责

```
              ┌──────────────── 手机 App（Android）────────────────┐
              │  默认：手机开热点（可带外网）  可选：与双板同连路由器  │
              └───────┬───────────────────────────────┬────────────┘
                      │                               │
           V21 会话（唯一一条）                      视频（非 V21）
           命令 UDP 8081 · 回程 TCP 8080              TCP/WS 副板端口
           配网命令也走这条链路                        │
                      │                               │
       ┌──────────────▼──────────────┐   ┌────────────▲──────────────┐
       │  主板                        │   │  副板                      │
       │  WiFi STA 唯一通道 · 回程    │   │  WiFi STA · 摄像头         │
       │  配网 / 命令 / 回程共用       │   │  视频直推手机              │
       │  命令执行 · DAT/LOG · AI 语音│   │  串口从设备（无 V21 状态）  │
       │  串口主设备（唯一会话持有者）│   │                            │
       └──────────────┬──────────────┘   └────────────▲──────────────┘
                      │  UART 921600 8N1（主 → 从）     │
                      │  配网凭据 / 命令 / 对时          │
                      └───────────────────────────────┘
              （从 → 主）命令结果 / 副板 IP 与端口 / 心跳 / 状态
```

| 能力 | 主板 | 副板 |
| --- | --- | --- |
| 运行命令入口（UDP 8081） | **唯一持有** | 无 |
| WiFi | 有（上电先开 AP `jianglingAPP` @ `192.168.4.1`，配网后作 STA） | 有（STA，由主板经串口开启） |
| V21 会话 / SEQ / 去重表 | **唯一持有**（只服务 WiFi） | **无** |
| 命令接收与解析 | **全部**（WiFi） | 无（只收板间 `0xF1`） |
| 命令执行 | 本地命令 | 转发命令（视频类、双端类） |
| DAT / LOG 产生 | **全部**（只走 WiFi） | 无（经 `0xF2`/`0xF3` 上报给主板） |
| AI 语音 | **是**（麦克风 + 功放） | 无 |
| 摄像头 / 视频推流 | 无 | **是**，直推手机 |
| 对外端口 | 命令 UDP 8081、回程 TCP 8080（含配网命令） | 视频端口（见 `0x88`） |
| 串口角色 | 主设备 | 从设备 |

- **App 面向两个地址、但只有一条协议会话**：主板 IP 承载全部 V21 流量（命令 UDP 8081 下行、回程 TCP 8080）；副板 IP 只用于连视频端口，不承载任何 V21 帧。
- `0xE0`~`0xEC` 的运动 / 云台命令全部由主板解析并本地执行，**不再有「命令发给副板」的路径**。

#### 3.6.2 会话边界（关键结论）

| 链路 | 承载 | 协议 | SEQ |
| --- | --- | --- | --- |
| App ↔ 主板 | CMD（UDP 8081）/ ACK·LOG·DAT（TCP 8080） | V21（仅 WiFi 运行期） | App CMD 全局计数器，**唯一一份** |
| App ↔ 主板（初始化） | `0xC4`~`0xCA` + 回执 | V21，**同一条 WiFi 链路** | 与运行期共用去重表；`0xC8`~`0xCA` 幂等 |
| App ↔ 副板 | 视频流 | 视频端口私有协议 | 不涉及 V21 SEQ |
| 主板 ↔ 副板 | 配网凭据 / 命令 / 结果 / 心跳 / 对时 | **板间帧**（§3.6.3） | 板间独立计数器，**不与 App 混用** |

- 副板**没有** `CMD_SESSION_INIT`、没有握手、没有方向校验表、没有 64 条去重环。
- 因此不存在「双会话冲突」：App 只需要连一个地址、握一次手、维护一套 SEQ 窗口。
- 副板重启或掉线**不会**让 App 的会话失效：主板的 V21 会话照旧，只是视频源不可用并影响转发类命令。

#### 3.6.3 板间链路与板间帧

| 项 | 值 |
| --- | --- |
| 物理层 | UART，3.3 V TTL，TX/RX 交叉 + 共地，短距直连 |
| 波特率 | **921600 8N1**（115200 也够：板间峰值 < 2 KB/s；921600 把往返压到亚毫秒，为视频类慢命令留余量） |
| 骨架 | **复用 V21**：`AA | SEQ | TYPE | LEN | PAYLOAD | CRC8`，帧长 `5 + LEN`，CRC-8/ATM |
| TYPE 空间 | **独立 `0xF0`~`0xF6`**，不进入 App 侧 TYPE 表 |
| SEQ 语义 | **板间请求序号**：主→副 每帧 +1（回绕），副板在 `0xF2` 原样回显；心跳不带 ACK，SEQ 只作去重参考 |
| 校验 | CRC8 与 LEN 任一不符即整帧丢弃，并从下一个字节重扫 `AA` |
| 重传 | 需应答的帧（`0xF0` / `0xF1`）200 ms 未回重发，最多 **3 次**（总 600 ms）；心跳不重发 |

**为什么复用骨架但独立 TYPE，而不是 V21 原帧透传**

| 理由 | 说明 |
| --- | --- |
| 副板没有 V21 状态 | 无握手、无方向校验、无去重表，透传原帧它无法判断合法性，只能全盘接收 |
| SEQ 无法配对 | 原帧 SEQ 是 App 的计数器，主板无法用它做「请求-响应」配对与重传；板间必须有独立请求序号 |
| ACK 会重复 | 透传意味着副板直接组 `ACK_RESULT`，一次超时重传就会让 App 收到两条同 `SEQ+cmdType` 的终态 ACK，对账出现歧义 |
| 等于复制协议栈 | 透传要求副板实现 `payloadLengthValid()` 与全部命令表，违背「副板只做从设备」的定位 |

结论：**骨架与 CRC 复用（解析器、抓包工具、代码都能复用），TYPE 与 SEQ 独立**；不做 V21 原帧透传。

**板间帧定义**

| TYPE | 名称 | 方向 | LEN | PAYLOAD |
| --- | --- | --- | --- | --- |
| `0xF0` | `PEER_WIFI_CFG` | 主板 → 副板 | 2~96 | 布局同 `0xC5`：`[0] ssidLen`、SSID、其余为密码；需应答 |
| `0xF1` | `PEER_CMD` | 主板 → 副板 | 1~97 | `[0] cmdType`（原 CMD 整字节）+ 该命令原 PAYLOAD（≤96 B）；需应答 |
| `0xF2` | `PEER_ACK` | 副板 → 主板 | 2 | `[0] cmdType`、`[1] status`（取值同 `ACK_RESULT` 的 0/3/4/5/6） |
| `0xF3` | `PEER_STATE` | 副板 → 主板 | 4 | `[0] stage`（0 启动 / 1 连网中 / 3 已连 / 5 失败）、`[1] wifiState`、`[2] flags`（bit0 摄像头就绪、bit1 视频推流中）、`[3] rssi`（int8，dBm，未知填 `0x7F`） |
| `0xF4` | `PEER_IP` | 副板 → 主板 | 6 | `[0~3] ipv4`、`[4~5] port`（u16 大端，视频端口） |
| `0xF5` | `PEER_TIME` | 主板 → 副板 | 4 | `[0~3] uptimeMs` 低 32 位；**可选后置**，只用于日志对齐 |
| `0xF6`~`0xFF` | 空闲 | — | — | 整段保留为板内私有 |

- 板间帧方向不可反：副板只发 `0xF2` / `0xF3` / `0xF4`，不得主动发 `0xF1`。
- 主板对 `0xF2` 的 `status` 原样透传进 `ACK_RESULT`，不改写（副板回 4/5/6 时 App 看到同样的码）。

#### 3.6.4 命令归属表

| 归属 | 命令 | 处理方式 |
| --- | --- | --- |
| **主板本地** | `0xC0`~`0xC2`、`0xC4`~`0xCA`（系统 / 配网 / 初始化） | 主板直接执行并回 ACK |
| **主板本地** | `0xD0`~`0xD3`（音频自检 / 音量 / 录音） | 麦克风与功放都在主板 |
| **主板本地** | `0xE1`~`0xE8`、`0xEB`、`0xEC`（运动 / **差速轮盘** / **云台**） | 电机与舵机都接在主板；云台**当前归主板**，后续换硬件（舵机挪到副板）再评估是否改为转发。`0xEB`/`0xEC` 是流式两分量命令，主板本地执行，不走串口 |
| **转发副板** | `0xCC CMD_PHOTO_CAPTURE`（**当前唯一的转发命令**） | 串口 `0xF1` 下发 → 副板满性能拍照 → `0xF2` 回结果与元数据 → 主板组 `0x02 ACK_PHOTO` 并把副板 IP / 端口 / 图 ID 交给 App → **App 直连副板取图** |
| **双端执行** | `0xE0 CMD_STOP`（急停） | 主板先本地停车并**立即回 ACK 3**，再向副板发 `0xF1`（不等应答、失败不改变已回的 ACK）；副板侧停视频推流与云台 |

规则：

- 转发命令**只在主板解析与校验**（TYPE、LEN、去重、参数合法性都在主板），副板只负责执行，不做协议校验。
- 主板不得把同一命令既本地执行又转发（急停除外，见上表）。
- 副板离线时，`0xCC` **立即回 `0x02 ACK_PHOTO(status=5, err=8)`**，不排队、不回 `ACK 0`，避免 App 干等 8 s。

**拍照链路要点**（完整时序、字段与错误码见 `命令.md`「拍照命令的时序与结果语义」）

| 要点 | 结论 |
| --- | --- |
| 照片是否进 V21 | **不进**。V21 只承载命令（`0xCC` / `0xCD`）与结果（`0x02`）；一张 UXGA JPEG 150~300 KB，切上千帧会毁掉 SEQ / 去重 / 时延 |
| 照片路径 | **副板 → App 直连**（副板 HTTP 8090），**不经过主板、不经串口** |
| 副板 → 主板 | 只回结果帧 `0xF2`（LEN=18：err / photoId / bytes / w / h / captureMs），不回图像字节 |
| 主板职责 | 只有三件：转发快门、回执与地址告知、离线 / 超时代回。**不接收、不缓冲、不转发图像** |
| 分辨率 | 拍照「满性能」：UXGA 级、质量优先，与视频的「低分辨率、稳定优先」是两套参数 |
| 与视频互斥 | 拍照瞬间**暂停视频推流**，拍完恢复；满性能拍照必然带来 ≤2 s 的视频断流 |
| 主板缓存 | 只缓存最近一次**结果元数据**（图 ID / 尺寸 / 耗时 / 副板地址），供 `0xCD` 重放；不存图 |

#### 3.6.5 转发时序与超时预算

```
App               主板                              副板
 │  CMD(SEQ=n)     │                                 │
 ├────────────────►│ ① 校验 TYPE/LEN/去重/参数        │
 │                 │ ② 判定离线？离线→直接回 5         │
 │                 │ ③ 0xF1(seq=k,[cmdType][data])   │
 │                 ├────────────────────────────────►│ ④ 执行
 │                 │                                 │ ⑤ 0xF2(seq=k,[cmdType][status])
 │                 │◄────────────────────────────────┤
 │                 │ ⑥ 组 ACK_RESULT(SEQ=n,[cmdType][status])
 │◄────────────────┤                                 │
```

**返回给 App 的 ACK 默认只有一条终态**（不带 `ACK 0`），理由：

- 串口往返最坏 600 ms（3 次重传）+ 执行时间，仍远小于 App 的 4 s ACK 超时，没有「先回 0 占位」的必要；
- 同一 `SEQ` 回两条 ACK 会让 App 的对账状态机多一个分支，收益为零；
- **唯一例外是 `0xCC` 拍照**：整体可能 2 s 以上，固定两段——先 `ACK 0`（已受理、已写入串口），再 `0x02 ACK_PHOTO`（终态，带地址与图 ID）。除此之外不得再有命令回两条 ACK。

**时间预算**

| 段 | 值 | 说明 |
| --- | --- | --- |
| 串口单向传输 | 921600 下 ≈ 10.9 µs/B，最长 101 B 帧 ≈ **1.1 ms**；典型 7 B 帧 ≈ **0.08 ms** | 115200 下按 ×8 估算，仍 < 9 ms |
| 副板执行（快命令） | ≤ 100 ms | 急停、切换推流状态 |
| 副板执行（拍照） | 预计 **300~800 ms** | UXGA 抓拍 + JPEG 编码；主板等 **2000 ms** |
| 主板等待（普通转发命令） | **300 ms** | 覆盖一次重传 + 执行余量 |
| 主板等待（`0xCC`） | **2000 ms** | 覆盖两次重传 + 抓拍编码 |
| 重传 | 200 ms × 3 次 | 超时后回 `ACK_RESULT 5`（拍照回 `0x02 err=7`） |
| 离线直回 | **≤ 10 ms** | 不发串口，直接回 5（拍照回 `0x02 err=8`） |
| App 兜底 | 4 s（普通命令）/ **8 s**（拍照） | 与现有口径一致 |

#### 3.6.6 副板离线判定与代报

| 项 | 值 |
| --- | --- |
| 心跳周期 | 副板 → 主板 `0xF3` 每 **200 ms** 一帧 |
| 判离线 | 连续 **3 帧**（**600 ms**）未收到任何有效板间帧 → 副板离线 |
| 判恢复 | 连续 **2 帧**有效心跳（≤400 ms）→ 副板在线 |
| 主板本地影响 | **无**：控制、遥测、AI 全部照常；只是转发类命令与视频不可用 |
| App 如何看到 | `0x87.flags.bit1`（副板在线）= 0、`0x87.flags.bit2`（视频源可用）= 0；同时推一帧 `0x88 DAT_VIDEO_ENDPOINT`（`state=0`） |
| 离线时命令行为 | 视频类命令**立即回 `ACK_ST_ERROR(5)`**；急停仍本地执行并回 3 |
| 恢复时通知 | 收到 `0xF4`（IP/端口）→ `0x87` 置 bit1/bit2 → 推 `0x88`（`state=1` + IP + 端口）；**不重跑初始化** |
| 串口线断 vs 副板掉电 | App 表现相同（视频源离线）；主板日志区分（心跳超时 / 串口 CRC 错） |

#### 3.6.7 视频地址下发与刷新

**唯一载体是 `0x88 DAT_VIDEO_ENDPOINT`**（新增，见 `数据.md`）：`[0] state`（0 不可用 / 1 可用）、`[1~4] ipv4`、`[5~6] port`。

| 时机 | 主板动作 |
| --- | --- |
| 收到 `0xF4` 且端点与上次不同 | 推一帧 `0x88`（`state=1`） |
| 副板离线 | 推一帧 `0x88`（`state=0`，IP/端口填 `0`） |
| 副板恢复且拿到 IP | 推一帧 `0x88`（`state=1`） |
| App 刚握手完成（`0xC0`） | 若已知端点，紧跟一次性数据后补推 `0x88` |
| App 主动补查 | `CMD_INIT_STATUS(0xC9)` 只回 ACK，不补 DAT；运行期重连后由 `0xC0` 握手触发补推 |

- **视频端口不写死**：副板在自己的视频服务起来后把实际端口填进 `0xF4`，主板原样转给 App。文档默认值取 `81`（规划），实际以 `0x88` 为准。
- **IP 变化即刷新**：副板重连路由器后 IP 可能变，主板收到新 `0xF4` 就推新 `0x88`；App 收到后先断开旧视频连接再连新地址，控制会话不受影响。
- **App 不要缓存过期端点**：超过 30 s 未收到心跳类状态（`0x87`/`0x88` 不变）不影响视频；但收到 `0x88.state=0` 必须立即置灰视频入口。

#### 3.6.8 启动状态机（主板侧）

| 状态 | 名称 | 进入条件 | 动作 | 出口 |
| --- | --- | --- | --- | --- |
| `S0` | `BOOT` | 上电 / 复位 | **WiFi 以 STA 连默认热点**（`jianglingAPP` / `31957172yz`，编译期常量），同时起 UART 等副板心跳 | 拿到 IP → `S6`；20 s 未连上 → `S7` |
| `S1` | `REPROVISION` | **作废** | 原「`0xCB[1]` 恢复 BLE 广播」不再存在；编号保留不复用 | — |
| `S2` | `WAIT_HANDSHAKE` | **作废** | 原「BLE 已连接、只处理初始化白名单」不再存在；编号保留不复用 | — |
| `S3` | `AUTO_APPLY` | **作废** | 原「读 NVS 自动应用」不再存在；编号保留不复用 | — |
| `S4` | `WAIT_INIT` | 收到 `0xC4`/`0xC5`/`0xC6` | 参数只存 RAM；**WiFi 保持现有网络（STA 或兜底 AP）**；回 `ACK 3` | 收到 `0xC8` → `S5` |
| `S5` | `APPLYING` | 收到 `0xC8` | 校验 → 凭据只存 RAM → **离开当前网络**：`mode=0` 用新凭据连 STA，`mode=1` 重新起兜底 AP → `0xF0` 同步副板并等 `0xF2`（≤20 s）；立即回 `ACK(0xC8,0)` | 主板网络就绪 → `S6`；失败 / 超时 → `S7` |
| `S6` | `READY` | 主板网络就绪（STA 拿到 IP，或兜底 AP 已起） | **主动发 `ACK(0xC8,3)`＝初始化完成**；UDP 8081 + TCP 8080 照常；STA 下 `0x87` 上报 IPv4，AP 下固定 `192.168.4.1`；**兜底 AP 起来后仍每 30 s 尝试 STA，成功即关 AP** | WiFi 掉线 → `S7` |
| `S7` | `RECONNECT` | 认证失败 / 拿不到 IP / STA 掉线 | 能回则回 `ACK_RESULT` 状态 `5`，否则只记日志；**每 30 s 用当前凭据退避重连**；**连续 3 次（≈2 min）仍失败 → 起兜底 AP**，AP 期继续重连；也可显式 `0xC4(1)` + `0xC8(1)` 立即回 AP | 重连成功（并关 AP）→ `S6`；重新提交 → `S4` |
| `S8` | `PEER_LOST` | 副板 600 ms 无心跳 | 控制 / 遥测 / AI **不受影响**；`0x87.flags.bit1=0`、`bit2=0`；推 `0x88 state=0`；视频类命令回 5 | 心跳恢复 → `S6` |
| `S9` | `BLE_OFF` | **作废**（原 `0xCB[0]` 断链停播） | 编号保留不复用 | — |
| `S10` | `BLE_IDLE_OFF` | **作废**（原广播 1 分钟空闲停播） | 编号保留不复用 | — |

```
上电/复位
   │
   ▼
[S0 BOOT] WiFi 以 STA 连默认热点（jianglingAPP @ 手机热点）· 起 UART 等副板心跳
   │ 拿到 IP（20 s 未连上 → S7 退避重连）
   ▼
[S6 READY] UDP 8081 + TCP 8080 开放，App 与板子在同一热点即可握手 / 换网
   │
   ├── App 经 UDP 8081 下发 0xC4 / 0xC5 / 0xC6
   │        ▼
   │   [S4 WAIT_INIT] 参数只存 RAM，WiFi 保持当前网络，回 ACK 3
   │        │ App 提交 0xC8
   │        ▼
   │   [S5 APPLYING] 存 RAM → mode=0 切 STA / mode=1 起兜底 AP → 0xF0 同步副板（等 0xF2）
   │        │ 回 ACK(0xC8,0)；网络就绪 → 主动发 ACK(0xC8,3) = 初始化完成
   │        └──────────────► 回到 [S6 READY]
   │
   ├── 连不上 ──► [S7 RECONNECT] 30 s 退避；连续 3 次失败 → 起兜底 AP（192.168.4.1），App 连 AP 配网
   ├── WiFi/TCP 断链 ──► 立即停车 + 每 30 s 重连（[S7 RECONNECT]）
   └── 副板 600 ms 无心跳 ──► [S8 PEER_LOST]，控制不受影响
```

#### 3.6.9 「本次运行是否已收到凭据」的判定（RAM 态，无持久化）

**不能用 `initDone` / NVS 判断「是否配置过」**：本方案不做任何网络凭据持久化，但**保留编译期默认 STA 凭据**——上电直接用它连手机热点（`jianglingAPP` / `31957172yz`），换网命令同样从 WiFi 下发。

| 判定 | 条件（仅 RAM） | 结果 |
| --- | --- | --- |
| **本次运行未收到凭据** | `staSsid` 为空 | 用常量凭据连默认热点；连不上 30 s 退避，连续 3 次后起兜底 AP |
| **本次运行已收到凭据** | `staSsid` 非空（来自 `0xC5`，断电即失） | `0xC8` 后用这组凭据切 STA；失败进 `S7`，连续 3 次起兜底 AP |
| **已就绪** | 主板网络就绪（STA 拿到 IP 或兜底 AP 已起） | `S6`，发「初始化完成」，流程结束 |

#### 3.6.10 凭据运行期保存与双板一致性（不落盘）

| 运行期字段（RAM） | 内容 | 写入方 / 时机 |
| --- | --- | --- |
| `wifiMode` | u8：0=STA、1=AP、2=APSTA；**上电初值 0（STA）** | 主板，默认值 + `CMD_WIFI_MODE(0xC4)`；**仅本次运行有效** |
| `staSsid` / `staPass` | 网络 SSID / 密码 | **上电取 `m.h` 常量**（`jianglingAPP` / `31957172yz`）；配网时由 `CMD_WIFI_STA_CONFIG(0xC5)` 覆盖 RAM；**只存 RAM**，并 `0xF0` 同步副板 |
| `apSsid` / `apPass` | 兜底 AP 凭据；默认取 `m.h` 的 `jianglingAPP` / `31957172yz` | 主板，`CMD_WIFI_AP_CONFIG(0xC6)` 可覆盖；只存 RAM，不下发副板 |

- **有默认 STA 凭据，上电自连**：`m.h` 的 `WIFI_DEFAULT_STA_SSID` / `WIFI_DEFAULT_STA_PASSWORD`（`jianglingAPP` / `31957172yz`，2.4 GHz）是上电直连用的**只读常量**；`WIFI_AP_SSID` / `WIFI_AP_PASSWORD` 同值，只在兜底 AP 时用。`0xC5` 只覆盖 RAM 的 `staSsid/staPass`，不改常量、不写 NVS。
- 副板不持久化，也无法自己「记住」网络；**每次主板连上后经 `0xF0` 同步当前凭据**，副板用同一组参数连接。
- 主板必须在收到副板 `0xF2`（`status=3`）之后才发「初始化完成」`ACK(0xC8,3)`；副板应答失败则整次提交失败（回 `5`）。
- 每次副板重连，主板重新推一遍当前 RAM 凭据（`0xF0`），**不需要用户介入**；断电重启后主板回到常量网络（自动连 `jianglingAPP`），副板等主板再同步一次。
- **不支持**「副板单独配网」：副板没有独立配网入口，唯一来源是主板。

#### 3.6.11 超时与失败行为

| 项 | 值 | 失败后的行为 |
| --- | --- | --- |
| 初始化完成 | `0xC8` 后 20 s 内网络未就绪 | 回 `ACK(0xC8,5)`，链路保持，可重试；退避重连，连续 3 次失败起兜底 AP |
| STA 连接 | 20 s | 进 `S7`；每 30 s 重试一次，**连续 3 次失败起兜底 AP**，记 `0x60/0x25` |
| 板间配置帧 `0xF0` | 200 ms × 3 次 | 整次提交失败，回 ACK `5`，链路保持，记 `0x60/0x3A` |
| 板间命令帧 `0xF1` | 快命令 300 ms / 慢命令 1500 ms，含重传 | 超时回 `ACK_ST_ERROR(5)`，记 `0x60/0x3A` |
| 板间心跳 `0xF3` | 200 ms 发 / 600 ms 判离线 | 主板进 `S8`；副板侧只停视频、不断 WiFi |
| 外网探测 | 见 §4.6.2 | 探测失败只关 AI 总开关，不影响 ctrl |

#### 3.6.12 幂等与重入

| 场景 | 主板行为 |
| --- | --- |
| `S4` 期间重复 `0xC5` / `0xC6` | 覆盖 RAM 并回 ACK `3`，不立即重连 |
| `S5 APPLYING` 期间再收 `0xC8` | 回 ACK `6`，不打断当前流程 |
| 初始化中途 TCP 断开 | 当前 RAM 凭据保留，**继续执行到 `S6`**，不回滚；App 重连后可用 `0xC9` 取状态 |
| 提交过程中掉电 | RAM 清空，下次上电回到常量网络（`jianglingAPP`）；**不存在 `initDone`** |
| `0xC9` 任意时刻 | 幂等只读：回 `ACK(0xC9,3)` 表示已初始化完成、`0` 表示已提交未就绪、`4` 表示未提交 |
| `0xCB` 任意时刻 | 已废弃：一律回 `ACK 4 (UNKNOWN)`，不执行、不产生日志，编号不复用 |
| 副板单独重启 | 主板 `S8` → 副板重连后经 `0xF0` 取回凭据自连 → `0xF4` 上报 IP → 心跳恢复 → 回 `S6`，**不重跑初始化** |
| 转发命令超时后副板才回 `0xF2` | 迟到的 `0xF2` 按请求序号丢弃，**不再补一条 ACK** |

#### 3.6.13 失败模式

| 场景 | App 看到 | 车端行为 | 恢复 |
| --- | --- | --- | --- |
| 主板在线、副板离线 | 控制 / 遥测 / AI 正常；视频入口置灰；视频类命令回 5 | 主板进 `S8`，其余照常 | 副板上电 → 自行 STA 重连 → `0xF4` 上报 → 推 `0x88` |
| 副板在线、主板离线 | 控制全无（无 ctrl）；若 App 已知副板端点仍能看到视频 | 副板只推视频，等主板 | 主板上电 → 用常量凭据重连手机热点（连不上走兜底 AP）→ 重新配网/查状态 |
| 串口断开（线松 / 干扰） | 视频照样能看；控制正常；视频类命令回 5 | 主板 `S8`；副板不受影响 | 线恢复 → 心跳恢复；无需重配 |
| 视频正常但控制断 | 有画面、无控制 | 主板侧 1 s 无命令自动停车 | App 重连主板；或重启主板 |
| 手机热点被回收 | 双板同时掉线，画面与控制一起消失 | 双板保持 STA 重连 | 重开热点 → 板子自动重连 → IP 可能变化 → 等 `0x88` 刷新 |

#### 3.6.14 TYPE 落位与冲突检查

**`0xCB CMD_BLE_CONTROL` 已于 2026-11-11 废弃**（蓝牙移除），编号保留不复用；下表保留该行只为说明「不会与后续新增冲突」：

| TYPE | 名称 | 持有方 | 区段 | 前一个已占编号 | 冲突 |
| --- | --- | --- | --- | --- | --- |
| `0xC8` | `CMD_INIT_COMMIT` | 主板 | CMD 系统段 | `0xC7` | 无；`[1] role` 改为**保留必须为 0** |
| `0xC9` | `CMD_INIT_STATUS` | 主板 | CMD 系统段 | `0xC8` | 无 |
| `0xCA` | `CMD_INIT_FACTORY_RESET` | 主板 | CMD 系统段 | `0xC9` | 无 |
| `0xCC` | `CMD_PHOTO_CAPTURE` | 主板 | CMD 拍照段 | `0xCA`（`0xCB` 已废弃、不复用） | 无；`LEN=0`，帧长 5 B |
| `0xCD` | `CMD_PHOTO_STATUS` | 主板 | CMD 拍照段 | `0xCC` | 无；`LEN=4`，帧长 9 B；`0xCE`~`0xCF` 仍空闲 |
| `0xEC` | `CMD_GIMBAL_VECTOR` | 主板 | CMD 运动段 | `0xEB`（`0xE9`/`0xEA` 预留未实现） | 无；`LEN=2`、帧长 7 B；`0xED`~`0xEF` 仍空闲 |
| `0x02` | `ACK_PHOTO` | 主板 | ACK 段 | `0x01`（`ACK_SESSION_INIT`） | 无；`LEN=23`，帧长 28 B；`0x03`~`0x0F` 仍空闲 |
| `0x87` | `DAT_INIT_STATE` | 主板 | DAT 状态段 | `0x86` | 无；`[3] role` 改为 `peerStage`，`LEN` 仍 **9** |
| `0x88` | `DAT_VIDEO_ENDPOINT` | 主板 | DAT 状态段 | `0x87` | 无；**新增**，`LEN=7`、帧长 12 B；`0x89`~`0x8F` 仍空闲 |
| `0xCB` | `CMD_BLE_CONTROL`（**已废弃 2026-11-11**） | 主板 | CMD 初始化段 | `0xCA` | 编号保留不复用；`LEN=1` 仅为历史定义；**收到一律回 `ACK 4 (UNKNOWN)`，不执行**。原因：蓝牙整体移除，不再有广播需要开关 |

- ACK 段新增 `0x02` 不影响 `0x00 ACK_RESULT`（仍固定 LEN=2）：拍照的两段结果分别用 `0x00`（受理）与 `0x02`（终态），App 按 `SEQ + cmdType` 对账。
- `0xCC` 落在 `0xCB` 与 `0xCD` 之间的拍照段，与运动段 `0xE0`~`0xEC` 不重叠；`0xCD` 只查询、不拍照、不占串口。

**板间私有帧（UART，App 不可见，占用 `0xF0`~`0xF6`）**：见 §3.6.3 表；`0xF7`~`0xFF` 仍空闲，整段不进入 App 侧 TYPE 表。

- 板间帧沿用同一套骨架与 CRC-8/ATM，解析复用 `Protocol.h`；TYPE 落 `0xF0` 段，与 App 侧 `0xC0`~`0xEC`、`0x80`~`0xA0` 无交集。
- KIND 高 2 位取 `11`（CMD 段），但不对外，App 与固件都不按「未知 TYPE」处理。

#### 3.6.15 副板资源预算（为将来本地视觉留空间）

**定位**：命令解析**全部在主板**，副板只执行少数命令（当前只有拍照）。这样做的目的就是**不占用副板资源**，给后续本地视觉模型留出空间。

**职责边界（副板不做什么）**

| 不做 | 原因 |
| --- | --- |
| 不做 V21 协议解析、不建会话、不维护 SEQ / 去重窗口 | 会话唯一在主板；副板只认板间帧 `0xF0`~`0xF5` |
| 不监听命令端口、不单独配网 | 配网入口唯一在主板；副板只做 HTTP 取图（8090）与视频推流 |
| 不向 App 直接发 ACK / DAT / LOG | 结果统一经 `0xF2` 回主板，由主板组帧 |
| 不缓存图像、不转发图像 | 照片从副板直传 App |

一句话：副板是**带摄像头的执行末端**，不是第二个协议端点。此前「副板保留最小 V21 端口」「副板独立会话 / 独立 SEQ」两条**作废**。

**内存预算（8 MB PSRAM）**

| 用途 | 占用 | 计算 / 说明 |
| --- | --- | --- |
| 视频帧缓冲 | **≤ 1 MB** | QVGA（320×240）RGB565 = 150 KB/帧，双缓冲 300 KB；若升 VGA 只能单缓冲（600 KB） |
| 拍照 JPEG（3 张） | **≤ 1.2 MB** | UXGA（1600×1200）JPEG 约 150~400 KB/张，取上限 400 KB × 3 |
| 推理输入张量（预留） | **0.5~1 MB** | int8 320×240×3 = 225 KB，输入 + 输出双张量约 0.5 MB；灰度 320×240 = 77 KB |
| 模型运行时（预留） | **1~2 MB** | 权重常驻 flash、按层载入 PSRAM 的部分 + 中间激活 |
| 系统 / WiFi 栈 / 缓冲 | **≈0.3 MB** | 主要在内部 SRAM |
| 余量 | **≥ 3 MB** | 防碎片；`esp_get_free_heap_size()` 长期低于 1.5 MB 视为告警 |

- **UXGA 整帧 RGB 不能进内存**：1600×1200×3 = 5.76 MB，所以拍照必须**边采集边 JPEG 编码**，只保留压缩帧；这也是「拍照暂停视频」的内存原因。
- QVGA 单帧 RGB565 = **150 KB**；UXGA 单帧 JPEG = **150~400 KB**；两个数量级差在压缩率，不在分辨率本身。

**CPU 预算（双核 240 MHz）**

| 任务 | 占用 | 依据 |
| --- | --- | --- |
| JPEG 编码（QVGA，30 fps） | 10~15 ms/帧 → **30~45% 单核** | 【估算】硬件编码 |
| JPEG 编码（UXGA，单张） | **150~400 ms/张** | 【估算】；决定拍照耗时上限 |
| WiFi 上行（QVGA 30 fps MJPEG ≈ 3.6 Mbps） | **10~20% 单核** | 【估算】 |
| 串口 921600 收发 | **< 2%** | 帧短（典型 7 B）、中断少 |
| 推理（将来，MobileNetV2 级 int8 224×224） | **200~400 ms/次** | 【待实测】 |

- **推理生效时必须让视频让路**：视频 30 fps + 推理 3 fps 可以并存；**满分辨率拍照 + 视频 + 推理三者不并行**（任取其二）。
- 推理期间建议把视频降到 10 fps 或暂停，把单核算力让给推理。

**Flash 与分区（现在就要定）**

现状 `partitions_8MB.csv`（8 MB Flash）：`nvs` 0x5000 / `factory` 0x4F0000（5.18 MB）/ `spiffs` 0x2F0000（2.94 MB，装 1.9 MB 中文字库）/ `coredump` 0x10000。**没有 model 分区，空间也已被字库占满。**

**副板分区建议（定稿，主板分区不动）**

| 分区 | Type / SubType | Offset | Size | 用途 |
| --- | --- | --- | --- | --- |
| `nvs` | data / nvs | `0x9000` | `0x5000` | 配网凭据副本（与现状一致） |
| `factory` | app / factory | `0x10000` | `0x300000`（3 MB） | 副板固件（远小于主板） |
| `model` | **data / 0x40-0x01** | `0x310000` | `0x400000`（**4 MB**） | 视觉模型权重 |
| `spiffs` | data / spiffs | `0x710000` | `0xE0000`（896 KB） | 配置 / 日志 / 证书（副板无字库） |
| `coredump` | data / coredump | `0x7F0000` | `0x10000` | 崩溃转储 |

**改分区的影响（必须一次说清）**

1. **必须整片重烧**：分区表变了，`pio run -t upload` 不够，需要 `erase_flash` 后重烧 bootloader + 分区表 + 固件。
2. **SPIFFS 会被清空**：分区尺寸变化等于换了一块文件系统，**主板侧字库必须重新 `uploadfs`**（副板无字库，但要重传配置）。
3. **NVS 位置不变（0x9000/0x5000）可保留配网数据**；一旦改动 `nvs` 大小，NVS 会被重新格式化，**配网数据丢失**。
4. **不能用 OTA**：当前是单 `factory` 分区，没有 OTA 槽位；将来要 OTA 得改成双 app，会进一步挤压 `model`。
5. **主板侧另有一笔账**：启用 ESP-SR 唤醒词同样需要 model 分区，而主板 8 MB 已被 5.18 MB 固件 + 2.94 MB 字库占满。建议主板把 `factory` 收到 3.2 MB、`spiffs` 收到 2.4 MB，腾出 **2.2 MB** 给 ESP-SR 模型——这一条**未定稿**，需按字库实际占用实测后再改。

**任务优先级建议（FreeRTOS，数值越大越高）**

| 任务 | 优先级 | 理由 |
| --- | --- | --- |
| 摄像头采集 / DMA | **8** | 硬实时，采集丢帧不可恢复 |
| 串口收帧与解析 | **6** | 见下方说明，**不能设最高** |
| 心跳发送（`0xF3`） | 5 | 200 ms 周期，抖动 ≤100 ms 可接受 |
| 视频编码 | 5 | 可丢帧，靠降帧率保稳 |
| WiFi 上行 | 5 | 可丢帧，有 socket 缓冲 |
| 图 HTTP 服务（8090） | 4 | 可被视频与推理挤占，靠 TCP 重传兜底 |
| 推理（将来） | **3** | 最低，随时可被抢占；按帧分片推进 |
| 拍照（一次性） | **10（临时提升）** | 短时独占摄像头，拍完立即降回 |

**为什么串口不能设最高**

- 串口帧极短（典型 7 B、最长 101 B，921600 下 ≤1.1 ms 传完），对调度延迟本来就不敏感；
- 可靠性靠 **200 ms 重传 × 3 次**兜底，不靠抢 CPU；
- 一旦把串口设成最高，它会抢占摄像头 DMA 与 WiFi 发送，直接表现就是视频掉帧、推流卡顿；
- 它是**低频控制面**，不是实时数据面，优先级的正确位置在摄像头之下、可丢任务之上。

**分辨率策略**

| 场景 | 分辨率 | 像素格式 | 理由 |
| --- | --- | --- | --- |
| 视频推流 | QVGA 320×240（必要时 VGA 单缓冲） | RGB565 → JPEG | 稳优先：低分辨率高帧率 |
| 拍照 | **UXGA 1600×1200** | JPEG | 清晰优先：单张、可等 |
| 推理（将来） | **320×240**，必要时灰度 | int8 | 模型输入固定，灰度省 2/3 带宽 |

- **切换分辨率有重配置成本**：sensor 重配置 + 稳定约 **50~150 ms**，切到 UXGA 更久（约 200~400 ms，【估算】）。
- 因此「边推流边拍照」不是无缝的：必须**暂停推流 → 重配 → 抓拍 → 重配 → 恢复**，总中断 ≈300 ms（最坏 2 s），与 `命令.md` 的拍照时序一致。
- 推理与视频共用 QVGA，切换成本低；**推理 + 拍照**仍要走一次 UXGA 重配置，不能高频交替。

**一条原则**

后续加本地视觉，**只是给副板加一个任务**——不动协议、不动 App、不新增 TYPE。若将来确实需要副板承担更多命令，再单开一轮评估，不在本次范围内。

## 4. 板块二：AI

### 4.1 职责与可用条件

- AI 是否可用由**两级开关**决定，见 §4.6：**总开关**（有外网 + 手机语音未开启 + AI 模块初始化正常）与**二层开关**（唤醒词命中）**同时为开**才运行。
- 判定「有外网」必须由**板子自己探测**（§4.6.2），**不得用「WiFi 已连接」代替**：手机开热点但不开数据时 DHCP 照样给 IP，网关却不与外网互通。
- `AP` / `APSTA` 下设备没有外网出口，总开关恒关，App 显示「需外网」。
- **AI 全设备侧完成**：麦克风采集、唤醒、推流、播放、30 s 计时都在**主板**上；App 不推流、不调 AI 接口。
- **不依赖远程（公网）操控**：AI 是设备**出站访问**小智云（OTA + WSS），与「远程操控」不是同一件事。

### 4.2 独立性

- AI 是**独立通道**，与 ctrl / video **互不干扰**；
- **不占用 ctrl 的命令 SEQ**，也不读写车端的 64 条去重环；
- 音频怕队头阻塞：不复用 ctrl 连接，不塞进 video 流；WiFi 传数据时不得阻断 AI 消息（见 §1 优先级链）。

### 4.3 上行与下行

| 方向 | 内容 | 规格 |
| --- | --- | --- |
| 上行 | 设备麦克风语音流 | PCM16 单声道 16 kHz / 16 bit，20 ms = 640 B；公网链路优先 Opus 24–32 kbps |
| 下行 | AI 回复**语音 + 文字** | 文字 = 喂给 TTS 的同一段文本（同源），按句下发；音频 20 ms/块 |
| 对齐 | `utteranceId + sentenceIndex` 把同一轮的音频与文本关联，不要求同帧到达 | |

- 文字与 TTS 输入同源：收到文本即可上屏，收到音频即播，**字幕与语音逐字一致**。
- 文本消息不得阻塞音频发送路径；发不出去就丢（字幕可补）。

### 4.4 唤醒词与问答边界

| 项 | 约定 |
| --- | --- |
| 麦克风 | **常开**，但只做**本地唤醒词检测**（`WakeNet` 一类），不上传、不联网 |
| 唤醒词来源 | **App 端配置**：写入设备（建议落 NVS），配置命令尚未定 TYPE，见 `命令.md` 表下说明 |
| 生效时机 | 写入成功并**重启 / 下一次 AI 会话开始时**生效（不热切正在进行的会话） |
| 问答范围 | **只有唤醒后才开始向云端推流**；未唤醒不产生任何上行流量 |
| 会话结束 | **30 s 内无新一轮问答**自动关闭，需重新唤醒 |

### 4.5 30 s 计时（纯设备端）

```
用户说一句 → 设备推流 → 云端 ASR/LLM/TTS → 设备收到语音+文字
                                              ↓
                          设备本地播放（I2S 缓冲排空 / 播放回调）= 「播报完成」
                                              ↓
                                     开始计时 30 s
                                              ↓
              30 s 内又检测到新一问 → 继续会话；否则关闭，等下一次唤醒
```

- **播报完成由设备本地判定**，因此 AI 通道消息集里**没有**「播报完成上报」这一条；
- 计时**从一次问答的回复语音播报完成之后**开始，不是从收到音频开始，也不是从云端返回开始；
- 30 s 内 App 只能看到字幕/状态，不参与计时。

### 4.6 AI 两级开关门控（定稿）

> 用户口径：**「一层开关（总闸）手机开语音就关、没网就关；二层开关唤醒词才开；两个开关同时开才可以运行」**。
> 本节是 AI 可用性的**唯一判定口径**，固件与 App 都按这里实现，不另起一套。

#### 4.6.1 两级开关与门控表

| 层 | 名称 | 位置 | 打开条件 | 关闭条件 |
| --- | --- | --- | --- | --- |
| 第一层 | **总开关**（系统级） | 设备（主板） | 三条**同时成立**：① 外网探测 = 可用（§4.6.2）；② 手机语音通道 = 未开启；③ AI 模块初始化 = 正常（麦克风、功放、WSS 客户端、唤醒词引擎均就绪） | 三条中**任一条**不成立 |
| 第二层 | **二层开关**（会话级） | 设备（主板） | 唤醒词命中（本地引擎判定） | ① 进入 `AI_LISTEN` 后 **30 s 无任何输入**；② 播放完成（`tts.stop` / 缓冲排空）后**再计时 30 s** 仍无新输入 |

**运行 = 总开关 且 二层开关**。任一层为关，AI 一律不采集、不上行、不播放。

| 总开关 | 二层开关 | AI 状态 | 说明 |
| --- | --- | --- | --- |
| 关 | 任意 | `AI_DISABLED` | 二层开关**无法打开**：唤醒词检测本身被关闭，说唤醒词没有反应 |
| 开 | 关 | `AI_IDLE` 待唤醒 | 麦克风只做本地唤醒词检测，不上传、不联网 |
| 开 | 开 | `AI_RUN` 运行 | 才允许上行推流与 TTS 播放 |

- App 观测口径：`0x87.flags.bit4` = 总开关，`bit5` = 二层开关（会话是否激活），见 `数据.md`。
- 两层开关**没有**独立的 App 开关命令：总开关由设备自动判定，二层开关只由唤醒词触发；App 只能读状态，不能直接置位（AI 开关相关命令见 `命令.md`）。

#### 4.6.2 「有外网」的探测方案（板端自测）

**判据不是「WiFi 已连接」**：离线形态下手机开热点但自身不开数据，DHCP 仍会分配 IP、`WL_CONNECTED` 也为真，可网关并不与外网互通。AI 依赖的是公网 443，只能由板子自己发真实探测。

| 项 | 值 | 理由 |
| --- | --- | --- |
| 主探测 | TCP 三次握手到 `api.tenclass.net:443`（小智云 OTA 域名），连上即关，不发任何应用层数据 | 一次同时验证 DNS 解析与外网 TCP 可达；443 就是 AI 实际要用的端口，探通即可用 |
| 备用探测 | DNS 解析 `api.tenclass.net`（超时 2 s） | 主探测失败时用于区分「DNS 不通」与「TCP 被拦」，只作日志归因，**不单独作为「有外网」判据** |
| 单次超时 | **3 s** | 热点 / 路由器链路 RTT < 50 ms，3 s 足以判定失败 |
| 有外网时复查周期 | **30 s** | 及时发现热点被回收、手机断网 |
| 离线时探测周期 | **10 s** | 更快恢复；代价只是每 10 s 一次 SYN |
| 判离线 | **连续 3 次失败**（最迟 3 × (10 s + 3 s) ≈ 39 s 内确认） | 避免单次抖动就关 AI |
| 判恢复 | **连续 2 次成功**（间隔 10 s） | 避免刚连上就抖导致 AI 反复启停 |
| 触发时机 | `STA` 拿到 IP 后**立即探一次**；切换 SSID、重连成功、IP 变化时**清零计数并立刻重探** | IP 变了，上一次结论不再有效 |
| 与 ctrl 的关系 | **完全独立**：探测失败只关 AI 总开关，`TCP 8080` 的 CMD / ACK / LOG / DAT 照常 | 离线只影响 AI，不影响控制与视频 |

**恢复后是否要重新走 OTA**

| 情况 | 是否重走 OTA |
| --- | --- |
| 同一外网会话内短暂抖动（IP 未变、SSID 未变） | **不重走**，复用上次 OTA 下发的 WSS 地址直接重连 |
| IP 变化或更换 SSID（手机热点 ↔ 路由器） | **重走 OTA**，重新取 WSS 地址后再建连 |

#### 4.6.3 门控状态图

```
        ┌─────────────────────────────────────────────────────────┐
        │ 总开关 OFF  →  AI_DISABLED                              │
        │ 条件：无外网 / 手机语音开启 / AI 模块初始化异常          │
        │ 动作：停采集 · 丢弃 AI 音频 · 唤醒词检测关闭            │
        └───────────▲──────────────────────────┬──────────────────┘
                    │ 任一条失效                │ 三条同时成立
                    │                          ▼
        ┌───────────┴─────────────────────────────────────────────┐
        │ 总开关 ON、二层开关 OFF  →  AI_IDLE（待唤醒）            │
        │ 麦克风仅做本地唤醒词检测，不上行、不播放                 │
        └───────────▲──────────────────────────┬──────────────────┘
                    │ 二层开关 OFF             │ 唤醒词命中（二层开关 ON）
                    │ 30 s 无输入 / 播放完成后  │
                    │ 再 30 s 无输入           ▼
        ┌───────────┴─────────────────────────────────────────────┐
        │ 双层全开  →  AI_RUN                                     │
        │ AI_LISTEN → AI_THINK → AI_SPEAK → AI_LISTEN（重新计时）  │
        └─────────────────────────────────────────────────────────┘
```

`AI_LISTEN` / `AI_THINK` / `AI_SPEAK` 的逐状态定义见 `语音.md` §1.6；本节只定「能否进入」。

#### 4.6.4 任一层关闭时的收敛动作

| 触发 | 时限 | 必须做的事 |
| --- | --- | --- |
| 外网判离线 | **≤ 200 ms** | 停上行采集 → 丢弃已收未播的 AI 音频 → 关 WSS → 关闭唤醒词检测 → 总开关置关 → 记一条 `0x70/0x36` |
| 手机语音开启（首包到达） | **≤ 100 ms** | 见 §4.6.6：先 ACK、再终止 AI、再进对讲 |
| AI 模块初始化失败 | 启动时 | 总开关保持关，唤醒词不启动，记 E 级日志 |
| 30 s 无输入 / 播放完成后再 30 s 无输入 | 判定 ≤ 1 个音频块（20 ms），收尾 ≤ 500 ms | 二层开关置关 → 回 `AI_IDLE`，唤醒词检测保持开启 |

「立即收敛」的含义是**三件事同时发生**：停止采集、丢弃 AI 音频、唤醒词失效。不允许「先把这句话说完再关」。

#### 4.6.5 无外网与恢复时的行为

| 状态跳变 | 设备行为 | 日志（`日志.md`） |
| --- | --- | --- |
| 有外网 → 无外网 | 关 AI（总开关关）；唤醒词**不生效**（说唤醒词无反应）；App 显示「需外网」；**控制与视频照旧** | `0x70/0x36`（Info，**每次跳变只记一条**，不按探测周期刷屏） |
| 无外网 → 有外网 | 总开关置开；AI 回到 `AI_IDLE` **待唤醒**，**不自动进入会话**，也不补播断网期间的消息 | `0x70/0x37`（Info） |
| 手机语音开启 → 关闭 | 总开关条件②恢复；但二层开关仍为关，**必须重新说唤醒词** | 不新增日志（语音侧另有自己的记录） |

#### 4.6.6 与手机语音的互斥（总开关的自然结果）

互斥**不单独写一套机制**：手机语音通道一开启，总开关条件②即不成立，总开关自动关，AI 按 §4.6.4 收敛。语音关闭后条件②恢复，但二层开关仍为关，所以要重新唤醒才可用。

时序约束沿用既有口径，三条顺序不能颠倒：

1. 先回 `ACK`（若由命令触发通道切换）；
2. **≤ 100 ms** 终止 AI：停上行、停 TTS 并丢弃剩余缓冲、关 WSS、关闭唤醒词检测；
3. 再进对讲 `ACTIVE`。

优先级不变：**手机语音 > AI**（§1 优先级链）。AI 正在播放时语音开启，同样立即中止 TTS，不留尾音、不叠加。

## 5. 板块三：语音

- **定位**：手机与车之间的近实时对讲（双向语音），不是 AI 问答；AI 问答应让位于它。
- **依赖**：WiFi **近程**链路（STA 或 SoftAP 均可，不需要外网）；要求接近实时通话的稳定性，抖动与延迟预算按通话标准而不是按推送标准。
- **优先级**：仅次于移动/云台命令（见 §1 优先级链），手机语音可打断 AI 上行与下行。
- **当前状态**：协议细节在 `语音.md`（第 6 份文档），UDP 8888 / 3 B 头 + 640 B PCM / 20 ms 一帧；**固件已落地**（`main/wife/Voice.cpp`），**App 侧仍待接**（App 尚未实现该 UDP 收发）。

### 5.1 通道与优先级（带宽预算 + 射频让路，定稿 2026-11-11）

**前提（定稿 2026-11-11）**：移动命令（`0xEB` / `0xEC` 等）**只走 WiFi UDP 8081**（§2.3），与语音、视频**共用同一条 WiFi 链路与同一个 2.4 GHz 射频**，参与带宽竞争。它的保护有三层：① UDP 无队头阻塞，丢帧下一帧补，不排队等待；② 板端**流式自停**（300 ms 无新帧即停，见 `命令.md`）；③ **断链即停**（WiFi / TCP 断开立即主动停车，见调度规则 6）。**限制视频码率仍然是安全问题，不是体验问题。**

| 通道 | 承载 | 实测口径 | 预算 |
| --- | --- | --- | --- |
| 移动 / 云台命令 | **UDP 8081**（V21 帧，`0xEB` / `0xEC`，约 5 帧/s） | 单包 17 B，一包一帧，不重传 | < 1 kbps；**与语音视频共用 WiFi**，靠 UDP 不排队 + 300 ms 自停兜底 |
| 语音 | UDP 8888，16 kHz 单声道 PCM16，640 B/包，50 包/s | `640 × 50 × 8` | **约 256 kbps**（双向各一份） |
| 视频 | WS 81，640×480、10 fps、JPEG q60 | 单帧约 25~37 KB | **约 2~3 Mbps**；**800×600 / 15 fps / q70 会到 6~9 Mbps，禁止配置**（会拖垮语音与命令） |
| 拍照 | 副板直传 App，TCP 突发 | 单张 UXGA 150~300 KB | **不占常驻带宽**，只在快门瞬间突发 |
| ACK / 日志 / 遥测 | ctrl TCP 8080（V21 帧） | 帧长 5~29 B，500 ms 一轮 | **合计 < 100 kbps** |
| AI | 上行复用语音通道的采音；下行只有文字 | 不走音频下行 | 上行随语音；下行可忽略 |

**调度规则（按优先级从高到低）**

1. **语音通话进行中，视频必须降到 5 fps 或暂停**；语音结束（`micBusy` 清零）后恢复原帧率。判定只有一个入口：`Mic::isBusy()` / `Voice::isActive()`，**禁止在视频模块里各处散写判断**。
2. **日志与遥测批量发送、可丢**：每 500 ms 一轮合批，不与运动帧抢发；拥塞时先丢 DEBUG/INFO，不丢 CMD 的 ACK。
3. **AI 采集只在语音空闲且外网可用时进行**：即 §4.6 总开关为开（`micBusy == false` 且 `internetOk == true` 且 AI 模块正常）。
4. **视频帧允许丢、允许降质、不重传**；弱网先降帧率，再降分辨率/质量，最后暂停视频保语音与命令。
5. **命令小包优先处理**：事件循环里先收命令（UDP 8081）再推视频，命令到达即执行，视频推流不得阻塞命令处理；视频码率上限存在的目的就是保证命令小包不被挤掉。
6. **断链即停（第二层，与 300 ms 看门狗并存，不合并）**：WiFi STA 掉线或 TCP 回程断开，任一发生即调用统一停车。

| 优先级 | 通道 | 被谁抢占 | 抢占动作 |
| --- | --- | --- | --- |
| 1 | 移动 / 云台命令（UDP 8081） | 无人可抢 | 语音期间视频降帧；运动靠 300 ms 自停 + 断链即停兜底 |
| 2 | 语音（UDP 8888） | 命令突发（小包，瞬时） | 视频降 5 fps / 暂停；日志降级 |
| 3 | 数据 / 日志 / 遥测（TCP 8080） | 语音、命令 | 合批、可丢、让出空档 |
| 4 | 视频（WS 81） | 语音、命令 | 降帧率 → 降分辨率/质量 → 暂停 |
| 5 | AI 问答 | 以上全部 | 总开关关闭即停采集、丢音频、唤醒词失效 |

## 6. 通信流：三个典型场景

### 6.1 WiFi 换网配置（江灵初始化）

```
上电即用常量凭据作 STA 连手机热点（jianglingAPP / 31957172yz），App 与板子连同一热点
   │
手机开热点、App 与双板都连上后：
手机 →（UDP 8081）→ CMD_WIFI_MODE(0xC4, 0=STA) → ACK（TCP 8080）
     → CMD_WIFI_STA_CONFIG(0xC5, [ssidLen][SSID][密码]) → ACK
     → CMD_INIT_COMMIT(0xC8, [mode][0]) → ACK 0（已受理，改用新凭据重连）
     → 主板只存 RAM → 串口 0xF0 把 SSID/密码下发给副板 → 等副板 0xF2
     → 双板各自按 STA 并行连接（≤20 s）
     → 副板拿到 IP 与视频端口 → 串口 0xF4 上报主板
     → 主板拿到 IP → 主动发 ACK(0xC8, 3) = **初始化完成**，流程结束
     → 运行期：手机向主板 8081 发命令（UDP）、向 8080 收回程（TCP）；IP 由 0x87 的 ipv4 上报
     → 视频用 0x88 的端点另连（不进 V21）
     → 后续控制 / 遥测 / AI 全走 WiFi；副板只执行转发命令并推视频
     → 连不上：30 s 退避重连，连续 3 次失败 → 起兜底 AP（jianglingAPP @ 192.168.4.1）重新配网
     → 要立刻回 AP：在当前网络里下发 0xC4(1) + 0xC8(1)
```

关键点：

- **上电即 STA**：`setup()` 用 `m.h` 的 `WIFI_DEFAULT_STA_SSID` / `WIFI_DEFAULT_STA_PASSWORD` 直接连手机热点，App 与板子在同一热点即可配网；**AP 只在连不上（连续 3 次退避）或 App 要求换网时短时开启，配完立即回 STA**（§2.2）。
- **主板是本次运行凭据的唯一权威（RAM）**，副板没有独立配网入口，凭据只能经串口 `0xF0` 下发（§3.6.10）。
- **App 不扫描周边 WiFi**：用户在 App 手填 SSID/密码，App 只负责 `0xC5` 原样下发，不做「扫描 → 选中 → 代连」的动作（§2.4）。
- **退避重连、超阈值才兜底**：STA 失败每 30 s 重试并记 `0x60/0x25`；**连续 3 次（≈2 min）仍失败才起兜底 AP**；AP 期后台继续重连，成功即关 AP；配网期间回 `ACK 5` 让 App 改参数。
- **凭据不落盘**：`0xC5` 只写 RAM，断电即忘；常量默认凭据是只读编译期值，不算网络记忆，重启仍连 `jianglingAPP`。
- 副板是否就绪由 `0x87.peerStage` / `flags.bit1` 单独表达（运行期经 WiFi 上报），**不影响主板的「初始化完成」回执**：控制可用即算成功，视频缺失只降级。

**唯一路径**（详见 §3.6.8）：

| 车端状态 | 路径 | App 动作 |
| --- | --- | --- |
| 上电 | `S0` 用常量凭据起 STA 连 `jianglingAPP`（连不上走 `S7`） | 让手机开热点，App 连同一热点 |
| 换网 | `S4` 收参数 → `S5` 提交 → `S6` 主动发 `ACK(0xC8,3)` | 经 UDP 8081 发 `0xC4`/`0xC5` → `0xC8`，收到 3 即结束 |
| 失败（`ACK 5`） | `S7` 30 s 退避重连；连续 3 次起兜底 AP | 改参数重提 `0xC8`，或连 `192.168.4.1` 重新配网 |
| 回 AP | `S5` 按 `mode=1` 起兜底 AP | 连回 `jianglingAPP` @ `192.168.4.1` 后重新配网 |

失败（ACK `5`）时链路保持，App 可改参数重提；恢复出厂用 `CMD_INIT_FACTORY_RESET(0xCA)`。

### 6.2 联网后 AI 对话

```
总开关三条同时成立（有外网 + 手机语音未开 + AI 模块正常，§4.6）
  → 本地唤醒词命中（二层开关开）→ 开 AI 会话（OTA + WSS 小智云）
  → 上行：麦克风 PCM16 16 kHz / 16 bit / 单声道，20 ms 一块
  → 云端 ASR → LLM → TTS
  → 下行：语音（20 ms/块）+ 同源文字（按句）
  → 车端边收边播、文字上屏；本地判定「播报完成」→ 起算 30 s
  → 期间 ctrl 的 DAT/LOG/视频照常，但优先级低于 AI 消息，不得抢占 AI 的带宽
  → 30 s 内无新一问 → 二层开关关，回到待唤醒
  → 期间若外网丢失 / 手机语音开启 → 总开关关，立即收敛（§4.6.4）
```

关键点：AI 与 ctrl 并行，靠优先级而不是靠关闭某一路来避让；AI 能否运行只看 §4.6 的两级开关。

### 6.3 手机语音通话

```
手机发起语音（独立 UDP 8888，不走 V21、不占 TYPE/SEQ，见 语音.md）→ 车端接受并**抢占通道**（优先级 1）
  → 上行：手机麦克风 → WiFi 近程 → 车端 Speaker
  → 下行：车端麦克风 16 kHz 单声道 → WiFi 近程 → 手机播放
  → 期间 AI 下行暂停/降级，DAT/LOG/视频让路（只在整帧边界切换）
  → 挂断 → 通道释放 → AI 与普通数据恢复原优先级
```

关键点：这一段只定义「谁让路」，不定义具体消息；音频帧定义、抖动缓冲与端口由 `语音.md` 负责。固件侧已实现，App 侧待接。

## 7. 协议帧：逐段说明、属性表与长度校验

> 本节是五份文档的公共底座。命令、回复、日志、数据四个分册只列各自的 TYPE 与 PAYLOAD 语义，帧结构统一以本节为准。

### 7.1 帧结构（含 LEN）

| 偏移 | 字段 | 长度 | 说明 |
| --- | --- | --- | --- |
| 0 | `AA` | 1 B | 帧同步头 |
| 1 | `SEQ` | 1 B | 帧序号 |
| 2 | `TYPE` | 1 B | 帧类型 |
| 3 | `LEN` | 1 B | PAYLOAD 字节数（不含 LEN 自身、不含 CRC） |
| 4 起 | `PAYLOAD` | LEN B | 负载，长度由 LEN 给出 |
| 4+LEN | `CRC8` | 1 B | 帧校验 |

- 帧总长 = **5 + LEN**。
- 接收端先收满 4 B 读出 `TYPE/LEN`，再按 `5 + LEN` 定界；收满即为一帧，不再靠「半帧超时」猜边界（超时只用于丢弃残帧）。
- `LEN` 为 1 B，上限 255；收发缓冲按最大帧 260 B 开，超出或与 TYPE 允许范围不符的帧整帧丢弃并记错误日志。
- 当前已定义帧最长 101 B（`CMD_WIFI_STA_CONFIG`，LEN=96）；常规 DAT 帧 ≤25 B，`DAT_INFO_VERSION` 为 24 B。

### 7.2 逐字段属性表

| 字段 | 含义 | 类型 | 长度 | 取值范围 / 枚举 | 字节序 |
| --- | --- | --- | --- | --- | --- |
| `AA` | 帧同步头 | 常量 | 1 B | 固定 `0xAA` | — |
| `SEQ` | 帧序号 | u8 | 1 B | `0x00`~`0xFF` | — |
| `TYPE` | 帧类型 | u8 | 1 B | `0x00`~`0xFF`，见 7.3 | — |
| `LEN` | PAYLOAD 长度 | u8 | 1 B | `0`~`255`；已定义 TYPE 的实际范围见 7.4 | — |
| `PAYLOAD` | 负载 | 字节数组 | LEN B | 已定义 TYPE 为 0~96 B | 多字节字段**大端** |
| `CRC8` | 帧校验 | u8 | 1 B | `0x00`~`0xFF` | — |

**SEQ 的归属**（不同方向不共用计数器）：

| 帧类 | SEQ 来源 | 规则 |
| --- | --- | --- |
| App→车 `CMD` | App 全局计数器 | 单通道一套；`0` 为免去重（当前用于 `CMD_SESSION_INIT`），其余从 `1` 起 |
| 车→App `ACK` | 回显 | 原样复制被应答 CMD 的 SEQ |
| 车→App `LOG` | 车端独立计数器 | 每发一帧 +1；一帧最多 8 条记录共用同一个 SEQ；首帧可为 `0` |
| 车→App `DAT` | 车端独立计数器 | 与 LOG **不共用**；首帧可为 `0` |

> `SEQ=0 免去重` 只是 **App→车 CMD** 的约定；车端 LOG/DAT 的 `0` 是普通序号，不触发 App 的握手逻辑。

**CRC8 校验**

| 项 | 值 |
| --- | --- |
| 算法 | CRC-8/ATM |
| 多项式 | `0x07`（x⁸ + x² + x + 1） |
| 初值 / 结果异或 | `0x00` / `0x00` |
| 输入/输出反射 | 否 / 否 |
| 覆盖范围 | 从 `AA`（偏移 0）到最后一个 PAYLOAD 字节，**含 LEN**；不含 CRC 自身 |
| 覆盖长度 | `4 + LEN` 字节（HEAD/SEQ/TYPE/LEN + PAYLOAD） |
| 校验失败 | 丢弃当前帧，从下一个字节重新找 `AA`（不额外回 ACK） |

### 7.3 TYPE 是平铺的 64 个类型

TYPE 是完整 1 B。低 6 位是**平铺的 64 个类型序号**，本文与四个分册全部按整字节列出；「分区」等中文分类只是文档阅读用的分组，不是位域。App 与固件都按整字节 TYPE 查表，不做位切分。

唯一真实存在的位含义是**高 2 位 KIND（方向）**；位运算只用于方向校验（`type >> 6`）与 LOG 帧识别。

**KIND（bit7~6）**

| 值 | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| 0 | `ACK` | 车→App | 命令回复 |
| 1 | `LOG` | 车→App | 日志帧（容器 TYPE 固定 `0x42`，记录 TYPE 在 PAYLOAD 内） |
| 2 | `DAT` | 车→App | 数据上报 |
| 3 | `CMD` | App→车 | 命令 |

> 各 TYPE 的整字节取值、长度与中文阅读分类见四个分册；`Protocol.h` 生成编号时使用的参数不进入解析。LOG 帧的容器 TYPE 恒为 `0x42`。

**ACK 状态码**（PAYLOAD 内的值，不是 TYPE）

| 值 | 名称 | 含义 |
| --- | --- | --- |
| 0 | `ACK_ST_RECEIVED` | 已收到、执行中 |
| 1 | `ACK_ST_YES` | 查询结果为真 |
| 2 | `ACK_ST_NO` | 查询结果为假 |
| 3 | `ACK_ST_DONE` | 执行完成（重复 CMD 也回这个） |
| 4 | `ACK_ST_UNKNOWN` | 未实现 / 未知请求 |
| 5 | `ACK_ST_ERROR` | 参数或状态非法（含凭据格式非法、本次运行无法应用） |
| 6 | `ACK_ST_CANNOT` | 当前状态不允许 |

### 7.5 为什么加 LEN / 加新 TYPE 要改哪里

**为什么加 LEN**

- WiFi 凭据（SSID 1~32 B + 密码 0~63 B）无法用固定长度表达；有 LEN 就不必补 `0x00` 到 96 B；
- 接收端按 `5 + LEN` 精确分帧，不必为「半帧」维护超时猜测；
- TYPE 与长度解耦，未来可变长字段（如更长文本）不再需要拆多个 TYPE；
- 代价是每帧多 1 B，且这是一次**不兼容变更**，协议版本从 `20` 升到 `21`，旧版本客户端在握手时被拒绝。

**新增一个 TYPE 的改动清单**

1. `Protocol.h`：新增 TYPE 常量（直接写十六进制整字节值），确认取值未被占用；
2. `payloadLengthValid(type, len)`：加该 TYPE 允许的 LEN 范围（漏加 = 永远非法、整帧被丢）；
3. `static_assert`：锁 TYPE 取值与关键 LEN 边界；
4. 组帧类（`Cmd`/`Dat`/`Log`）无需改帧长逻辑，帧长自动等于 `5 + LEN`；
5. App 侧同步 TYPE 与 LEN 校验（App 是独立副本，不会自动跟随）；
6. 文档：总览 7.4 表 + 对应分册 + 变更记录；
7. 两端联调：先确认方向校验（KIND）、LEN 定界与 CRC，再看业务字段。

> **执行顺序（文档先行）**：先做第 6 步（文档定稿：本表 7.4 + 对应分册 + 变更记录，设计依据写进 `操控.md` / `语音.md`），再动第 1~5 步（`Protocol.h`、校验表、组帧类、App）。文档未定稿的 TYPE / LEN / ACK 口径不得先进代码。

### 7.6 已废弃：BLE 与 WiFi 的双链路对照

> **2026-11-11 作废**：蓝牙整体移除后，江灵只剩 WiFi 一条链路，「同一条命令走 BLE / WiFi 有什么不同」不再成立。原对照表（20 B 分片、MTU 23、512 B 接收缓冲、BLE 断连重播等）删除，追溯请看 git 历史。
>
> **现行口径**：命令 **UDP 8081 一包一帧**（`5 + LEN` 不等于报文长度即整包丢弃，不跨包拼接）；回程 **TCP 8080 流式重组**，320 B 缓冲、半帧 100 ms 超时兜底；断线按 5/10/20/30 s 退避重连，重连后重新 `CMD_SESSION_INIT`。

## 9. 协议共性速查

| 项 | 值 |
| --- | --- |
| 帧头 | `0xAA`，1 B |
| 帧结构 | `AA | SEQ | TYPE | LEN | PAYLOAD | CRC8`，帧总长 = `5 + LEN` |
| 单帧上限 | LEN ≤255（1 B）；已定义最长 101 B（`CMD_WIFI_STA_CONFIG`，LEN=96） |
| LEN | = PAYLOAD 字节数，不含 LEN 自身、不含 CRC；收满 `5 + LEN` 即为一帧 |
| CRC | CRC-8/ATM（`0x07`，初值 `0x00`），覆盖 `AA` 到最后一个 PAYLOAD 字节（含 LEN） |
| TYPE | 1 B；低 6 位为平铺的 64 个类型序号，高 2 位 KIND 只表示方向 |
| KIND | `00`=ACK、`01`=LOG、`10`=DAT、`11`=CMD |
| LOG | 容器 TYPE 固定 `0x42`；`AA | SEQ | 0x42 | LEN | 每条 [TYPE,LEN=1,param] | CRC8`；一帧最多 8 条，LEN=3×条数 |
| 协议版本 | `21`（`CMD_SESSION_INIT` 的 PAYLOAD；旧版本 20 在握手时被拒绝） |
| 优先级 | 移动/云台命令（UDP 8081） > 手机语音（UDP 8888） > 数据/日志/遥测（TCP 8080） > 视频 > AI |
| 未知 TYPE | 整帧丢弃，逐字节重扫 `0xAA`，**不回任何帧** |
| 板间帧（UART） | 骨架同上，TYPE 用私有段 `0xF0`~`0xF6`、独立请求序号；只传凭据 / 命令 / 结果 / 心跳，不传图像（§3.6.3） |
| 拍照 | `0xCC` 下发、`0x00` 受理、`0x02` 终态（带副板 IP / 端口 / 图 ID）；照片走副板 HTTP 8090 直连 |
| 未登记 CMD | 车端**静默丢弃**，不回 ACK；App 4 s 超时判失败 |
| 队列满提示 | LOG 队列满与 DAT 队列满都发 `0x62 / param=0x01`，**App 无法区分来源** |

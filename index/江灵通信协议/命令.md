# 江灵通信协议 · 命令（CMD）

> 本文件只写 CMD（App → 车）。TYPE 与长度取自固件 `Protocol.h`。
> 这 64 个类型是**平铺**的：低 6 位就是类型序号，表里的「分区」只是文档阅读用的中文分类，不是位域，App 与固件都按整字节 TYPE 查表。唯一真实存在的位含义是高 2 位 KIND 表示方向（本表全部为 CMD）。
> 帧格式：`AA | SEQ | TYPE | LEN | PAYLOAD | CRC8`，帧总长 `5 + LEN`；LEN 由 App 按本条 PAYLOAD 实际长度填写，车端用 `payloadLengthValid()` 校验「TYPE 允许的 LEN」，不符或未知 TYPE 整帧丢弃。SEQ 由 App 全局计数器分配，`0` 仅用于免去重命令（当前 `CMD_SESSION_INIT`）。

**传输通道（定稿 2026-11-11 第三版：只有 WiFi 一条通道，蓝牙整体取消）**

| 项 | 规定 |
| --- | --- |
| 运行通道 | App → 主板 **UDP 8081**；**一包一帧**，一个数据报只放一个完整 V21 帧；报文长度 ≠ `5 + LEN` 时整包丢弃，**不跨包拼接** |
| 为什么 UDP | 避免 TCP 队头阻塞导致操控一顿一顿；丢帧不补，下一帧（约 200 ms 后）自然接上 |
| 初始化通道 | **同样是 UDP 8081**：`0xC4` / `0xC5` / `0xC6` / `0xC8` / `0xC9` / `0xCA` 与运行期命令走同一条通道、同一套帧格式，**没有第二条通道** |
| 上电默认 | 板子用编译期常量作 **STA** 连手机热点 `jianglingAPP` / `31957172yz`；App 与板子连同一热点即可下发命令、完成换网。**AP 仅兜底**：连续 3 次退避重连失败后才短时起（固定 `192.168.4.1`），配完立即回 STA |
| 回程 | ACK / LOG / DAT 走 **TCP 8080**（主板 → App）；**所有 ACK 都从这里回**，不走 UDP |
| 自停看门狗 | 以「**收到 WiFi 命令**」为唯一刷新条件：UDP 8081 有帧即刷新计时，300 ms 无新命令即停 |
| 断链即停 | WiFi 断开（STA 掉线 / TCP 8080 断开）即**立即主动停车**；与 300 ms 看门狗是两层，不合并 |
| 端口占用 | 命令 UDP **8081**、回程 TCP **8080**、语音 UDP **8888**、副板视频 WS **81**、副板取图 HTTP **8090**。其中 **8888 / 81 / 8090 不承载 V21 帧**（语音、视频、取图各有自己的板块与帧口径） |

> **表内命令的通道归属**：本表全部 TYPE（含初始化命令 `0xC4`~`0xCA`）**只经 WiFi UDP 8081** 下发，回程统一走 TCP 8080；不存在「某条命令只允许某个通道发」的划分。已废弃的 `0xCB` 见下表该行。

| `0xCA` | `CMD_INIT_FACTORY_RESET` | 系统 | `001010` | 清空本次运行的配网数据 | `LEN=1` — `[0] magic` u8，固定 `0x5A`，不符回 `5` | 经 **UDP 8081** 下发返回 ACK。清空 RAM 中的 `wifiMode`/`staSsid`/`staPass`/`apSsid`/`apPass`（**无 NVS 可清**）；回 ACK `3` 后重启；重启后回到**常量网络**（STA 自动连 `jianglingAPP` / `31957172yz`），与刚上电一致；`magic` 不符回 `5`。**要「回 AP 但不清凭据」用 `0xC4(1)` + `0xC8(1)`，不需要 `0xCA`** |

| `0xD1` | `CMD_VOLUME` | 音频 | `010001` | 设置音量 | `1B` — `volume` u8：0 静音 ~ 100 满量程 | ACK 1/3；响度由功放 GAIN 决定，100 不代表固定分贝 |

- **两套计时，互不干扰**：离散运动命令（`0xE1`~`0xE4`）仍是 1 s 无新命令自停；流式命令 `0xEB` / `0xEC` 各自独立计时，**300 ms** 无新帧即停（见 `操控.md` §4.3）。两套计时器不共用，也不互相刷新。`0xE0` 停止命令对两者都立即生效。
- 有参数的命令即使值是 0 也必须显式发 `0x00`；`0xEB` / `0xEC` 的 `0/0` 等价于「停」，但正常松手仍应发 `0xE0`。
- 未登记 TYPE 静默丢弃、不回 ACK；App 以超时兜底（4 s），不自动重发。
- WiFi 配置流程（**全程走 UDP 8081**）：App 与板子连同一网络（手机热点 / 路由器）后，`CMD_WIFI_MODE(0xC4)` 选模式 → `CMD_WIFI_STA_CONFIG(0xC5)` / `CMD_WIFI_AP_CONFIG(0xC6)` 下发凭据 → `CMD_INIT_COMMIT(0xC8)` 应用并换网 → 收到 `[0xC8][3]` 即完成，无后续收尾命令。模式与凭据**只存 RAM，掉电即忘，不写 NVS**；**上电默认以常量凭据作 STA 连手机热点**（`jianglingAPP` / `31957172yz`），**AP 仅在退避重连连续 3 次失败或显式 `0xC4(1)`+`0xC8` 时兜底**（`总览.md` §2.2、§2.5）。初始化命令与运行期命令共用同一条 UDP 8081，但 `0xC8` / `0xC9` / `0xCA` **不参与运行期 CMD 去重**；`0xCB` 已废弃，收到回 `4`。
- **换网回 AP**：板子当前在 STA 时，App 在同一个网络里下发 `CMD_WIFI_MODE(0xC4, [1])` + `CMD_INIT_COMMIT(0xC8, [1][0])`，板子离开 STA、重新起 `jianglingAPP` / `192.168.4.1`，App 连回热点后重新配网。**现有 TYPE 已能完整表达，不新增命令字**；`0xC6`（AP 凭据）可选，不下发则沿用默认 `jianglingAPP` / `31957172yz`。
- **配网职责（定稿 2026-11-11）**：App **不扫描周边 WiFi**，只把用户手填的 SSID/密码经 `0xC5` 原样下发；STA 连不上时先**每 30 s 退避重连**，**连续 3 次（≈2 min）仍失败才由板端起兜底 AP**（`jianglingAPP` @ `192.168.4.1`），App 可改参数重提，或显式 `0xC4(1)` + `0xC8(1)` 立即回 AP。完整分工见 `总览.md` §2.4 与 §3.6.8。
- 唤醒词的配置命令仍未定 TYPE，不列入本表。
- **AI 两级开关没有独立 CMD**：总开关（有外网 + 手机语音未开启 + AI 模块正常）与二层开关（唤醒词）都由设备自行判定，App **只能读不能写**，状态看 `0x87.flags.bit4`（总开关）/ `bit5`（二层开关），口径见 `总览.md` §4.6。不要为「打开 AI」新增命令。

**差速轮盘：`0xEB` / `0xEC` 的帧格式、字段与责任边界（定稿 2026-11-11）**

App 侧操控从「离散四方向」改为**虚拟轮盘八方位**，车端模型从麦轮 `vx/vy` 改为**差速两分量**。本节是 App 与固件共同的实现口径，设计推导见 `操控.md`。

1）帧格式（与全部 V21 帧一致，无私有变体）

| 字段 | 长度 | `0xEB` 移动 | `0xEC` 云台 |
| --- | --- | --- | --- |
| `HEAD` | 1 B | 固定 `0xAA` | 固定 `0xAA` |
| `SEQ` | 1 B | App 全局计数器，1~255 循环；`0` 仅用于 `0xC0` | 同左（**与移动共用同一个计数器**） |
| `TYPE` | 1 B | `0xEB` | `0xEC` |
| `LEN` | 1 B | 固定 `2` | 固定 `2` |
| `PAYLOAD[0]` | 1 B | `drive` int8 | `pan` int8 |
| `PAYLOAD[1]` | 1 B | `turn` int8 | `tilt` int8 |
| `CRC8` | 1 B | CRC-8/ATM(`0x07`)，覆盖 `HEAD` 到最后一个 PAYLOAD 字节 | 同左 |
| 帧总长 | — | **7 B**（`5 + LEN`） | **7 B** |

2）取值范围与符号（两端同一套定义）

| 量 | 类型 | 范围 | 正值方向 | 负值方向 | `0` |
| --- | --- | --- | --- | --- | --- |
| `drive` | int8 | `-100`~`+100` | 前进（车头方向） | 后退 | 不产生前后分量 |
| `turn` | int8 | `-100`~`+100` | **左转**（俯视逆时针） | 右转（俯视顺时针） | 不产生转向分量 |
| `pan` | int8 | `-100`~`+100` | 云台向右（俯视顺时针） | 云台向左 | 水平不转 |
| `tilt` | int8 | `-100`~`+100` | 云台向上 | 云台向下 | 俯仰不转 |

- 单位统一为**最大量的百分比**：`±100` = 满量程，`±50` = 一半。移动的 `100` 对应最大轮速 5.00 r/s（`MAX_WHEEL_RPS_HUNDREDTHS = 500`，【代码】）；云台的 `100` 对应该轴最大角速度（软件限幅 90°/s，【设计】）。
- int8 的传输码就是补码原字节（`-100` = `0x9C`、`-1` = `0xFF`、`+100` = `0x64`）。

3）合成关系（**只有这一套公式**）

```
左轮百分比 = clamp(drive − turn, −100, +100)
右轮百分比 = clamp(drive + turn, −100, +100)
```

- 轮速百分比 → `0.01 r/s`：`rps = 百分比 × 500 ÷ 100`；→ PWM：`pwm = 百分比 × 255 ÷ 100`（沿用【代码】既有换算）。
- 例：`drive=+100, turn=0` → 左右各 +100（直行）；`drive=+100, turn=+100` → 左 0、右 +200→夹到 +100（左转弧线）；`drive=0, turn=+100` → 左 −100、右 +100（**原地左转**）。
- 越界不报错：先按上式合成，再各自夹到 `±100`（`drive`/`turn` 本身越界同样夹取），保证推送流不中断。

4）八方位映射（App 端对照表，`L`/`T` 为档位幅度）

| 方位 | `drive` | `turn` | 同步下发？ |
| --- | --- | --- | --- |
| 正前 | `+L` | `0` | 是 |
| 左前 | `+L` | `+T` | 是 |
| 右前 | `+L` | `−T` | 是 |
| 正后 | `−L` | `0` | 是 |
| 左后 | `−L` | `−T` | 是（后退 + 顺时针转，车尾向屏幕左下） |
| 右后 | `−L` | `+T` | 是（后退 + 逆时针转，车尾向屏幕右下） |
| **正左** | — | — | **否**：差速车无法横移，App 在构造帧前拦截，不下发 |
| **正右** | — | — | **否**，同上 |

- 「正左 / 正右」被拦截的判定发生在 **App 构造帧之前**（`操控.md` §9.3），车端不会收到这两格的帧，也就不需要任何降级逻辑。
- 原地转向不在八方位轮盘里，但协议本身允许 `drive=0, turn≠0`；App 若提供独立转向按钮，直接发这一对值即可，**不需要新增 TYPE**。

5）下发节奏与停止语义

| 项 | 约定 |
| --- | --- |
| 按住期间 | **约 200 ms 一帧**持续下发（5 Hz），值不变也照发——车端靠「有新帧」续命，App 不做变化检测 |
| 松手 | **立即停止下发**，**不补发最后一帧、不补发零向量** |
| 最后一帧 | 就是松手前那一帧，车端按超时自行停止；App 不需要、也不应该额外发一帧 `0/0` |
| 正常停车 | 用户按「停止」按钮 → `0xE0 CMD_STOP`，优先级最高，见下 |
| 时效约定 | App **只保证把帧发出去**（写进 UDP 8081 即算完成），**不负责**超时判定；超时自停是车端责任 |

**停止命令覆盖（`0xE0`）**

- `0xE0` 优先级最高：主板收到即清空移动目标、清零 PWM、**清掉 `0xEB` 的计时**，并同样清掉 `0xEC` 的计时，不等任何超时。
- 覆盖范围：正在执行的 `0xEB` 移动、`0xEC` 云台转动、以及旧离散运动命令，一律立即停止。
- `0xE0` 之后再收到的 `0xEB` 帧才会重新起步；`0xE0` 与 `0xEB` 不做「后到者赢」之外的任何仲裁。

6）双方校验规则（App 与车端各自负责什么）

| 环节 | App 侧（发送前） | 车端（接收时） |
| --- | --- | --- |
| TYPE | 只发本表登记的 TYPE；`0xEB`/`0xEC` 必须已随协议版本 21 一起发布 | 未登记 TYPE 整帧丢弃、不回 ACK（`payloadLengthValid()` 返回 false） |
| LEN | 按上表填写，固定 `2`；不得省略 `0` 值字节 | `LEN≠2` 整帧丢弃并重扫 `0xAA`，不回 ACK |
| CRC | 用同一份 CRC-8/ATM 组帧 | CRC 不符整帧丢弃，不回 ACK |
| 取值 | 保证在 `-100`~`+100`；轮盘归一化 + 死区在 App 内完成 | 越界**夹取不报错**（流式命令不回 ERROR，避免 5 Hz 抖动） |
| 方向 | — | `KIND_CMD(3)` 之外的方向一律丢弃 |
| 方位合法性 | **正左/正右不下发**（`操控.md` §9.3） | 不判断方位，只认两个分量 |
| ACK | 每条命令都有 ACK，App 必须读走，但**不逐帧对账** | 每帧回 `ACK_RESULT`：`status=0`（已受理）或 `3`（`0/0` 等价停车） |

7）云台与移动的独立性

- 两个 TYPE 各有独立的**目标值、计时器、超时判定**；`0xEC` 不会刷新 `0xEB` 的计时，反之亦然。
- 可以同时发：一边前进一边转云台是合法组合，互不覆盖。
- 云台超时只停转、**不回中**（保持当前角度）；回中由 App 发 `0xE5`/`0xE6` 的绝对角度或后续单独定义。
- 云台位置型命令 `0xE5`/`0xE6` 继续有效：它们是**绝对角度**，与 `0xEC` 的**角速度分量**并存；同一条链路里先到先执行，后到的覆盖目标。

**命令执行位置**

- **只有一条 V21 会话，只有一条 WiFi 通道**：所有 CMD（含初始化命令 `0xC4`~`0xCA`）都由主板经 **UDP 8081** 接收、解析，运行期命令按 SEQ 去重（`0xC8`~`0xCA` 不参与去重），SEQ 全局唯一；回程 ACK 统一走 TCP 8080。
- 执行位置总表见 `总览.md` §3.6.4（主板本地 / 转发副板 / 双端执行）。本表里**只有 `0xCC` 转发副板**；`0xE0` 急停是双端执行；云台 `0xE5`/`0xE6`/`0xEC` 当前**归主板**（舵机接在主板），硬件变更后再评估。`0xEB`、`0xEC` 都是**主板本地执行**，不走串口。
- 转发命令的 ACK 由主板按副板回执统一组帧，副板**从不直接对 App 说话**（`回复.md` §1.6）。

**江灵初始化的命令时序（`0xC4`~`0xCA`，全程 WiFi 单通道）**

```
上电：用常量凭据作 STA 连手机热点 jianglingAPP / 31957172yz
   │  （连不上：30 s 退避，连续 3 次失败才起兜底 AP @ 192.168.4.1）
   │
手机开热点、App 与板子连同一网络 → 直接经 UDP 8081 下发（回程 ACK 走 TCP 8080）
   │
   ├─ CMD_SESSION_INIT(0xC0, [21])         → ACK 建立会话（SEQ=0）
   ├─ CMD_WIFI_MODE(0xC4, [0])             → ACK 3   选 STA（仅本次运行）
   ├─ CMD_WIFI_STA_CONFIG(0xC5, …)         → ACK 3   下发热点/路由器凭据（只存 RAM，WiFi 仍跑旧网络）
   ├─ CMD_WIFI_AP_CONFIG(0xC6, …)          → ACK 3   可选，仅 AP/APSTA 用
   └─ CMD_INIT_COMMIT(0xC8, [mode][0])
                                           → ACK 0   已受理，离开当前网络
                                           → [内部] 串口 0xF0 下发副板凭据 → 等 0xF2
                                           → [内部] mode=0 切 STA / mode=1 起兜底 AP
                                           → ACK 3   ★ 初始化完成（PAYLOAD = [0xC8][3]）
                                           → 5       20 s 未就绪，连接保持，可重试；连续 3 次失败自动起兜底 AP
   │
可选：CMD_INIT_STATUS(0xC9, LEN=0)         → ACK 0/3/4   补查一次，不做轮询
       CMD_INIT_FACTORY_RESET(0xCA, [0x5A]) → ACK 3 后重启，回到常量网络（自动连 jianglingAPP）
换网回 AP：CMD_WIFI_MODE(0xC4, [1]) + CMD_INIT_COMMIT(0xC8, [1][0]) → 板子起兜底 AP @ 192.168.4.1
运行期：只有 WiFi（命令 UDP 8081 / 回程 TCP 8080 / 语音 8888 / 副板视频 81）
```

- **初始化与运行期同一条通道**：`0xC4`~`0xCA` 与运行期命令都走 UDP 8081、同一套 `AA|SEQ|TYPE|LEN|PAYLOAD|CRC8` 帧格式，ACK 统一从 TCP 8080 回；**没有第二条通道，也没有「某条命令只允许某通道发」的限制**。`0xCB` 已废弃，收到回 `ACK_RESULT` `4`，不执行任何动作。
- **初始化完成 = `ACK_RESULT` `PAYLOAD=[0xC8][3]`**，由板子在新网络就绪后**主动**发出，不需要 App 轮询；`CMD_INIT_STATUS(0xC9)` 只是补查手段。
- `0xC8` 的 `mode` 与已下发的 `0xC4` 必须一致；不一致时以 `0xC8` 为准（只改 RAM）。
- `0xC8` 成功的前提包含**副板应答**（`0xF2 status=3`）：副板无法应用凭据则整次提交回 `5`。**当前固件未实现主板↔副板串口（`0xF0`/`0xF1`/`0xF2`）**，`0xC8` 只处理主板自身网络；副板链路接入后按本口径补齐转发与等待。
- `0xC9` 只读：任意时刻可发，只回 ACK（`3` 已完成 / `0` 已提交未就绪 / `4` 未提交），不改状态、不触发断链、不启停 WiFi。
- `0xCA` 是「清空本次运行」：清掉 RAM 中的凭据后重启；重启后回到**常量网络**（STA 自动连 `jianglingAPP` / `31957172yz`），等于回到刚上电的状态；`magic=0x5A` 用来防误触。副板的凭据副本**不单独清除**，下次由 `0xF0` 覆盖。**只回 AP、要保留已下发凭据时用 `0xC4(1)` + `0xC8(1)`，不重启。**

**拍照命令的时序与结果语义（`0xCC` / `0xCD` / `0x02`）**

```
App → 主板     CMD_PHOTO_CAPTURE(0xCC, LEN=0)
主板           ├ 副板离线？ → 0x02 ACK_PHOTO(status=5, err=8)（≤10 ms，不发串口，不回 0）
               └ 副板在线 → ACK_RESULT(0x00, [0xCC][0])          ① 受理（App 显示「拍摄中」）
主板 → 副板    0xF1(seq=k, [0xCC])                                ② 下发快门
副板           ├ 暂停视频推流 → UXGA 抓拍 → JPEG 编码 → 存本板 PSRAM
               ├ 分配 photoId（u32 递增）
               └ 0xF2(seq=k, [0xCC][3|5] + err/photoId/bytes/w/h/ms)  ③ 结果回主板
主板           ├ 缓存最近一次结果（photoId / 尺寸 / 字节数 / 耗时 / 副板 IP 与端口）
               └ 0x02 ACK_PHOTO(status, err, …)                     ④ 终态（App 拿到才能取图）
App            GET http://<副板IP>:<端口>/photo/<photoId>             ⑤ 直连取图
```

**`ACK_RESULT(0x00)` 与 `0x02 ACK_PHOTO` 的分工（固定两段）**

| 段 | 帧 | 触发点 | 含义 | App 显示 |
| --- | --- | --- | --- | --- |
| 第 1 段 | `ACK_RESULT(0x00)` `[0xCC][0]` | 主板**已完成协议校验并已把 `0xF1` 写进串口** | 已受理。**不代表拍摄成功** | 「拍摄中」 |
| 第 2 段 | `0x02 ACK_PHOTO`（终态） | 副板结果已回主板，或判定失败 | `status=3` 图已存在可取；`status=5` 拍摄失败（看 `err`） | 成功图 / 失败原因 |

- 第 2 段是**唯一终态**。App 只有收到 `0x02` 才能认为图存在；8 s 内只收到第 1 段则按超时处理。
- 副板离线时**只发** `0x02(status=5, err=8)`，**不回**第 1 段（避免「已受理」误导）。
- 两段同一 `SEQ`；`0x02` 的 `cmdType` 固定 `0xCC`，与 `ACK_RESULT` 的对账条件一致（`SEQ + cmdType`）。

**`0x02 ACK_PHOTO` 字段（LEN=23，帧长 28 B）**

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| `[0]` | 1 B | `cmdType` | 固定 `0xCC` |
| `[1]` | 1 B | `status` | `3` 成功（图已存在）；`5` 失败；`6` 上一张未完成（当前不允许） |
| `[2]` | 1 B | `err` | 错误码，见下表；成功时 `0` |
| `[3~6]` | 4 B | `photoId` | u32 大端；失败时 `0` |
| `[7~10]` | 4 B | `bytes` | JPEG 字节数；失败时 `0` |
| `[11~12]` | 2 B | `width` | 像素宽；失败时 `0` |
| `[13~14]` | 2 B | `height` | 像素高；失败时 `0` |
| `[15~16]` | 2 B | `captureMs` | 副板拍摄 + JPEG 编码耗时（ms），上限 65535 |
| `[17~20]` | 4 B | `ipv4` | 副板 IP（主板由 `0xF4` 缓存）；失败或无地址时 `0` |
| `[21~22]` | 2 B | `port` | 副板取图端口（默认 **8090**）；失败时 `0` |

**错误码 `err`**

| err | 名称 | 产生方 | App 该怎么做 |
| --- | --- | --- | --- |
| `0` | 无 | — | 正常取图 |
| `1` | 对焦失败 | 副板 | 可重试 1 次（对准光源/目标） |
| `2` | 内存不足 | 副板 | 提示清理并重试；连续出现需降分辨率（待定） |
| `3` | JPEG 编码失败 | 副板 | 重试 1 次 |
| `4` | 副板忙（上一张未完成 / 视频切换中） | 副板 | 500 ms 后重试一次 |
| `5` | 摄像头未就绪 | 副板 | 等视频源上线后重试 |
| `6` | **图 ID 已失效** | 主板（`0xCD` 查询时判定） | 用 `/photo/latest` 重取，或重拍 |
| `7` | **串口超时**（副板未在 2 s 内回结果） | 主板 | 重试 1 次 |
| `8` | **副板离线**（600 ms 无心跳） | 主板 | 等 `0x87.flags.bit1` 恢复后重拍 |
| `9` | 副板地址未知（`0xF4` 未上报） | 主板 | 等 `0x88` 端点后重拍 |
| `0xFF` | 其它 | 副板 | 提示失败，可重试 |

**副板 → 主板的结果帧（`0xF2`）**

`0xF2` 的基础形态是 `[cmdType][status]`（LEN=2）；**当 `cmdType=0xCC` 时 LEN=18**，追加 `err` 与拍摄元数据，与主板下发的快门命令用同一个板间 `SEQ` 对应：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| `[0]` | 1 B | `cmdType` = `0xCC` |
| `[1]` | 1 B | `status`（3 成功 / 5 失败） |
| `[2]` | 1 B | `err`（同 `0x02` 错误码，`6`/`7`/`8`/`9` 由主板生成，副板不会回） |
| `[3~6]` | 4 B | `photoId` |
| `[7~10]` | 4 B | `bytes` |
| `[11~12]` | 2 B | `width` |
| `[13~14]` | 2 B | `height` |
| `[15~16]` | 2 B | `captureMs` |
| `[17]` | 1 B | 保留，填 `0` |

- 副板**只回结果，不回地址**：IP 与端口由主板从 `0xF4` 取，避免两块板对「我该报哪个 IP」产生分歧。
- 结果帧与 `0xF1` 的 `SEQ` 一一对应；超时后迟到的结果按 `SEQ` 丢弃，不再补 ACK。

**`CMD_PHOTO_STATUS(0xCD)`：图 ID 失效的明确回答**

App 取图收到 `404`、或怀疑 ACK 丢失时，发 `0xCD`（LEN=4，`[0~3] photoId`），主板用**缓存**回答，不重新拍照：

| 条件 | 主板回复 |
| --- | --- |
| `photoId` 与缓存一致 | `0x02` `status=3` + 完整元数据（图地址、字节数、宽高、耗时）→ App 直接重取，**不必重拍** |
| `photoId` 与缓存不一致 | `0x02` `status=5`、`err=6`（图 ID 已失效） |
| 缓存为空（主板重启过） | `0x02` `status=5`、`err=6` |
| 从未拍过照 | `0x02` `status=5`、`err=6` |

- 主板缓存**最近一次结果**（成功或失败都缓存），只存元数据、不存图，占几十字节；被下一次 `0xCC` 覆盖。
- 缓存随主板重启丢失，此时统一回 `err=6`，App 走 `/photo/latest` 或重拍即可。
- `0xCD` 幂等只读，不改变任何状态、不占用串口。

**分段超时**

| 段 | 起点 → 终点 | 超时 | 超时后 |
| --- | --- | --- | --- |
| ① 受理 | App 发出 → 主板 `ACK 0` | **10 ms**（本地判定，无重传） | 不适用；副板离线直接走终态 `err=8` |
| ② 拍摄 | `0xF1` 写入串口 → 副板 `0xF2` | **2000 ms**（UXGA 抓拍 + 编码预计 300~800 ms，含 200 ms × 3 次重传） | 主板回 `0x02 status=5, err=7`，记 `0x60/0x3D` |
| ③ 终态 | 收到 `0xF2` → 发出 `0x02` | **10 ms** | 不重发；App 用 `0xCD` 或 `/photo/latest` 兜底 |
| ④ 取图 | App GET → 收完 JPEG | App 侧 **10 s**（300 KB @ 2~5 Mbps ≈ 0.5~1.2 s） | `Range` 续传；仍失败则 `0xCD` 查状态 |
| 整体 | App 发出 → 收到 `0x02` | App 侧 **8 s** 兜底 | 提示超时，可 `0xCD` 补查 |

**三种失败与两种成功的区分（App 不得靠猜）**

| 情形 | 判定依据 | App 表现 |
| --- | --- | --- |
| **成功·可开始传输** | `0x02 status=3` 且 `err=0` 且 `photoId≠0` | 立即按 `ipv4:port` + `photoId` 取图 |
| **成功但地址缺失** | `0x02 status=3`、`err=9` | 先等 `0x88` 端点再取图（正常流程不会出现，`err=9` 只会出现在失败终态） |
| **失败·副板离线** | `0x02 status=5`、`err=8`（且无第 1 段 `ACK 0`） | 提示离线，等恢复 |
| **失败·拍摄失败** | `0x02 status=5`、`err=1~5` 或 `0xFF` | 按 `err` 给具体原因，可重试 |
| **失败·串口超时** | `0x02 status=5`、`err=7` | 提示超时，重试 1 次 |
| **图 ID 已失效** | 取图 `404` → `0xCD` 回 `err=6` | 走 `/photo/latest` 或重拍 |

**副板取图接口（App 直连）**

| 项 | 值 | 说明 |
| --- | --- | --- |
| 协议 | **HTTP/1.1（明文，不做 TLS）** | 局域网直连，TLS 只增加握手与内存开销 |
| 端口 | **8090**（副板） | 与视频端口（`0x88` 下发，默认 81）分开；主板不监听 |
| 单张 | `GET /photo/<photoId>` | `<photoId>` 取 `0x02` 的十进制 u32 |
| 最近一张 | `GET /photo/latest` | ACK 丢失、`err=6`、`404` 后的兜底 |
| 响应头 | `Content-Type: image/jpeg`、`Content-Length`、`X-Photo-Id`、`ETag` | App 用 `X-Photo-Id` 校正本地记录 |
| 断点续传 | **支持单段 Range**：`Range: bytes=a-b` → `206` + `Content-Range`；不支持多段 | 弱网从断点续，不整张重下 |
| 方法限制 | 只允许 `GET` / `HEAD`，其余回 `405` | 只读接口，杜绝误写 |
| 并发 | **1 个连接**，第二个请求回 `503` | 副板 CPU / 带宽有限 |
| `404` | 图不存在 / 已淘汰 / 副板重启过 | 用 `0xCD` 查，或走 `/photo/latest` |

**图 ID 与保留策略**

| 项 | 结论 |
| --- | --- |
| ID 规则 | `u32` **单调递增**，从 `1` 开始，`0xFFFFFFFF` 回绕到 `1`；`0` 保留表示「无效」 |
| 重启后 | **归零重来**：PSRAM 随掉电清空，旧 ID 全部失效，App 收到 `404` 后按 `err=6` 处理 |
| 保留张数 | **3 张**（3 × ≤400 KB ≈ 1.2 MB，PSRAM 8 MB 余量充足） |
| 淘汰 | 环形覆盖**最旧**一张；被覆盖的 ID 再取回 `404` |
| 是否落 flash | **不落**：擦写寿命、写入延迟与无必要都不划算 |
| 主板缓存 | **只缓存最近一次结果元数据**（`photoId`、`bytes`、`w`、`h`、`captureMs`、`ipv4`、`port`、`err`），**不缓存图像、不开收图端口** |
| 缓存寿命 | 直到下一次 `0xCC` 覆盖，或主板重启（RAM） |

**主板在拍照链路里的职责（只有三件）**

1. **转发快门**：`0xCC` → `0xF1`，只做协议校验与串口转发。
2. **回执与地址告知**：终态 `0x02` 里给副板 IP、端口、图 ID、字节数、宽高、耗时，并缓存这份元数据供 `0xCD` 重放。
3. **离线 / 超时代回**：副板离线立即 `err=8`；串口超时 `err=7`，绝不静默、不用 `ACK 0` 糊过去。

主板**不接收、不缓冲、不转发任何图像字节**——照片从副板直接到手机。

**与视频并存：拍照瞬间暂停视频**

- **暂停**，不并存：同一摄像头不能同时输出「低分辨率稳定流」与「UXGA 单帧」；UXGA 会挤占 ISP 与 PSRAM 带宽，并存会同时掉帧。
- 暂停时长典型 **≤300 ms**（抓拍 + 编码），最坏 2 s；拍完立即恢复推流。
- 代价：视频断 1~3 帧，不补帧、不重连；若暂停超过 2 s，副板结束本次推流，App 重新拉流。
- 明确取舍：**视频要稳（低分辨率高帧率），照片要清（高分辨率单张）**。

**安全**

- 局域网内**不做鉴权**：取图接口只读（`GET`/`HEAD`）、设备不暴露公网、照片内容不敏感。
- **「随机端口」不作为安全手段**：端口在 `0x02` 里明文下发，扫描照样能找到；固定 8090 反而便于排障。
- 若将来需要鉴权，做法是 `0x02` 里带一次性 token、取图时放 `?t=`，一次有效；当前不做。

**照片为什么不进 V21**

| 原因 | 说明 |
| --- | --- |
| 长度 | V21 的 LEN 为 1 B（≤255 B）；一张 UXGA JPEG 约 150~300 KB，要切上千帧 |
| 序号 | 上千帧会瞬间刷掉 64 条去重环，SEQ 窗口失去意义 |
| 校验 | 每帧 CRC8 只能保单帧，整图仍需端到端校验，等于两套校验 |
| 重传 | 丢一帧就要整图重传，而 HTTP/TCP 已经处理了重传与流控 |
| 阻塞 | 上千帧会占满 ctrl 队列，把 ACK 与运动命令压到秒级延迟 |

结论：**V21 只承载「拍照命令 + 两段结果」，照片本体走副板的 HTTP 直连通道。**

# 江灵通信协议 · 回复（ACK）

> 本文件只写 ACK（车 → App）。TYPE 与长度取自固件 `Protocol.h`。
> 这 64 个类型是**平铺**的：低 6 位就是类型序号，表里的「分区」只是文档阅读用的中文分类，不是位域；App 与固件都按整字节 TYPE 查表。高 2 位 KIND 只表示方向（本表全部为 ACK）。
> 帧格式：`AA | SEQ | TYPE | LEN | PAYLOAD | CRC8`，帧总长 `5 + LEN`。`ACK_RESULT` / `ACK_SESSION_INIT` / `ACK_ERROR` 的 PAYLOAD 均为 2 B（`LEN=2`、帧长 7 B）；新增的 `ACK_PHOTO(0x02)` 为 23 B（帧长 28 B）。SEQ 原样回显被应答 CMD 的 SEQ。

| TYPE | Name | 分区 | KIND_TYPE | 功能 | 参数及说明 | 特殊说明 |
| --- | --- | --- | --- | --- | --- | --- |
| `0x00` | `ACK_RESULT` | 回复 | `000000` | 命令结果应答 | `2B — [cmdType, status]`：`cmdType` = 被应答 CMD 的完整 TYPE；`status`：`0` 已收到/执行中、`1` 是、`2` 否、`3` 完成、`4` 未实现、`5` 参数或执行错误、`6` 当前不允许 | SEQ 回显 CMD 的 SEQ；对账必须 `SEQ + cmdType` 双条件；ACK 丢失不重发；重复 CMD 也回 `3` |
| `0x01` | `ACK_SESSION_INIT` | 回复 | `000001` | 握手指令应答 | `2B — [status, resetDone]`：`status` 同上；`resetDone` = `1` 车端已复位 / `0` 未复位 | 只应答 `CMD_SESSION_INIT`（SEQ=0）；`resetDone=1` 时 App 清空 SEQ 窗口与待确认队列；版本不等回 `5` |
| `0x02` | `ACK_PHOTO` | 拍照 | `000010` | 拍照终态应答（带取图地址与图元数据） | `23B — [cmdType][status][err][photoId:4][bytes:4][width:2][height:2][captureMs:2][ipv4:4][port:2]`，全部大端；字段表与错误码见 §1.6 | 只在 `0xCC` / `0xCD` 使用；`status=3` 表示图已存在、可直连取图；SEQ 回显被应答 CMD 的 SEQ |
| `0x10` | `ACK_ERROR` | 错误 | `010000` | 协议 / 链路级错误 | `2B — [cmdType, errorCode]`：`errorCode` 尚未定义 | 已定义、当前不发；与 `ACK_RESULT` 状态 5 分工：前者协议/链路级，后者命令执行级 |

- 未登记 TYPE 车端不应答；超时是唯一兜底：普通命令 4 s，`0xCC` 8 s，不自动重发。
- 一个命令只回一条 `ACK_RESULT`；**唯一允许两段的命令是 `0xCC`**：先 `ACK_RESULT 0`（已受理），再 `0x02`（终态），两帧同一 SEQ。
- **ACK 只有一条回程通道**：初始化命令（`0xC4`~`0xCA`）与运行期命令的 ACK 一律走 **回程 TCP 8080**，不按通道分叉。命令下行单走 UDP 8081，**ACK / DAT / LOG 全部走 TCP 8080**。
- **回程保活（定稿 2026-11-12）**：TCP 客户端连上后，板子保证**任意 9 s 窗口内至少发出 1 帧**回程数据（空闲、未完成 `0xC0` 会话初始化、AP 档均成立）。实现复用 `0x86 DAT_WIFI_STATUS`：客户端连上立即一帧，之后每 **5 s** 一帧，`mode`/`state` 跳变立即补帧；不新增 TYPE。App 侧断链判定可用「TCP 无字节 3 s × 3 次 = 9 s」。
- `CMD_WIFI_MODE(0xC4)` 等配置命令的失败（参数非法、缺凭据）统一回 `ACK_ST_ERROR(5)`；`CMD_WIFI_STATUS(0xC7)` 只回 `ACK_RESULT`（`3` 已就绪 / `5` 未就绪），状态细节由运行期 `0x86` 提供。

## 1. 江灵初始化的 ACK 语义

初始化命令（`0xC4`~`0xCA`）**没有独立 ACK TYPE**，一律复用 `ACK_RESULT(0x00)`（`cmdType` 填被应答命令的完整 TYPE，SEQ 回显），状态码沿用上表 0~6。命令从 **UDP 8081** 下发，ACK 从 **TCP 8080** 回；`0x87` / `0x88` 等 DAT 同样只走 TCP 8080。

> 前提：**配网也走 WiFi**。App 在 UDP 8081 上依次下发 `0xC4`（模式）/ `0xC5`（STA 凭据）/ `0xC6`（AP 凭据），`0xC8` 提交（`0xC9` 查状态、`0xCA` 恢复默认），ACK 全部从 TCP 8080 回。不存在第二条配网链路。

### 1.1 `CMD_INIT_COMMIT(0xC8)` 的状态码

| status | 含义 | 车端动作 | App 应做什么 |
| --- | --- | --- | --- |
| `0` | 已收到、开始执行 | 保存到 RAM、向副板同步凭据、**断开旧 STA 用新凭据重连**（≤20 s） | **静默**，只切到「配置中」界面；不弹窗、不重发，等终态 |
| `3` | **初始化完成** | 新网络已就绪（副板凭据已经串口 `0xF0` 同步）；**此帧由板子主动发出** | **提示「初始化完成」**；随后直接用 `0x87.ipv4` 连 TCP 8080，不再有切换通道的动作 |
| `5` | 参数或执行错误 | 保持当前 WiFi 状态，留在等待态等重试 | **提示原因并留在配网页**：模式越界、缺 STA 凭据、认证失败、兜底 AP 起不来、**副板同步失败**、20 s 未拿到 IP |
| `6` | 当前不允许 | 上一次 `0xC8` 还在执行中 | **静默**（不重发），等前一次的终态 |

- `4`（未实现）与 `1`/`2` 不用于 `0xC8`。
- `0` 与 `3` 是**异步两条**、同一 SEQ；App 的对账条件仍是 `SEQ + cmdType` 双条件，收到 `3` 才算结束。
- **`3` 只代表主板本板就绪**：副板是否连上属于运行期信息（`0x87` / `0x88`），不影响 `0xC8` 的结论（视频缺失只降级，不影响控制）。
- **初始化完成只看 `[0xC8][3]`**：没有第二条链路需要关闭，也没有「断开即成功」的信号可依赖。
- 副板 `0xF0` 同步失败（`0xF2 status≠3`）→ 整次提交回 `5`，App 可重提。

### 1.2 `CMD_BLE_CONTROL(0xCB)`（已废弃）

`0xCB` 随蓝牙整体移除而废弃：**编号保留、不复用**。车端收到后一律回 `ACK_RESULT` `[0xCB][4]`（`UNKNOWN`），**不执行任何动作**，也不产生 LOG。

| status | 场景 | 车端动作 | App 应做什么 |
| --- | --- | --- | --- |
| `4` | 任何 `0xCB`（任意 `LEN` / PAYLOAD） | 只回 `[0xCB][4]`：不改 WiFi 状态、不断链、不重配网 | 不依赖 `0xCB`；配网直接用 `0xC4`~`0xC8` |

- 废弃原因：蓝牙整体移除，不再存在广播开关与断链收尾；`0xCB` 的历史语义（`payload[0]=0` 关闭蓝牙、`=1` 恢复广播）**全部作废**。
- 保留编号是为了不让既有 TYPE 表出现空洞与重排。

### 1.3 `CMD_INIT_STATUS(0xC9)`

| 场景 | 车端 | App |
| --- | --- | --- |
| 未提交过 `0xC8` | `ACK_RESULT` `[0xC9][4]` | 还没开始初始化 |
| `0xC8` 已受理、新网络未就绪 | `ACK_RESULT` `[0xC9][0]` | 继续等 `[0xC8][3]` |
| 初始化完成 | `ACK_RESULT` `[0xC9][3]` | 同收到 `[0xC8][3]`，初始化完成 |

- `0xC9` **只回 ACK**，不回 DAT、不改状态、不触发断链。

### 1.4 `CMD_INIT_FACTORY_RESET(0xCA)`

| status | 含义 | App |
| --- | --- | --- |
| `3` | 已清空并即将重启 | **提示已恢复出厂**；清空本地缓存的车 IP 与配网状态；板子重启后回到**常量网络**（STA 自动连 `jianglingAPP`），需重新配网时下发 `0xC4`~`0xC8`。只想换回兜底 AP、不清凭据时用 `0xC4(1)` + `0xC8(1)`，不要用本命令 |
| `5` | `magic != 0x5A` 或清空 RAM 凭据失败 | **提示失败**，保持连接 |

### 1.5 App 的提示策略（总结）

| 收到 | 提示 | 理由 |
| --- | --- | --- |
| `0xC8` → `0` | 不提示（转圈/进度态） | 中间态，用户不需要知道 |
| `0xC8` → `3` | 提示「初始化完成」 | 这是唯一的成功判据 |
| `0xCB` → `4` | 不提示 | 已废弃，编号保留不复用，收到即 `UNKNOWN` |
| `0xC8` → `5` | 提示失败原因，留在配网页 | 需要用户改参数重试 |
| `0xC8` → `6` | 不提示 | 重复点击导致，等前一次结果 |
| `0xC9` → `3` | 不提示 | 只读补查 |
| `0xCA` → `3` | 提示已恢复出厂 | 破坏性操作要明确告知 |
| 4 s 无任何 ACK | 提示「设备无响应」 | 链路问题，超时是唯一兜底 |

### 1.6 拍照的 ACK 语义（`0xCC` / `0xCD` → `0x02`）

拍照是**唯一转发到副板**的命令，也是唯一允许两段 ACK 的命令。两段分工：

| 段 | 帧 | 触发点 | 含义 | App 显示 |
| --- | --- | --- | --- | --- |
| 第 1 段 | `ACK_RESULT(0x00)` `[0xCC][0]` | 主板已完成校验并**把 `0xF1` 写进串口** | 已受理，**不代表拍到了** | 「拍摄中」 |
| 第 2 段 | `0x02 ACK_PHOTO` | 副板结果已回主板，或主板判定失败 | 终态：`status=3` 图已存在可取；`status=5` 失败看 `err` | 成功图 / 失败原因 |

**`0x02` 字段**

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| `[0]` | 1 B | `cmdType` | `0xCC`（拍照）或 `0xCD`（状态查询）；`0xCD` 的回复同样用 `0x02` |
| `[1]` | 1 B | `status` | `3` 成功 / `5` 失败 / `6` 上一张未完成 |
| `[2]` | 1 B | `err` | 错误码，成功时 `0` |
| `[3~6]` | 4 B | `photoId` | u32；失败时 `0` |
| `[7~10]` | 4 B | `bytes` | JPEG 字节数；失败时 `0` |
| `[11~12]` | 2 B | `width` | 像素宽；失败时 `0` |
| `[13~14]` | 2 B | `height` | 像素高；失败时 `0` |
| `[15~16]` | 2 B | `captureMs` | 拍摄 + 编码耗时（ms） |
| `[17~20]` | 4 B | `ipv4` | 副板 IP（主板由 `0xF4` 缓存）；失败或无地址时 `0` |
| `[21~22]` | 2 B | `port` | 副板取图端口（默认 8090）；失败时 `0` |

**错误码 `err`**

| err | 含义 | 产生方 | App 处理 |
| --- | --- | --- | --- |
| `0` | 无 | — | 按 `ipv4:port` + `photoId` 取图 |
| `1` | 对焦失败 | 副板 | 重试 1 次 |
| `2` | 内存不足 | 副板 | 提示后重试 |
| `3` | JPEG 编码失败 | 副板 | 重试 1 次 |
| `4` | 副板忙 | 副板 | 500 ms 后重试 |
| `5` | 摄像头未就绪 | 副板 | 等视频源上线 |
| `6` | 图 ID 已失效 | 主板（`0xCD` 判定） | 走 `/photo/latest` 或重拍 |
| `7` | 串口超时 | 主板 | 重试 1 次 |
| `8` | 副板离线 | 主板 | 等 `0x87.flags.bit1` 恢复 |
| `9` | 副板地址未知 | 主板 | 等 `0x88` 端点后重拍 |
| `0xFF` | 其它 | 副板 | 提示失败 |

**三种失败、两种成功的判定（App 不得靠猜）**

| 情形 | 判定 | App 行为 |
| --- | --- | --- |
| 成功·可开始传输 | `0x02 status=3`、`err=0`、`photoId≠0`，且此前已收到 `ACK 0` | 直接取图 |
| 成功·但图已不在 | 取图 `404`，`0xCD` 回 `err=6` | 改取 `/photo/latest` 或重拍 |
| 失败·副板离线 | `0x02 status=5`、`err=8`，**且没有第 1 段 `ACK 0`** | 提示离线，等恢复 |
| 失败·拍摄失败 | `0x02 status=5`、`err=1~5`/`0xFF` | 按 `err` 给具体原因 |
| 失败·串口超时 | `0x02 status=5`、`err=7` | 提示超时，重试 1 次 |
| 超时兜底 | 8 s 内只有 `ACK 0` 或什么都没有 | 提示超时，可发 `0xCD` 补查 |

- **`0xCD` 不拍照**：主板用缓存比对 `photoId`，一致就重放 `status=3` + 完整元数据（App 不必重拍），不一致或缓存为空回 `err=6`。
- 副板离线时**不回 `ACK 0`**，只回终态 `err=8`，避免「已受理」误导。

### 1.6 转发命令的通用 ACK 口径

| 项 | 约定 |
| --- | --- |
| 谁回 ACK | **只有主板**。副板的结果经 `0xF2` 回主板，主板按 `ACK_RESULT` / `0x02` 统一组帧；副板从不直接对 App 说话 |
| 终态来源 | `ACK_RESULT.status` 原样透传副板的 `0xF2.status`（`0`/`3`/`4`/`5`/`6`），主板不改写 |
| 超时 | 普通转发命令 300 ms 无 `0xF2` → 主板回 `ACK_RESULT 5`；`0xCC` 为 2000 ms → `0x02 err=7` |
| 离线 | 副板离线（600 ms 无心跳）→ 立即回 5（`0xCC` 回 `0x02 err=8`），不发串口、不排队 |
| 迟到结果 | 超时后迟到的 `0xF2` 按板间请求序号丢弃，**不补第二条 ACK** |
| ACK 丢失 | 与既有口径一致：**不重发**；由 App 用幂等查询（`0xC9` / `0xCD`）或下一次业务动作兜底 |
| 去重 | 重复的转发命令按主板 64 条 CMD 环去重，重复时回 `3`，**不会让副板再执行一次** |

- 这里没有独立的「转发 ACK」TYPE：统一复用 `ACK_RESULT`，拍照例外用 `0x02`。
- `SEQ` 始终是 App 的计数器；板间序号只在串口内部使用，App 看不到也不需要知道。

### 1.7 流式运动 / 云台的 ACK 口径（`0xEB` / `0xEC`）

| 项 | 约定 |
| --- | --- |
| 谁回 | 主板本地执行后直接回，不经串口 |
| 每帧都回 | **是**。`0xEB`、`0xEC` 各 5 Hz，两条同时跑约 10 条 ACK/s，回复栈（8 条）够用 |
| 状态码 | `[cmdType][0]`：已受理并写入目标；`[cmdType][3]`：本次为 `0/0`（等价停车，目标已清零） |
| 越界值 | 车端夹取后**照常执行**并回 `0`，不回 `5`——流式命令不因单个坏值中断推送 |
| 非法帧 | `LEN≠2`、CRC 错、未登记 TYPE：整帧丢弃、**不回 ACK**，App 以 4 s 超时兜底 |
| ACK 丢失 | **不重发、不补第二条**；App 不做逐帧对账，只用它判断「链路仍然通」 |
| ACK 丢失 ≠ 车停 | 车是否继续动，只看有没有新帧；ACK 丢不影响动作，**车端按 300 ms 超时自停** |
| 与 `0xE0` 的关系 | `0xE0` 回 `[0xE0][3]`，回完即已清空全部移动 / 云台目标与计时，之后不会再有旧动作的 ACK |
